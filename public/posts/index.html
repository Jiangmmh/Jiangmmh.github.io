一、简介 RISC-V的支持 RISC-V 指令（包括用户指令和内核指令）操作的是虚拟地址。而机器的RAM则需要使用物理地址来访问。RISC-V 页表硬件通过将每个虚拟地址映射到一个物理地址，将这两种地址连接起来。 xv6使用RISC-V的Sv39模式，其仅使用64位虚拟地址中低39位。在该设置下： 每个页面为4KB，使用低12位地址索引 采用三级页表，每级页表使用9位，共剩余27位进行索引 RISC-V 的设计为虚拟地址和物理地址的扩展都预留了空间。如果需要更多虚拟地址空间，RISC-V 支持 Sv48 模式，即 48 位虚拟地址。 下面是页表项的构成，包括了上述的39位物理地址和低10位的标志位。 PTE_V：指示了该PTE是否存在 PTE_R、PTE_W、PTE_X：指示可读、可写和可执行权限 PTE_U：控制该页面是否可以被用户程序访问 PTE_G、PTE_A：暂时未使用 RSW：还剩下两个保留位，可以根据需要来使用 每当执行RISC-V的访存指令时，就需要执行上述地址转换过程。在xv6的进程被调度上CPU时，会将进程根页目录表的地址存放到当前CPU的控制寄存器 satp 中。 多级页表虽然节省内存，但是访问某个页面中的数据需要多次访问内存，为了尽可能避免从虚拟地址到物理地址转换过程中的访存开销，RISC-V硬件提供了TLB（Translation Look-aside Buffer）来缓存部分虚拟地址到物理地址到映射，其思想和Cache类似，都是通过局部性原理构建。 内核地址空间 xv6 启动时会创建一个单页表，用于描述内核的地址空间，具体的布局定义见kernel/memlayout.h。 QEMU 模拟一台计算机，该计算机包含从物理地址0x80000000开始，直至0x88000000 。 其中大部分页面都采用对等映射（对等映射）实现（虚拟地址 == 物理地址），只有少数几个内核虚拟页面没有直接映射： 跳转页（Trampoline）。它被映射到虚拟地址空间的顶部；用户页表也具有相同的映射关系。一个物理页（包含跳转代码）在内核的虚拟地址空间中被映射了两次：一次在虚拟地址空间的顶部，另一次是直接映射。 内核栈保护页。每个进程都有自己的内核栈，它映射到较高的内核虚拟地址，这样 xv6 可以在其下方留下一个未映射的保护页。保护页的页表项 (PTE) 无效（即PTE_V未设置），因此如果内核栈溢出，很可能会导致缺页错误，内核崩溃。如果没有保护页，溢出的栈会覆盖其他内核内存，导致运行异常。崩溃崩溃是更可取的。 二、物理内存源码分析 物理内存的初始化 在main()函数中，调用了kinit()函数来初始化物理内存子模块： void kinit() { initlock(&kmem.lock, "kmem"); freerange(end, (void *)PHYSTOP); } 其中调用了freerange()函数，传入两个参数end和PHYSTOP，前者在链接脚本中被定义，位于 .text, .rodata, .data, .bss段之后的位置。后者的值为0x88000000，表示物理地址顶部。 void freerange(void *pa_start, void *pa_end) { char *p; p = (char *)PGROUNDUP((uint64)pa_start); for (; p + PGSIZE <= (char *)pa_end; p += PGSIZE) { kfree(p); } } 其中通过反复调用kfree()构造出一个存储4KB物理页帧的freelist。 struct run { struct run *next; }; struct { struct spinlock lock; struct run *freelist; } kmem; // Free the page of physical memory pointed at by pa, // which normally should have been returned by a // call to kalloc(). 本文是基于经典 BSD 进程间通信教程所涉及的概念重新编写的中文学习笔记，并非原文的逐字翻译。 参考原文： Stuart Sechrest, An Introductory 4.4BSD Interprocess Communication Tutorial 。原文属于 4.4BSD 文档档案。 一、为什么需要进程间通信？ 现代操作系统通常同时运行大量进程。例如文本编辑器、浏览器、数据库、网络服务、编译器以及系统后台服务，都可能由多个进程协同完成工作。 进程之间拥有相对独立的地址空间。一个进程中的普通指针通常不能直接访问另一个进程的内存，因此，进程不能像同一个程序中的两个函数那样，直接通过共享变量交换数据。 例如，一个网络服务器可能将工作划分为多个部分： 主进程负责监听连接和接收客户端请求。 工作进程负责处理具体请求。 日志进程负责收集并写入日志。 其他辅助进程负责缓存、配置更新或后台任务。 这些进程需要交换数据、传递任务、同步状态，甚至协调资源的使用。这就需要进程间通信机制，即 IPC（Inter-Process Communication）。 Unix/Linux 提供了多种 IPC 机制，包括： 匿名管道（Pipe） 命名管道（FIFO） socketpair() Unix Domain Socket TCP Socket UDP Socket 共享内存 消息队列 信号量与其他同步机制 这些机制并不是彼此完全独立的技术。它们反映了操作系统设计中的几个核心问题： 通信双方如何找到彼此？ 内核如何在两个进程之间传递数据？ 通信是否需要可靠、有序地交付数据？ 通信双方是否必须存在于同一台机器？ 数据是否具有明确的消息边界？ 当一方退出、崩溃或停止读取时，另一方会发生什么？ 理解这些问题，比单纯记住系统调用更重要。 本文主要围绕 Berkeley Unix 4.4BSD 的经典 IPC 教程所涉及的机制展开，并使用现代 Linux/POSIX C 接口编写示例。原始手册是理解 Unix IPC 设计的重要历史材料，但部分环境细节和接口习惯具有时代特征，因此本文会区分通用概念与现代 Linux 实践。 二、Unix IPC 的基本设计思想 2.1 将通信抽象为 I/O Unix 的一个重要设计思想是：尽可能使用统一的接口操作不同类型的资源。 ...
