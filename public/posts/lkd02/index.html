1. 本章概览#

第一章介绍了 Linux 内核的历史、定位和整体设计，而第二章开始进入实际开发：如何获取内核源码、如何编译和安装内核，以及编写内核代码时需要遵循哪些特殊规则。

本章主要回答三个问题：

  1. 源码从哪里来？ 如何获取、管理和组织 Linux 内核源码？
  2. 内核如何构建？ 如何配置、编译和安装一个 Linux 内核？
  3. 内核代码有什么特殊之处？ 为什么内核开发不能完全按照普通 C 程序的方式进行？

其中，第三个问题尤其重要。Linux 内核虽然主要使用 C 语言编写，但它并不是一个普通的 C 应用程序。它运行在特权环境中，直接管理硬件和内存，必须处理异步中断、多处理器并发以及严格的资源限制。

2. 获取 Linux 内核源码#

Linux 内核源码可以从官方网站获取：

  • 官方网站：https://www.kernel.org/
  • 官方 Git 仓库：https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

官方提供两种主要获取方式：

  • Tarball：完整源码压缩包。
  • Git：通过版本控制系统获取和管理源码。

2.1 使用 Git#

Linux 内核使用 Git 进行版本管理。Git 最初由 Linus Torvalds 创建，具有分布式版本控制的特点。

相比下载压缩包，使用 Git 更适合长期阅读、修改和研究内核源码。

获取 Linus 主线仓库：

git clone https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux

查看当前版本：

git describe --tags --always

获取远程更新：

git pull

查看提交历史：

git log --oneline --graph --decorate -20

查看某个文件的修改历史：

git log --oneline -- kernel/sched/core.c

查看某次提交修改了什么：

git show <commit>

为什么推荐使用 Git？

内核开发不是简单地下载一份源码然后阅读。我们经常需要：

  • 对比不同版本的实现；
  • 追踪某个函数的历史变化；
  • 查看一个 bug 是如何被修复的；
  • 将自己的修改与上游版本进行比较；
  • 在不同版本之间切换，验证某个行为。

Git 可以将这些工作整合到同一个工作流中。

2.2 安装内核源码#

除了 Git，也可以下载完整源码压缩包。

例如：

wget https://cdn.kernel.org/pub/linux/kernel/v6.x/linux-6.x.y.tar.xz
tar -xf linux-6.x.y.tar.xz
cd linux-6.x.y

这里的版本号只是示意，应根据 kernel.org 上实际发布的版本选择。

书中还介绍了传统的 gzip 和 bzip2 压缩包：

tar xvzf linux-x.y.z.tar.gz
tar xvjf linux-x.y.z.tar.bz2

需要注意源码目录的位置。

书中建议不要直接在 /usr/src/linux 中进行开发。这个目录通常用于存放系统安装的内核源码或相关链接。实际研究和修改时，应该将源码放在自己的工作目录中。

例如：

mkdir -p ~/kernel
cd ~/kernel
git clone https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

这样可以避免开发过程依赖 root 权限，也能避免影响系统原有的源码目录。

2.3 使用 Patch#

在 Linux 内核开发社区中，Patch（补丁）是非常重要的代码交流方式。

开发者通常不会直接把整个源码目录发送给其他人，而是通过补丁描述代码修改。

例如：

git diff

生成补丁：

git diff > my-change.patch

应用补丁：

patch -p1 < my-change.patch

如果使用 Git，也可以使用：

git format-patch -1

生成适合提交邮件的补丁。

应用 Git 格式的补丁：

git am 0001-some-change.patch

Patch 不仅用于提交自己的代码，也可以用于版本升级。

例如，假设当前有一个旧版本源码，需要升级到下一个版本。如果存在对应的增量补丁，就不必重新下载整个源码包。

patch -p1 < patch-x.y.z

不过，需要注意补丁的基准版本：补丁通常针对特定的上游版本生成，不能随意应用到不匹配的源码树上。

3. Linux 内核源码目录结构#

Linux 内核是一个规模庞大的软件项目。理解源码树的组织方式，可以帮助我们快速定位需要阅读的代码。

以下是内核源码根目录中比较重要的目录：

目录 作用
arch/ 与处理器架构相关的代码
block/ 块设备 I/O 层
crypto/ 加密相关接口与实现
Documentation/ 内核文档
drivers/ 设备驱动
firmware/ 驱动使用的固件
fs/ VFS 和具体文件系统
include/ 内核头文件
init/ 内核启动和初始化
ipc/ 进程间通信
kernel/ 内核核心子系统，例如调度器
lib/ 内核通用辅助函数
mm/ 内存管理与虚拟内存
net/ 网络协议栈
samples/ 示例代码
scripts/ 构建和辅助脚本
security/ 安全子系统
sound/ 音频子系统
tools/ 内核开发相关工具
usr/ 早期用户空间相关代码
virt/ 虚拟化相关基础设施

这里需要重点关注几个目录：

arch/：体系结构相关代码

不同处理器架构在启动流程、中断处理、内存管理和上下文切换等方面存在差异。

例如：

arch/
├── arm/
├── arm64/
├── powerpc/
├── riscv/
└── x86/

如果研究 x86 系统调用入口，可以从 arch/x86/ 入手；如果研究 RISC-V 的异常和中断处理，则需要关注 arch/riscv/。

kernel/：内核核心功能

这里包含许多核心子系统，例如：

  • 进程管理；
  • 调度器；
  • 同步机制；
  • 定时器；
  • 内核模块相关基础设施。

mm/：内存管理

这里包含物理内存分配、虚拟内存管理、页面回收等实现。

fs/：文件系统

包含 VFS（Virtual Filesystem）以及各种具体文件系统的实现。

drivers/：设备驱动

包含大量硬件设备驱动程序，是内核源码中规模非常庞大的部分。

3.1 根目录中的重要文件#

除了目录，根目录还有几个值得关注的文件：

文件 作用
COPYING Linux 内核许可证，GPL-2.0
CREDITS 对内核贡献者的致谢
MAINTAINERS 子系统和驱动维护者信息
Makefile 内核顶层构建入口
.config 当前内核配置

其中，MAINTAINERS 对源码阅读和开发非常有用。

当你不知道某个子系统由谁维护，或者准备向上游提交修改时，可以通过这个文件找到对应的维护者和邮件列表。

4. 构建 Linux 内核#

Linux 内核使用 Makefile 组织构建流程。

一个典型的内核构建过程包括：

  1. 配置内核；
  2. 编译内核；
  3. 编译内核模块；
  4. 安装内核和模块；
  5. 配置引导程序并启动新内核。

4.1 配置内核#

Linux 支持大量硬件设备、文件系统和内核功能。不同机器的硬件环境和使用需求不同，因此内核提供了丰富的配置选项。

配置选项通常以 CONFIG_ 开头。

例如：

CONFIG_SMP
CONFIG_PREEMPT
CONFIG_MODULES

其中：

  • CONFIG_SMP：控制对对称多处理器的支持。
  • CONFIG_PREEMPT：与内核抢占相关。
  • CONFIG_MODULES：控制内核模块支持。

配置选项不仅决定哪些源文件参与编译，也可能通过预处理宏影响代码逻辑。

配置选项主要有以下几种类型：

Boolean：布尔类型

只有两种状态：

  • y：启用；
  • n：禁用。

Tristate：三态类型

具有三种状态：

  • y：编译进内核主体；
  • m：编译为独立的可加载模块；
  • n：不编译。

例如：

CONFIG_EXT4_FS=y
CONFIG_USB_STORAGE=m

前者表示将 ext4 文件系统直接编译进内核，后者表示将 USB 存储驱动编译为模块。

此外，配置项还可以是字符串或整数，用来向内核代码提供具体的配置值。

4.2 常用配置工具#

Linux 提供了多种配置工具。

make config

逐项询问所有配置选项：

make config

配置项很多，因此这种方式通常比较繁琐。

make menuconfig

基于 ncurses 的文本交互界面：

make menuconfig

这是非常常见的内核配置方式。

make gconfig

基于 GTK 的图形配置界面：

make gconfig

make defconfig

使用当前架构的默认配置生成 .config：

make defconfig

适合初次编译内核时快速建立一个可用的配置基础。

make oldconfig

使用已有的 .config，针对新版本中增加或变化的配置项进行更新：

make oldconfig

例如，将旧版本的配置文件复制到新版本源码目录后，可以运行 make oldconfig，让配置系统处理新旧版本之间的差异。

4.3 .config 文件#

内核配置最终保存在源码根目录的 .config 文件中。

例如：

CONFIG_64BIT=y
CONFIG_SMP=y
CONFIG_MODULES=y
CONFIG_PREEMPT_NONE=y

可以直接搜索配置：

grep CONFIG_SMP .config

也可以查看当前正在运行的内核是否提供了配置文件：

zcat /proc/config.gz > .config

这要求当前内核启用了 CONFIG_IKCONFIG_PROC。

这种方式的价值在于：可以基于当前系统的内核配置，构建一个具有相似功能和硬件支持的新内核。

4.4 编译内核#

完成配置后，就可以开始编译：

make

Linux 内核的 Makefile 会根据配置自动组织编译过程。

书中指出，从 Linux 2.6 开始，构建系统已经进行了较大改进，不再需要早期版本中的某些手动依赖生成步骤。

实际开发中，建议使用多任务并行编译：

make -j$(nproc)

nproc 会返回当前系统可用的处理器数量。

例如：

make -j8

表示最多使用 8 个并行任务。

内核构建系统的依赖关系已经能够支持并行编译，因此可以显著缩短构建时间。

4.5 减少编译输出#

内核编译过程中会产生大量输出信息。

如果希望减少终端输出，可以将标准输出重定向：

make > build.log

如果只想保留错误输出：

make > /dev/null

不过，实际开发中我更推荐保留完整日志：

make -j$(nproc) 2>&1 | tee build.log

这样既可以实时观察构建过程，也能在失败后检查日志。

例如：

grep -n "error:" build.log
grep -n "warning:" build.log

4.6 安装新内核#

编译完成后，需要安装内核及其模块。

书中以 x86 和 GRUB 为例，介绍了手动复制内核镜像、修改引导配置的方式。

例如，传统 x86 构建的内核镜像通常位于：

arch/i386/boot/bzImage

现代 x86-64 构建的镜像通常位于：

arch/x86/boot/bzImage

安装模块：

sudo make modules_install

模块通常会被安装到：

/lib/modules/<kernel-version>/

随后还需要将内核镜像放入启动分区，并配置引导程序。不同发行版和启动环境可能采用不同的安装流程。

书中还提到了 System.map 文件。它包含内核符号及其地址映射信息，在分析内核地址、定位符号和调试时具有价值。

一个非常重要的实践建议：不要直接覆盖唯一可用的内核。

始终保留一个已知可以正常启动的内核，以便新内核启动失败时能够恢复。

5. 内核是一种不同的程序#

本章后半部分是最值得理解的内容：Linux 内核和普通用户态程序之间有哪些根本区别？

内核主要使用 C 语言编写，但不能将普通用户态 C 程序的编程习惯直接搬到内核中。

书中总结了内核开发的几个重要特征：

  1. 没有 libc 和标准 C 头文件；
  2. 使用 GNU C 扩展；
  3. 缺乏用户态程序所拥有的内存保护；
  4. 不方便使用浮点运算；
  5. 内核栈较小且大小固定；
  6. 必须认真处理同步和并发；
  7. 必须重视可移植性。

下面逐一理解。

5.1 没有 libc 和标准头文件#

普通用户态程序通常依赖 C 标准库，例如：

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

可以直接使用：

printf();
malloc();
free();
memcpy();
strlen();

但是，Linux 内核不能直接使用 libc。

原因主要有两个：

  • 内核不能依赖一个需要内核自身提供基础服务才能正常运行的用户态库；
  • 完整的 C 标准库对于内核来说过于庞大，直接依赖它会增加不必要的开销和复杂度。

因此，内核提供了自己的基础设施。

例如：

用户态常见接口 内核中的相关接口
printf() printk()
malloc() kmalloc() 等
free() kfree()
memcpy() 内核提供的 memcpy()
strlen() 内核提供的 strlen()

这里需要注意：这些接口并不是简单的一一替换。

例如，kmalloc() 和用户态 malloc() 的语义及使用约束并不相同，内核还需要考虑分配上下文、是否允许睡眠以及内存分配标志等问题。

内核自身的字符串操作函数可以在相关内核头文件中找到，例如：

#include <linux/string.h>

内核打印信息则使用：

printk("Hello world: %s, %d\n", str, i);

printk() 会将格式化信息写入内核日志缓冲区，用户可以通过 dmesg 等工具查看。

dmesg

核心理解：内核不能依赖用户态的 C 运行时环境，因此必须拥有自己的基础函数、内存管理和运行时设施。

5.2 GNU C#

Linux 内核并不局限于严格的 ANSI C 语法，而是使用 GNU C 提供的扩展。

这些扩展能够让内核代码更简洁，也可以更直接地表达底层操作。

本章重点介绍了三类内容：

  • Inline Functions；
  • Inline Assembly；
  • Branch Annotation。

5.2.1 Inline Functions#

内联函数使用 inline 关键字声明：

static inline int add(int a, int b)
{
    return a + b;
}

编译器可以将函数调用展开为函数体中的指令，从而减少普通函数调用的开销。

内核中经常使用内联函数实现短小、频繁调用的辅助操作。

不过，inline 只是向编译器提供优化建议，并不保证一定会展开。是否真正内联还受到编译器优化策略的影响。

5.2.2 Inline Assembly#

GNU C 支持在 C 代码中嵌入汇编指令。

基本形式：

asm volatile(
    "assembly code"
    : output operands
    : input operands
    : clobbered registers
);

例如：

unsigned long value;

asm volatile(
    "mov %%rsp, %0"
    : "=r"(value)
);

这段代码在 x86-64 上读取当前栈指针。

其中：

  • asm 表示嵌入汇编；
  • volatile 告诉编译器不要随意删除这段汇编；
  • =r 表示输出操作数使用通用寄存器；
  • %0 表示第一个操作数。

在内核开发中，内嵌汇编通常用于：

  • 访问特殊寄存器；
  • 执行处理器特定指令；
  • 实现原子操作；
  • 操作中断和处理器状态；
  • 实现架构相关的底层机制。

需要注意，内嵌汇编不等于可以忽略编译器约束。寄存器、内存和条件码等副作用必须正确声明，否则编译器优化可能破坏程序行为。

5.2.3 Branch Annotation#

内核提供了 likely() 和 unlikely() 宏，用于向编译器表达分支预测倾向。

例如：

if (unlikely(error)) {
    /* error handling */
}

表示错误分支通常不应该发生。

相反：

if (likely(success)) {
    /* normal path */
}

表示成功分支通常会发生。

这两个宏可以帮助编译器优化分支布局，使常见执行路径更加高效。

需要注意：

  • likely() 和 unlikely() 不会改变程序的逻辑；
  • 它们不是运行时的分支预测器；
  • 只有在能够合理判断分支概率时才应该使用。

如果错误地标记分支，反而可能损害性能。

5.3 内核没有用户态的内存保护#

这是内核开发和普通应用开发之间非常重要的区别。

用户态程序运行在受操作系统保护的环境中。

例如：

int *p = NULL;
*p = 10;

如果用户态程序访问非法地址，处理器会产生异常，内核接管异常处理，通常向进程发送 SIGSEGV，终止该进程。

但是，如果内核代码发生类似的非法内存访问，后果要严重得多。

内核代码运行在特权环境中，可以访问系统内核空间以及特定的硬件资源。内核发生非法访问可能导致 Oops，严重时甚至引起系统崩溃。

例如：

int *p = NULL;
*p = 10;

如果这段代码在内核上下文中执行，就可能导致内核 Oops。

另一个重要区别是：内核内存通常不能像普通用户进程的匿名内存那样被随意换出。

因此，内核开发需要特别关注：

  • 指针是否有效；
  • 内存是否已经释放；
  • 数组是否越界；
  • 对象生命周期是否正确；
  • 并发访问是否安全；
  • 内存分配是否符合当前执行上下文的约束。

内核中的内存错误不仅仅影响当前函数，还可能影响整个系统。

5.4 不方便使用浮点运算#

普通用户态程序可以自由使用浮点数：

float a = 1.5f;
double b = 2.5;

double result = a * b;

但内核不能像用户态程序一样随意使用浮点指令。

原因在于浮点运算依赖处理器的浮点寄存器和相关处理器状态。用户态进程使用浮点运算时，操作系统需要保证上下文切换过程中浮点状态能够正确保存和恢复。

内核如果也使用浮点运算，就必须额外处理这些状态，避免破坏当前进程的浮点上下文。

因此，内核通常避免浮点运算。

如果确实存在特殊需求，需要使用架构提供的专门机制管理浮点状态，而不能直接在普通内核代码中使用浮点指令。

实践原则：内核代码尽可能使用整数运算。

5.5 小而固定的内核栈#

普通用户态线程通常拥有较大的栈空间，并且栈可以根据运行环境进行扩展。

内核栈则不同：它通常较小，而且大小固定。

书中以当时的 x86 系统为例，介绍了 4KB 或 8KB 等内核栈配置；历史上也存在每个进程使用两个页面作为内核栈的实现。

具体大小取决于处理器架构和内核配置，不能将书中的数值直接套用到现代所有 Linux 系统。

内核栈较小意味着：

  • 不应该在栈上分配大型数组；
  • 不应该在栈上放置过大的结构体；
  • 递归调用需要格外谨慎；
  • 函数调用链不能无限增长。

例如，不推荐：

void process_data(void)
{
    char buffer[1024 * 1024];

    /* ... */
}

这会尝试在内核栈上分配一个 1MB 的数组，远远超出正常内核栈能够承受的范围。

如果需要较大的内存空间，应该根据实际场景选择适当的内核内存分配接口。

5.6 同步与并发#

这是内核开发中最重要的基础问题之一。

普通程序可能通过多个线程访问共享数据，而 Linux 内核的并发来源更加复杂。

书中主要强调了四种并发来源。

1. 抢占式多任务

Linux 是抢占式多任务操作系统。

一个任务正在执行内核代码时，可能被调度器抢占，随后另一个任务开始执行。

如果两个任务访问相同的共享资源，就可能产生竞态条件。

2. 对称多处理器（SMP）

Linux 支持多个处理器核心同时执行内核代码。

例如：

CPU 0                  CPU 1
  |                      |
  v                      v
访问共享变量            访问共享变量
  |                      |
  +----------+-----------+
             |
             v
         共享数据

如果没有适当的同步机制，两个 CPU 可能同时修改同一个变量，导致数据不一致。

3. 异步中断

硬件中断可以在几乎任意时刻到来。

例如：

正常内核代码执行
       |
       v
访问共享数据
       |
       +------ 硬件中断到来
       |              |
       |              v
       |          中断处理程序
       |              |
       |          访问共享数据
       |              |
       +--------------+
       |
       v
继续执行

如果中断处理程序访问了当前代码正在修改的数据，就可能出现竞态。

4. 内核抢占

即使代码没有显式调用调度函数，也可能因为内核抢占机制而暂时停止执行。

如果共享数据没有得到保护，另一个执行路径就可能在中间修改它。

常见同步机制#

本章简单提到了两类重要同步机制：

机制 基本思想 典型特点
Spinlock 获取不到锁时持续自旋等待 适合短临界区，持锁期间不能睡眠
Semaphore 获取不到资源时可以睡眠等待 适合允许睡眠的场景

后续第九章和第十章会详细介绍内核同步问题以及各种同步原语。

这里需要先建立一个认识：

内核中的并发并不只是多个线程同时执行，还包括进程上下文、中断上下文、抢占和多处理器之间的交互。

因此，设计共享数据结构时，必须提前考虑所有可能访问它的执行路径。

5.7 可移植性#

Linux 是一个支持多种处理器架构的操作系统。

内核代码不能默认运行环境只有 x86，也不能假设不同处理器拥有完全一致的字长、字节序、页大小和内存访问规则。

书中强调了几个重要原则：

  • 不要依赖特定的字节序；
  • 保证代码能够正确处理 32 位和 64 位环境；
  • 不要假设机器字长固定；
  • 不要假设页面大小固定；
  • 将架构相关代码与通用代码分离。

例如，架构相关的实现通常放在：

arch/x86/
arch/arm64/
arch/riscv/

而通用功能尽量放在：

kernel/
mm/
fs/
net/

这种组织方式让 Linux 能够在不同硬件平台上复用大量核心代码。

核心思想：架构相关的差异应该被明确封装，而不是散落在通用代码中。

6. 本章知识总结#

本章可以归纳为两个部分：内核开发环境，以及内核代码的特殊约束。

6.1 内核开发流程#

获取 Linux 内核源码
        |
        v

        |
        v
编译内核（make）
        |
        v
安装内核模块

安装内核镜像

6.2 内核与用户态程序的区别#

对比项 用户态程序 Linux 内核
C 运行时 通常使用 libc 不依赖 libc
头文件 使用标准 C 头文件等 使用内核自己的头文件
打印 printf() printk()
内存分配 malloc() / free() kmalloc() / kfree() 等
语言特性 标准 C / C++ 等 C 与 GNU C 扩展
内存保护 受内核保护 运行在特权环境中
浮点运算 通常可以直接使用 通常避免使用
栈 通常较大，可增长 较小且固定
并发 线程并发为主 线程、抢占、中断、SMP 等
可移植性 由应用需求决定 必须考虑多架构支持

6.3 必须记住的关键点#

  1. Linux 内核源码可以通过官方 Git 仓库或源码压缩包获取，长期研究推荐使用 Git。
  2. Patch 是内核社区交流和提交代码的重要形式。
  3. arch/、kernel/、mm/、fs/、drivers/ 是阅读内核源码时最常接触的目录。
  4. .config 决定内核的功能配置，make menuconfig 是常用的配置工具。
  5. make -j$(nproc) 可以利用多核 CPU 加速编译。
  6. 内核没有 libc，必须使用内核自身提供的函数和头文件。
  7. Linux 内核使用 GNU C 扩展，包括内联汇编和 likely() / unlikely()。
  8. 内核栈空间有限，不能随意在栈上分配大型对象。
  9. 中断、抢占和 SMP 使内核面临复杂的并发问题。
  10. 内核代码必须考虑不同处理器架构之间的差异。

7. 动手实践：从源码到启动一个内核#

本章最值得做的事情，是亲自完成一次内核编译。

对于初学者，我建议先在虚拟机或 QEMU 中完成实验，不要直接替换日常使用机器的内核。

下面以现代 Linux x86-64 环境为例。

7.1 安装构建依赖#

以 Ubuntu 为例：

sudo apt update

sudo apt install -y \
    build-essential \
    bc \
    bison \
    flex \
    libssl-dev \
    libelf-dev \
    libncurses-dev \
    dwarves \
    git

不同内核版本和配置可能需要额外依赖。

7.2 获取源码#

mkdir -p ~/kernel
cd ~/kernel

git clone https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux

实际研究时，建议选择一个明确的稳定版本或实验版本，并记录对应的 Git commit，避免源码不断更新导致实验结果不一致。

7.3 配置内核#

make defconfig
make menuconfig

如果希望使用当前系统的配置，也可以尝试：

cp /boot/config-$(uname -r) .config
make oldconfig

注意，当前发行版内核的配置可能包含发行版特有选项，跨版本迁移时需要处理新增或变化的配置。

7.4 编译#

make -j$(nproc)

7.5 编译并安装模块#

sudo make modules_install

随后可以根据发行版的安装方式配置内核镜像、initramfs 和 GRUB。Ubuntu 等发行版通常提供相应的内核安装工具，也可以通过 make install 触发系统安装流程，但具体行为取决于环境。

7.6 在 QEMU 中实验#

如果只是学习内核启动、异常处理和内核调试，我更推荐使用 QEMU。

QEMU 可以让我们：

  • 启动自己编译的内核；
  • 使用 GDB 调试内核；
  • 观察启动过程；
  • 修改内核代码并重新编译；
  • 在实验出错时快速恢复。

例如，针对 x86-64 构建的内核，常见的镜像路径为：

arch/x86/boot/bzImage

可以结合 QEMU 的 -kernel 参数启动内核。具体还需要准备合适的根文件系统或 initramfs。

9. 我的理解#

第二章实际上是在建立一种正确的内核开发思维。

内核开发并不只是掌握 C 语言和阅读大量源码。更重要的是理解代码所处的执行环境，以及这个环境对程序施加的约束。

例如：

  • 用户态可以调用 malloc()，内核却必须考虑当前上下文是否允许睡眠；
  • 用户态发生非法内存访问通常只影响当前进程，内核发生类似问题却可能影响整个系统；
  • 用户态线程并发主要通过线程同步解决，内核还必须处理异步中断、抢占和多处理器访问；
  • 普通应用可以针对特定平台开发，而 Linux 内核需要考虑不同体系结构之间的差异。

这些约束并不是内核开发的额外负担，而是操作系统必须承担的职责。

本章最后传达的一个重要观点是：理解内核最有效的方式，是阅读源码并亲自修改、编译和运行它。

因此，后续学习不应该停留在概念层面。每学习一个内核子系统，都应该尽可能找到对应的源码入口，沿着调用链追踪实现，并通过实验验证自己的理解。
