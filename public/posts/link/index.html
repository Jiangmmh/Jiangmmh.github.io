1. 链接的历史：为什么需要链接器？#

1.1 从一个源文件到一个完整的程序#

当我们编写一个 C 程序时，通常会经历以下过程：

源代码
  │
  ▼
预处理（Preprocessing）
  │
  ▼
编译（Compilation）
  │
  ▼
汇编（Assembly）
  │
  ▼
目标文件（Object File）
  │
  ▼
链接（Linking）
  │
  ▼
可执行文件（Executable）
  │
  ▼
装载与执行（Loading & Execution）

初学编程时，我们可能会认为，编译器只需要把源代码翻译成机器指令，再将这些指令交给处理器执行即可。但当软件规模扩大到数十万行、数百万行甚至更多时，问题就变得复杂起来。

假设我们有这样一个程序：

// main.c

#include <stdio.h>

int add(int a, int b);

int main(void)
{
    int result = add(10, 20);
    printf("%d\n", result);
    return 0;
}

函数 add() 的实现位于另一个文件：

// add.c

int add(int a, int b)
{
    return a + b;
}

我们可以分别编译这两个源文件：

gcc -c main.c -o main.o
gcc -c add.c -o add.o

这时会得到两个目标文件：

main.o
add.o

但是，main.o 中调用了 add()，它自身并不包含 add() 的机器指令。编译器如何生成调用指令？这条调用指令最终应该跳转到哪个地址？

同样，如果一个文件引用了另一个文件中定义的全局变量，编译器又如何知道这个变量最终位于哪里？

这便引出了两个核心问题：

  1. 符号解析（Symbol Resolution）：一个符号究竟由哪个目标文件或库定义？
  2. 重定位（Relocation）：找到符号定义以后，如何修正机器指令或数据中的地址，使程序能够正确执行？

链接器（Linker）的核心职责，就是协调多个目标文件和库，将它们组织成可以执行的程序，或者组织成可以进一步链接的库。

1.2 为什么不直接生成最终地址？#

假设编译器编译 main.c 时，能够直接把 add() 的调用地址写入机器指令，那么编译器必须提前知道 add() 最终在内存中的位置。

但是，这个地址在编译 main.c 时往往并不存在。

  • add() 可能在另一个尚未编译的源文件中。
  • 即使 add() 已经编译成目标文件，它在最终程序中的位置也尚未确定。链接器可能将不同目标文件中的代码按照一定的布局规则放置到输出文件中。

例如：

main.o                    add.o
┌─────────────────┐      ┌─────────────────┐
│ main()          │      │ add()           │
│                 │      │                 │
│ call add(?)     │      │ add 的机器指令   │ 
└─────────────────┘      └─────────────────┘
          │                       │
          └──────────┬────────────┘
                     ▼
                  链接器
                     │
                     ▼
             ┌──────────────────┐
             │ 最终程序          │
             │                  │
             │ main()           │
             │ add()            │
             └──────────────────┘

因此，编译器可以先生成尚有部分符号引用和地址需要处理的目标文件，再由链接器完成跨文件的符号解析和地址修正。

这也使得 独立编译（Separate Compilation） 成为可能：每个源文件可以独立编译，修改某个源文件时通常只需要重新编译受影响的部分，而不必重新编译整个项目。

需要注意，独立编译不意味着不同模块之间完全没有约束。函数声明、数据类型、调用约定、ABI 等接口约定仍然必须兼容。

1.3 从早期装入程序到现代动态链接#

链接和装载并不是现代操作系统才出现的概念。随着程序逐渐由多个独立模块组成，早期系统就需要能够将分散保存的程序片段组合起来，并处理它们在内存中的位置。

链接器的发展大致可以理解为以下几个阶段。

第一阶段：装入与重定位#

早期计算机的内存资源十分有限，程序往往需要由多个模块组成。装入程序（Loader）除了把代码放入内存，还需要解决各模块之间的地址引用问题。

当一个模块被放置到新的内存位置时，部分地址也必须随之调整。这类操作就是重定位的早期形式。

到了 20 世纪 60 年代前后，链接编辑器（Linkage Editor）逐步发展起来，能够将多个目标模块组合成一个程序，解决跨模块引用，并生成可执行程序。

相关历史可以参阅 John R. Levine 的《Linkers and Loaders》。

第二阶段：静态链接成为一种简单可靠的组织方式#

随着编译器和程序库的发展，程序员希望将公共功能编译成可复用的模块。

例如，数学函数、字符串处理函数、输入输出函数，都可以独立编译成目标文件，再在构建程序时与应用代码组合起来。

静态链接很好地满足了这一需求。

应用目标文件 ──┐
               ├── 链接器 ──> 可执行文件
库目标文件 ────┘

链接完成后，所需的库代码已经集成进可执行文件。运行程序时，不需要再寻找这些已经静态链接进去的库文件。

这种方式简单、可靠，但也带来了代码重复、程序体积较大以及库更新后需要重新链接程序等问题。

第三阶段：动态链接与共享库#

如果系统中有几十个应用程序都使用相同的库，每个应用程序都将同一份库代码包含在自己的可执行文件中，就可能造成磁盘空间和内存使用上的浪费。

更进一步，假如系统库修复了一个安全漏洞，静态链接的应用程序通常还需要重新构建或重新发布，才能包含修复后的代码。

动态链接则提供了另一种思路：

  • 构建程序时，记录程序对外部共享库的依赖。
  • 程序启动时，由动态链接器装载所需的共享库。
  • 根据实际装载地址和符号定义完成必要的重定位。
  • 让多个程序在满足映射条件时共享同一份共享库的文件支持代码页。

20 世纪 60 年代的 Multics 已经探索了动态链接。此后，不同操作系统在静态链接、动态链接和共享库机制上采取了不同设计。今天，Linux ELF、Windows PE/DLL 和 macOS Mach-O 都支持动态链接，但其文件格式、ABI 和装载机制并不相同。

历史资料可参阅 Multics 执行环境中的动态链接机制。

1.4 链接究竟解决了什么问题？#

为了理解后续的静态链接和动态链接，我们需要先明确几个基本概念。

目标文件（Object File） 是编译器或汇编器输出的文件。它通常包含机器指令、数据、符号表和重定位信息。

在 Linux ELF 环境中，常见的文件类型包括：

文件类型 常见后缀 主要用途
可重定位目标文件 .o 作为链接器的输入
静态库 .a 归档多个目标文件，供链接器选择使用
共享库 .so 提供运行时可装载的共享代码与数据
可执行文件 无固定后缀要求 作为程序运行的入口映像

符号表#

符号（Symbol）可以是函数名、全局变量名等。目标文件的符号表记录了这些名称及其相关属性。

可以使用 nm 查看目标文件中的符号：

nm main.o

输出可能类似：

                 U add
0000000000000000 T main
                 U printf

这里：

  • U 表示未定义符号，即当前目标文件引用了它，但没有在本文件中定义。
  • T 通常表示符号定义在代码段中。
  • main 是当前目标文件定义的函数。
  • add 和 printf 需要从其他目标文件或库中找到定义，或者在动态链接场景中由运行时链接机制处理。

重定位信息#

在链接之前，目标文件中的某些机器指令或数据还不能确定最终地址。

例如，main.o 中调用 add() 的位置可能需要由链接器修正。编译器会生成相应的重定位记录，告诉链接器：

  • 需要修正的位置在哪里；
  • 该位置引用了哪个符号；
  • 应当采用哪种架构相关的重定位类型；
  • 是否包含额外的加数等信息。

对于一种常见的 PC 相对重定位，计算形式可以抽象为：

\[ V = S + A - P \]

其中：

  • \(S\)：被引用符号的地址；
  • \(A\)：重定位记录中的加数；
  • \(P\)：需要写入或修正的位置的地址；
  • \(V\)：最终需要写入的位置相关值。

对于绝对地址形式，常见的计算形式则是：

\[ V = S + A \]

具体公式取决于目标架构和重定位类型。

至此，我们已经有了理解链接器的基础：符号表回答“引用的是谁”，重定位信息回答“应该如何修正引用位置”。

2. 静态链接#

2.1 什么是静态链接？#

静态链接（Static Linking）是指在构建阶段，由链接器将应用程序需要的目标代码与其他目标文件组合，生成最终的可执行文件或共享库。

在 Linux 中，静态库通常以 .a 为后缀，例如：

libmathops.a
libpthread.a        # 这里只作为名称示例，不代表现代系统上的实际链接方式

静态库本质上是一个归档文件，内部通常包含多个可重定位目标文件以及用于加速符号查找的索引。

它并不是一个已经完整布局、可以直接运行的可执行文件。

假设我们有：

main.o
libmathops.a

其中 main.o 引用了 add()，而 libmathops.a 中的某个归档成员定义了 add()。

链接器可以从静态库中提取需要的目标文件成员，将相关代码和数据整合进可执行文件。

                 构建阶段
┌──────────────┐
│ main.o       │
└──────┬───────┘
       │ 引用 add()
       ▼
┌──────────────────┐
│ 链接器           │
│                  │
│ 查询符号         │
│ 提取所需归档成员 │
│ 处理重定位       │
└──────┬───────────┘
       │
       ▼
┌──────────────────┐
│ app_static       │
│                  │
│ main()           │
│ add()            │
└──────────────────┘

这里需要区分两个概念：

  1. 使用静态库链接某个模块：该模块所需的目标代码被集成到最终输出文件中。
  2. 整个程序采用完全静态链接：程序的所有相关依赖也都不依赖运行时动态库。

这两者并不等价。即使我们把自己编写的 libmathops.a 静态链接进程序，最终程序仍然可能动态依赖 GNU C Library 等系统共享库。

2.2 如何制作静态链接库？#

我们以一个简单的数学库为例，目录结构如下：

link-demo/
├── include/
│   └── mathops.h
├── src/
│   ├── add.c
│   └── main.c
└── build/

首先，编写头文件：

// include/mathops.h

#ifndef MATHOPS_H
#define MATHOPS_H

int add(int a, int b);

#endif

头文件声明了 add() 函数，使调用者可以在不查看实现细节的情况下使用它。

接下来编写函数实现：

// src/add.c

#include "mathops.h"

int add(int a, int b)
{
    return a + b;
}

我们先不生成库，而是将源文件编译为目标文件。

mkdir -p build

gcc -Wall -Wextra -O2 \
    -Iinclude \
    -c src/add.c \
    -o build/add.o

其中：

  • -Wall -Wextra 用于启用一组常见警告；
  • -O2 开启优化；
  • -Iinclude 指定头文件搜索目录；
  • -c 表示只编译和汇编，不执行最终链接；
  • -o 指定输出文件。

此时的 build/add.o 仍然是可重定位目标文件。

接下来使用 ar 将目标文件打包为静态库。

ar rcs build/libmathops.a build/add.o

参数含义如下：

  • r：将成员加入归档；如果归档中已经存在同名成员，则替换它。
  • c：在需要时创建归档文件。
  • s：更新符号索引，方便链接器快速查找归档中定义的符号。

现在，我们已经生成了静态库：

build/libmathops.a

可以通过以下命令检查：

ar t build/libmathops.a
nm -s build/libmathops.a

ar t 用于列出归档中的成员，而 nm -s 可以查看归档的符号索引。

需要注意，ar 并不负责把所有成员完成最终链接。它的主要任务是组织目标文件并维护索引，真正的符号解析和最终重定位仍然由链接器执行。

2.3 如何使用静态链接库？#

接下来编写应用程序：

// src/main.c

#include <stdio.h>
#include "mathops.h"

int main(void)
{
    int result = add(10, 20);
    printf("result = %d\n", result);
    return 0;
}

将其编译为目标文件：

gcc -Wall -Wextra -O2 \
    -Iinclude \
    -c src/main.c \
    -o build/main.o

然后将应用程序目标文件与静态库链接：

gcc build/main.o \
    -Lbuild \
    -lmathops \
    -o build/app_static

这里需要重点理解三个参数：

  • -Lbuild：告诉链接器从 build 目录查找库文件。
  • -lmathops：要求查找名为 mathops 的库。在 GNU/Linux 上，通常会考虑 libmathops.so 和 libmathops.a 等候选文件，具体选择取决于工具链和选项。
  • -o build/app_static：生成最终可执行文件。

由于这里构建目录中只有 libmathops.a，链接器会从它里面提取需要的目标文件。

运行程序：

./build/app_static

预期输出：

result = 30

至此，我们已经完成静态库的创建和使用。

2.4 静态链接的内部原理#

理解上述流程后，我们再深入一步：链接器究竟如何处理静态库？

第一步：识别未定义符号#

main.o 调用了 add()，但自身并未定义这个函数。

nm build/main.o

输出中会出现类似：

U add

这表示当前目标文件需要外部提供 add 的定义。

第二步：查找库中的符号定义#

链接器处理静态库时，会根据当前尚未解决的符号，判断归档中哪些目标文件成员可能提供所需定义。

例如：

libmathops.a
├── add.o       定义 add()
├── sub.o       定义 sub()
├── mul.o       定义 mul()
└── div.o       定义 div()

如果应用程序只使用 add()，链接器通常只需要提取包含 add() 定义的 add.o，而不必把整个归档中的全部成员都加入最终程序。

这也是为什么静态库并不一定会让程序包含整个库的所有代码。

不过，提取单位通常是归档成员，而不是任意一条函数定义。如果多个函数位于同一个目标文件中，其中一个被引用时，该成员中的其他代码和数据也可能随之进入输出文件，之后还可能通过节级别的垃圾回收等优化删除部分未使用内容。

链接器也有强制提取归档成员的选项，例如 GNU ld 的 --whole-archive。

第三步：完成符号解析#

链接器将找到的目标文件成员纳入链接过程，并将对应的符号定义与引用匹配起来。

main.o
  │
  └── 未定义符号：add
                │
                ▼
        libmathops.a
                │
                ▼
           add.o 被提取
                │
                ▼
           add() 得到定义

第四步：执行重定位#

链接器需要确定最终输出文件中的代码和数据布局，并处理相应的重定位记录。

例如，假设链接器将 main() 和 add() 放置在输出文件的不同位置，那么原先指向未确定地址的调用指令就需要被修正，使其在最终布局下能够正确地调用 add()。

这一步的结果是：对于已经由静态链接器解决的引用，输出文件中不再需要在运行时寻找这份静态库，才能确定它们的目标。

但输出文件是否还包含其他动态依赖，是另一个问题。

2.5 静态库链接的几个细节#

链接顺序很重要#

GNU ld 通常按照命令行出现的顺序处理对象文件和库。对于常见的静态库链接，库通常应当放在引用它的对象文件之后。

例如：

gcc build/main.o -Lbuild -lmathops -o build/app_static

一般来说，这种顺序是正确的。

而下面这种顺序可能导致链接失败：

gcc -Lbuild -lmathops build/main.o -o build/app_static

原因在于，链接器扫描静态库时，如果当时还没有发现需要由这个库解决的未定义符号，可能不会提取相关成员。之后才出现的符号引用不一定会使它重新扫描之前处理过的库。

对于多个静态库之间存在循环依赖的情况，GNU ld 还提供了 --start-group 和 --end-group 等选项，可以要求链接器重复扫描指定的库组，直到不再发现新的未解决引用。

静态库必须与目标平台兼容#

静态库中的机器指令不是与平台无关的抽象代码。

构建项目时，目标架构、ABI、编译选项以及相关依赖都可能影响静态库是否可以正常链接和运行。

例如，为 ARM64 编译的静态库通常不能直接作为 x86-64 程序的目标代码使用。

静态库更新后，应用程序通常需要重新链接#

假设某个静态库存在 bug，我们更新了库的实现并重新生成 .a 文件。

已经生成的可执行文件不会自动替换其中的旧机器指令。要让应用程序使用修复后的代码，一般需要重新链接，通常也会通过构建系统重新编译或构建受影响的目标。

2.6 静态链接的优缺点#

优点：

  1. 部署时不必为静态链接进去的库单独准备运行时共享库文件。
  2. 对于已经包含在输出文件中的代码，运行时不需要为该库再执行相应的符号查找和动态重定位。
  3. 更容易将特定版本的库代码固定在构建产物中，减少运行环境中某些依赖版本变化带来的不确定性。
  4. 在精简运行环境、受控部署或部分嵌入式场景中，静态链接可能更加方便。

缺点：

  1. 如果许多不同的应用程序各自静态链接相同的库代码，磁盘中可能产生重复副本，应用程序文件也可能变大。
  2. 库修复或更新后，通常需要重新链接并重新发布依赖它的应用程序。
  3. 如果静态库依赖其他库，这些依赖仍需要被适当处理；静态链接并不自动解决全部依赖问题。
  4. 完全静态链接可能受到系统库、运行时组件、工具链配置及平台约束的影响。

3. 动态链接#

3.1 什么是动态链接？#

动态链接（Dynamic Linking）将一部分符号解析与重定位工作留到程序装载阶段或运行过程中完成。

在 Linux ELF 环境中，应用程序可以在构建时引用共享库，但并不将共享库中的全部代码复制到应用程序文件中。

例如：

app_dynamic
    │
    ├── 依赖 libmathops.so.1
    │
    ├── 依赖 libc.so.6
    │
    └── 可能依赖其他共享库

程序构建完成后，动态依赖通常会记录在 ELF 文件的动态段中。

运行时，Linux 动态链接器会根据依赖信息装载所需共享库，并执行必要的动态重定位与符号解析。

在典型的 Linux ELF 系统中，动态链接器常见的名称是 ld-linux-x86-64.so.2，实际路径取决于系统和目标架构。

理解动态链接，需要先区分三个角色：

组件 主要职责
编译器和汇编器 将源代码转换为目标文件
静态链接器 生成输出文件，处理可在构建阶段解决的符号与重定位，并记录动态依赖
动态链接器/装载器 装载共享对象，处理运行时符号解析和重定位，并准备程序执行

因此，动态链接不等于取消构建阶段的链接，而是把部分链接工作推迟到运行时。

3.2 动态链接的详细过程：从代码到 main()#

本节是理解动态链接最重要的部分。

我们不仅讨论怎样生成 .so 文件，还要解释 ELF 文件中保存了什么信息，以及 Linux 如何利用这些信息完成动态装载。

3.2.1 第一步：编译器生成带有外部引用的目标文件#

仍然以 main.c 中调用 add() 为例。

int main(void)
{
    return add(10, 20);
}

编译器不会总是直接生成一个已经知道最终运行地址的 add() 调用。

它通常会生成机器指令和与之相关的重定位信息。具体形式与目标架构、代码模型及编译选项有关。

可以通过下面的命令查看：

gcc -O2 -Iinclude -c src/main.c -o build/main.o

nm build/main.o
readelf -r build/main.o
objdump -dr build/main.o

其中：

  • nm 查看符号；
  • readelf -r 查看重定位记录；
  • objdump -dr 同时展示反汇编及关联的重定位信息。

在 x86-64 等架构上，目标文件中的外部函数调用可能对应某种 PC 相对重定位。链接器将根据最终输出形式决定如何处理该调用。

此时最重要的一点是：目标文件已经包含了机器指令，但它仍可能包含尚未确定的外部符号引用。

3.2.2 第二步：静态链接器生成动态可执行文件#

构建动态链接程序时，静态链接器仍然会执行大量工作。

它需要：

  1. 处理输入目标文件与链接选项；
  2. 解析构建阶段可以确定的符号；
  3. 安排输出文件中的节和程序段；
  4. 处理构建阶段可以完成的重定位；
  5. 保留动态链接所需的符号、字符串和重定位信息；
  6. 在动态段中记录所需的共享库依赖。

例如：

gcc build/main.o \
    -Lbuild \
    -lmathops \
    -Wl,-rpath,'$ORIGIN' \
    -o build/app_dynamic

当链接器使用共享库来满足 add() 的引用时，它通常不需要把 add() 的实现复制到可执行文件中，而是可以将依赖记录为一个动态依赖项。

在 ELF 中，DT_NEEDED 表示所依赖共享对象的名称。这个名称通常对应共享库的 SONAME，而不一定是构建时使用的完整文件路径。

可以这样检查：

readelf -d build/app_dynamic

输出中可能包含类似内容：

(NEEDED)    Shared library: [libmathops.so.1]
(RUNPATH)   Library runpath: [$ORIGIN]

实际输出格式和内容可能有所差异。

DT_NEEDED 告诉动态链接器程序需要哪些共享对象；DT_RUNPATH 则提供一组运行时共享库搜索目录。

这说明，动态链接程序在构建完成时就已经保存了依赖关系，只是相关共享库的最终装载地址通常要到运行时才能确定。

3.2.3 第三步：操作系统找到动态链接器#

执行动态链接程序时，应用程序并不是简单地从 ELF 文件中找到 main()，然后立即跳转过去。

在 Linux 上，内核首先处理 ELF 可执行文件的装载。

如果文件指定了动态解释器，内核会根据 ELF 中的 PT_INTERP 程序头信息找到相应的动态链接器。

可以查看：

readelf -l build/app_dynamic

输出中可能出现：

INTERP
[Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]

这里的具体路径因发行版、架构和工具链而异。

PT_INTERP 告诉内核应使用哪个程序解释器来准备动态链接程序。

接下来，内核与动态链接器协同完成可执行文件和相关共享对象的装载工作。对于典型的动态链接 ELF 程序，动态链接器会处理其依赖和运行时重定位，再将控制权交给程序的启动代码。

3.2.4 第四步：动态链接器装载共享库#

动态链接器需要根据可执行文件中的依赖信息找到共享库。

在 ELF 中，DT_NEEDED 给出依赖名称，但这个名称不一定包含目录。

例如：

libmathops.so.1

动态链接器需要确定它实际对应哪个文件。

对于 Linux glibc 动态链接器，当依赖名称不含斜杠时，常见搜索顺序包括：

  1. 若存在适用的 DT_RPATH 且不存在 DT_RUNPATH，先搜索其指定目录；
  2. 搜索 LD_LIBRARY_PATH，但安全执行模式可能忽略它；
  3. 搜索 DT_RUNPATH 指定的目录；
  4. 搜索 /etc/ld.so.cache 中的候选库；
  5. 搜索系统默认库目录。

如果依赖字符串本身包含斜杠，则按照它指定的路径处理。实际结果还会受到安全执行模式、硬件能力目录和具体动态链接器规则等因素影响。

可以参阅 Linux 手册中的 ld.so(8)。

RUNPATH 和 RPATH 并不完全一样。 在 glibc 的 ELF 搜索规则中，RUNPATH 通常只用于查找当前对象的直接依赖，不会自动为依赖的子依赖提供同样的传递搜索路径；传统 RPATH 的行为有所不同。

找到共享库后，动态链接器会依据 ELF 程序头中的 PT_LOAD 等信息，将相应内容映射到进程地址空间。

可以把这一阶段简化为：

app_dynamic
     │
     │ DT_NEEDED
     ▼
动态链接器
     │
     ├── 查找 libmathops.so.1
     ├── 查找 libc.so.6
     ├── 递归处理其他依赖
     │
     ▼
将可执行文件与共享对象映射到地址空间

需要注意，映射共享库并不意味着所有机器代码都必须立即从磁盘完整读入物理内存。操作系统可以通过按需调页等机制，在实际访问页面时再将数据装入内存。

3.2.5 第五步：ASLR 为什么让重定位更加重要？#

现代操作系统通常会使用地址空间布局随机化（ASLR），使程序或共享库在不同运行实例中可能被映射到不同的虚拟地址。

假设某个共享库的代码在链接时以某个基准地址组织，但实际运行时被装载到了另一个地址。

如果机器指令和数据全部依赖固定绝对地址，那么直接使用原始地址就可能出错。

这就是重定位在动态装载阶段的重要作用。

对于一个以位置无关方式构建的 ELF 共享对象，可以将实际装载地址表示为：

\[ \text{实际地址} = \text{装载基址} + \text{对象内偏移} \]

动态链接器需要根据实际装载位置和重定位类型处理相关地址引用。

ELF 动态重定位可能涉及多种架构相关的重定位类型。例如，在 x86-64 ELF 中，可能看到：

  • R_X86_64_RELATIVE
  • R_X86_64_GLOB_DAT
  • R_X86_64_JUMP_SLOT

这些类型具有不同的用途，不能简单地认为所有动态重定位都是“把函数地址填进去”。

例如，某些相对重定位可以仅根据对象装载基址和重定位加数计算；某些重定位需要查询符号最终解析到的地址；与 PLT 调用有关的重定位则可能采用延迟绑定方式处理。

需要注意，具体重定位类型及其计算规则由目标架构的 ABI 定义。

3.2.6 第六步：动态符号解析#

现在，动态链接器已经装载了可执行文件与所需共享对象，但仍需要将特定符号引用绑定到实际定义。

例如，应用程序引用了：

int add(int a, int b);

而 add() 的定义在 libmathops.so.1 中。

动态链接器需要依据动态符号表、字符串表、动态依赖关系和符号查找规则确定最终定义。

ELF 动态链接涉及以下信息：

ELF 信息 作用
.dynsym 对应的动态符号表 提供参与动态链接的符号信息
.dynstr 对应的动态字符串表 保存符号名等字符串
.dynamic 保存动态链接所需的标签与相关信息
.rela.dyn 等重定位表 保存动态重定位记录，具体名称与架构及文件形式有关
.rela.plt 等 PLT 重定位信息 保存与过程链接表调用有关的重定位信息，具体形式取决于目标平台

这里需要区分 ELF 的节（Section）和程序段（Segment）：节主要为链接、符号组织等工作服务；程序段则定义了装载器需要关注的映射内容。

在运行时，动态链接器通常依据程序头、动态段和相应元数据完成工作，并不要求目标文件的所有链接期节表都必须保留。

另外，符号解析并不总是简单地“从指定共享库查找同名函数”。在 ELF 系统中，符号可见性、依赖顺序、符号版本、符号插入（interposition）以及其他链接规则都可能影响最终绑定结果。

因此，某个共享库里存在同名函数，并不意味着运行时一定会绑定到你预期的那份实现。

3.2.7 第七步：GOT 与 PLT 如何完成函数调用？#

动态链接最经典的实现机制之一，是通过全局偏移表（GOT，Global Offset Table）和过程链接表（PLT，Procedure Linkage Table）完成函数调用。

这部分也是理解 Linux 动态链接时最值得掌握的内容之一。

GOT：保存需要在运行时确定的地址#

动态链接器在装载过程中，可能无法在构建阶段为某个外部符号确定最终运行地址。

GOT 提供了一个间接寻址机制，使机器代码可以通过表中的地址引用外部对象或函数。

可以抽象地理解为：

调用代码
   │
   ▼
GOT 中的某个表项
   │
   ▼
实际目标地址

在实际 ELF 中，GOT 表项的用途和访问方式与架构、重定位模型及编译选项有关。有些表项需要动态链接器在启动时修正；有些表项则与延迟绑定配合工作。

PLT：为外部函数调用提供跳转入口#

对于传统的 x86-64 ELF PLT 实现，调用外部动态函数时，目标文件或最终可执行文件中的调用指令可能先跳转到 PLT 对应的入口。

一种典型形式可以抽象为：

call add@PLT

注意，这只是用于说明机制的汇编表示，具体指令与符号表现形式取决于编译器和反汇编工具。

第一次调用时，传统 PLT 机制可能通过尚未完成绑定的 GOT 表项转入动态链接器的解析路径。动态链接器根据对应的重定位记录找到目标函数，并将解析结果写入相关 GOT 表项。

此后再次调用同一函数时，控制流就可以通过已经修正的 GOT 表项直接跳转到目标函数，而不必每次都重新执行完整的符号解析过程。

简化过程如下：

第一次调用
    │
    ▼
PLT 入口
    │
    ▼
尚未解析的 GOT 表项
    │
    ▼
动态链接器解析目标符号
    │
    ▼
更新 GOT 表项
    │
    ▼
跳转到目标函数


后续调用
    │
    ▼
PLT 入口
    │
    ▼
已经解析的 GOT 表项
    │
    ▼
直接跳转到目标函数

这称为**延迟绑定（Lazy Binding）**的一种典型实现形式。

它允许某些函数的实际绑定工作推迟到首次调用时完成，而不是启动时解析所有 PLT 函数引用。

但是，并非所有动态重定位都支持这种延迟行为，也并非所有现代构建都使用传统 PLT 机制。编译器和链接器可以通过不同选项改变调用方式，程序也可以要求尽早完成绑定。

例如，在 GNU/Linux 环境中：

LD_BIND_NOW=1 ./build/app_dynamic

这会要求动态链接器在程序启动时完成通常可以延迟的符号绑定工作，而不是等到第一次调用相应函数时才进行解析。

提前绑定可能更早发现符号解析问题，也会改变启动时间和后续调用的开销分布。

进一步阅读时，还可以关注 -z now、-z relro 和 -fno-plt 等选项，以及它们对绑定时机、GOT 保护和函数调用方式的影响。

3.2.8 第八步：从动态链接器进入程序#

完成必要的装载和重定位之后，动态链接器还需要处理程序启动过程中的初始化工作。

其中包括相关运行时组件的初始化，以及共享对象和程序的初始化函数。

对于使用标准 C 运行时的程序，执行入口通常并不是我们在源码中写的 main()，而是运行时启动代码，例如 _start。

启动代码完成相应的运行时准备后，才会调用 main()。

简化来看：

execve()
   │
   ▼
内核装载 ELF 与指定的动态解释器
   │
   ▼
动态链接器装载依赖并完成必要的重定位
   │
   ▼
运行时初始化与启动代码
   │
   ▼
main()

实际执行流程包含架构相关的入口约定、启动代码和初始化顺序等细节，但从程序员的角度来看，最重要的是：

在动态链接程序进入 main() 之前，相关共享库通常已经被装载，必要的重定位已经完成，相应的运行时初始化工作也已执行。

3.3 如何制作动态链接库？#

理解动态链接的基本原理后，我们重新回到实践。

仍然使用之前的目录和文件：

link-demo/
├── include/
│   └── mathops.h
├── src/
│   ├── add.c
│   └── main.c
└── build/

第一步：以位置无关代码编译目标文件#

执行：

gcc -Wall -Wextra -O2 -fPIC \
    -Iinclude \
    -c src/add.c \
    -o build/add.pic.o

这里引入了重要选项：

-fPIC

PIC 是 Position-Independent Code，即位置无关代码。

共享库可能被映射到不同的虚拟地址。如果机器代码严重依赖固定绝对地址，那么每次装载时就可能需要对代码本身进行更多修正。

位置无关代码通过适当的寻址方式，尽量减少对固定装载地址的依赖。在 x86-64 等架构上，这可能利用指令相对寻址和 GOT 等机制完成访问。

需要注意，位置无关代码不意味着完全不存在动态重定位。动态链接器仍然可能需要修正 GOT 表项、数据地址或其他运行时引用。

第二步：生成共享库#

接下来执行：

gcc -shared \
    -Wl,-soname,libmathops.so.1 \
    -o build/libmathops.so.1.0.0 \
    build/add.pic.o

这里的关键选项是：

  • -shared：要求生成共享对象；
  • -Wl,：将后面的参数传递给链接器；
  • -soname,libmathops.so.1：设置共享库的 SONAME。

SONAME 是共享库用于标识其运行时兼容身份的重要信息。

在常见的 Linux 库发布方式中，会通过符号链接区分开发时使用的链接名称、运行时依赖名称和实际版本文件：

libmathops.so       -> libmathops.so.1
libmathops.so.1     -> libmathops.so.1.0.0
libmathops.so.1.0.0

其中：

  • libmathops.so 通常用于开发阶段的链接；
  • libmathops.so.1 表示 SONAME 对应的库名称；
  • libmathops.so.1.0.0 是实际的库文件。

创建符号链接：

ln -sf libmathops.so.1.0.0 build/libmathops.so.1
ln -sf libmathops.so.1 build/libmathops.so

现在，动态库已经构建完成。

可以使用以下命令进行检查：

file build/libmathops.so.1.0.0

readelf -h build/libmathops.so.1.0.0

readelf -d build/libmathops.so.1.0.0

nm -D build/libmathops.so.1.0.0

其中：

  • file 用于识别文件类型；
  • readelf -h 查看 ELF 文件头；
  • readelf -d 查看动态段；
  • nm -D 查看动态符号表中的符号。

与静态库不同，共享库是可被装载的 ELF 对象。它包含动态装载所需的结构和信息，可以供其他程序在运行时使用。

3.4 如何使用动态链接库？#

我们已经生成了：

build/libmathops.so.1.0.0

并创建了相应的链接名称。

接下来，使用它构建程序：

gcc build/main.o \
    -Lbuild \
    -lmathops \
    -Wl,-rpath,'$ORIGIN' \
    -o build/app_dynamic

这条命令与静态链接的形式十分相似。

区别在于，链接器现在可以选择 libmathops.so 来满足动态库依赖，而不是从 libmathops.a 中提取目标文件并将其代码集成进可执行文件。

这里有两个值得理解的细节。

第一，-lmathops 负责的是构建阶段的库查找。

在通常的 GNU/Linux 配置下，如果静态库与共享库都存在，链接器通常优先选择共享库；也可以使用相应选项控制选择行为。

因此，不能仅凭命令行中出现了 -lmathops，就判断最终产物一定采用静态链接或动态链接。

第二，-rpath 用于设置运行时库搜索路径信息。

这条命令中的：

-Wl,-rpath,'$ORIGIN'

将 $ORIGIN 作为运行时路径的一部分交给链接器记录。对于 glibc 动态链接器，$ORIGIN 表示包含当前可执行文件或共享对象的目录。

这里 app_dynamic 与共享库都位于 build 目录，因此这种配置适用于当前示例。实际项目应当根据可执行文件与共享库的部署目录安排搜索路径。

现在运行：

./build/app_dynamic

输出应当为：

result = 30

这说明，程序在运行时能够找到并使用我们的共享库。

如何验证它使用了动态库？#

首先检查动态依赖：

readelf -d build/app_dynamic | grep -E 'NEEDED|RUNPATH'

你应当能找到类似：

Shared library: [libmathops.so.1]
Library runpath: [$ORIGIN]

然后检查运行时依赖：

ldd build/app_dynamic

在本例的正常构建环境中，输出应当显示 libmathops.so.1 被解析到了 build 目录中的共享库，并列出程序的其他动态依赖。

ldd 展示的是依赖解析结果，而不是动态链接的全部内部流程；对于来源不可信的可执行文件，优先使用 readelf -d 或 objdump -p 检查其依赖信息更加稳妥。

还可以执行：

objdump -T build/libmathops.so.1.0.0
readelf -r build/app_dynamic
objdump -d build/app_dynamic

将动态符号表、重定位记录和反汇编结果结合起来观察，就能进一步分析函数引用在最终程序中是如何实现的。

3.5 不要把动态链接和动态加载混为一谈#

我们已经介绍了动态链接库的构建和常规使用方式，但还存在另一种常见需求：

程序在启动时并不知道自己需要哪些模块，要运行到某个阶段才决定加载哪个库。

例如：

  • 图像处理软件按需加载不同的图像格式插件；
  • 数据库根据配置加载不同的存储引擎；
  • 应用程序通过插件系统扩展功能；
  • 程序运行时才决定使用哪个第三方模块。

在 Linux 上，可以使用 dlopen() 和 dlsym() 等接口进行运行时动态加载和符号查找。

例如，先实现插件：

// plugin.c

int plugin_add(int a, int b)
{
    return a + b;
}

构建插件库：

gcc -fPIC -shared \
    -o libplugin.so \
    plugin.c

接下来，编写主程序：

// host.c

#include <dlfcn.h>
#include <stdio.h>

typedef int (*add_fn)(int, int);

int main(void)
{
    void *handle = dlopen("./libplugin.so", RTLD_NOW | RTLD_LOCAL);

    if (handle == NULL) {
        fprintf(stderr, "dlopen failed: %s\n", dlerror());
        return 1;
    }

    dlerror();

    add_fn add = (add_fn)dlsym(handle, "plugin_add");

    const char *error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "dlsym failed: %s\n", error);
        dlclose(handle);
        return 1;
    }

    printf("result = %d\n", add(10, 20));

    dlclose(handle);
    return 0;
}

编译并运行：

gcc host.c -o host -ldl

./host

预期输出：

result = 30

这段代码与之前的常规动态链接有明显区别。

在常规动态链接中，应用程序在构建时就已经记录了对共享库的依赖。运行时，动态链接器会根据这些依赖自动装载相应对象。

而在这里，主程序显式调用 dlopen()，要求装载指定的共享对象，再通过 dlsym() 获取函数地址。

几个关键参数的含义如下：

  • RTLD_NOW：要求在 dlopen() 返回前完成该次加载所需的未解决符号绑定，而不是使用默认的延迟绑定方式。
  • RTLD_LOCAL：默认情况下不将新加载对象的符号加入后续对象的全局符号查找范围。
  • dlclose()：减少对应对象的引用计数；当不再有相关引用时，动态链接器可能卸载该对象，但不能简单地认为每次调用都会立即从内存中移除它。

需要特别注意：卸载共享对象后，如果程序仍然保存并调用指向该对象代码的函数指针，或者继续访问已经失效的对象数据，就可能产生未定义行为或其他严重错误。因此，实际插件系统必须明确管理对象生命周期。

对于 dlsym()，还应通过 dlerror() 检查查找结果，因为返回空指针本身不能在所有情况下都被简单地解释成查找失败。

动态加载接口的详细行为，可以参考 Linux 手册的 dlopen(3) 与 dlsym(3)。

4. 如何选择静态链接和动态链接？#

理解两者的实现之后，选择就不应当只看可执行文件的大小，而应当综合考虑部署方式、运行环境、更新策略、安全性和性能。

4.1 两种方式的核心区别#

对比维度 静态链接 动态链接
链接发生的主要阶段 构建阶段 构建阶段加运行时
库代码如何进入程序 将需要的目标代码集成进输出文件 通常由运行时装载共享对象
运行时依赖 被静态链接进去的库不需要独立的共享库文件 需要找到并装载相应共享库
可执行文件体积 可能较大，取决于纳入的代码 通常较小，但取决于实际使用方式和依赖
多程序共享代码 不同应用中的同一库代码可能重复 可共享同一共享库的文件支持代码页
库更新 通常需要重新链接程序 满足兼容性要求时，可以独立更新共享库
部署可预测性 更容易固定库代码版本 运行环境中的依赖版本及搜索路径更加重要
启动过程 仍可能包含其他动态依赖 通常需要处理动态库装载与重定位
运行时符号解析 静态链接进去的引用通常已经在构建阶段解决 需要处理动态符号与相关重定位
插件扩展 需要额外设计插件或加载机制 可结合 dlopen() 等实现运行时扩展

需要补充的是，静态链接不保证整个程序没有任何动态依赖；动态链接也不意味着每条函数调用都需要反复进行符号查找。

实际效果取决于输出文件的类型、链接选项、运行时环境和程序的具体行为。

4.2 什么场景适合静态链接？#

场景一：受控环境中的独立部署#

如果程序需要在版本固定、依赖环境受控的机器上运行，将部分第三方库静态链接进去，可以减少对目标机器安装特定共享库的要求。

不过，如果程序还动态依赖 C 运行时、其他系统组件或插件，那么这些依赖仍然需要处理。

场景二：小型工具和部分嵌入式应用#

某些工具或嵌入式程序希望减少运行环境中的依赖。在工具链与系统库支持的情况下，静态链接能够简化部署。

但应当区分“把自己的库静态链接进去”与“将整个程序完全静态链接”。后者可能受到系统 API、运行时组件和 libc 实现等方面的限制。

场景三：固定构建产物中的第三方代码版本#

当一个应用需要严格控制某些第三方库版本时，静态链接可以让库的机器代码随应用程序一起固定下来，减少运行时共享库发生变化的影响。

代价是，后续更新和安全修复往往需要重新构建、重新发布应用程序。

4.3 什么场景适合动态链接？#

场景一：大型桌面应用和服务器软件#

大型应用通常依赖多个第三方库和系统库。动态链接有利于建立独立的模块交付、维护和升级方式。

当然，这也要求项目正确维护共享库依赖、ABI 兼容性和运行时搜索路径。

场景二：需要复用大量公共代码的系统#

动态共享库能够让同一份共享库的文件支持代码页被多个进程映射和复用。

但这不意味着所有进程之间的整个库内存都完全共享：可写数据通常具有各进程自己的语义和映射，发生重定位或写入时也可能涉及写时复制。

场景三：插件式架构#

对于需要根据配置或业务情况加载功能模块的程序，动态库和动态加载接口能够提供更灵活的扩展方式。

不过，插件接口仍然需要清晰定义 ABI、符号导出规则、依赖管理和生命周期约定。

4.4 静态链接也不一定更快#

静态链接和动态链接之间的性能差异不能仅凭概念推断。

动态链接程序在启动阶段通常需要处理共享对象依赖、映射和必要的动态重定位。对于大量动态对象或者复杂的符号依赖，这些步骤可能增加启动开销。

传统 PLT 延迟绑定可能在第一次调用某个外部函数时引入额外开销，但后续调用可以使用已经解析的地址。使用立即绑定时，部分工作则会提前到启动阶段完成。

静态链接能够在构建阶段处理更多引用，但不意味着静态链接一定让所有函数调用更快。编译器优化、链接时优化（LTO）、调用方式、代码布局、缓存行为以及程序本身的工作负载，都会影响最终结果。

因此，涉及性能决策时，应当通过实际构建、反汇编和性能测量来判断，而不是简单地将静态链接等同于高性能。

4.5 动态链接的维护成本：依赖和 ABI#

动态链接为独立更新共享库提供了便利，但它同时引入了运行时兼容性问题。

例如，某个应用程序依赖：

libmathops.so.1

当共享库更新后，至少需要关注几个问题：

  1. 库的 SONAME 是否仍然对应兼容的 ABI；
  2. 已有导出符号是否仍然存在；
  3. 函数的参数、返回值、数据结构布局和调用约定是否兼容；
  4. 新的动态库依赖是否能够在目标环境中找到；
  5. 动态库搜索路径是否正确且安全。

如果程序在构建时依赖了一个符号，但运行时找到的库不再提供该符号，就可能在装载阶段失败。

即使符号名称没有变化，如果函数调用约定、对象布局或数据语义发生不兼容变化，也可能导致程序异常。

因此，共享库的版本管理与 ABI 设计是系统软件开发中的重要问题。动态链接解决了代码组织和复用的一部分需求，但并不会自动保证库之间兼容。

4.6 动态链接的安全性与部署实践#

动态库搜索路径也会影响安全性。

假如程序在不可信的目录中搜索共享库，恶意文件就可能以预期库的名称被加载。

在 Linux 上，LD_LIBRARY_PATH 可以改变动态链接器的搜索路径，但它并不是所有部署问题的通用解决办法。在安全执行模式下，该变量可能被忽略；将其用于生产环境前，也需要考虑进程环境的来源和可信程度。

对于可部署的软件，通常应当明确共享库的安装位置，并采用合适的 SONAME、受控搜索路径、运行时依赖管理和发布方式。

如果使用 $ORIGIN，也应当确保该相对路径所指向的位置处于可信的部署目录中。

此外，静态链接并不自动消除安全风险。静态集成的第三方代码如果存在漏洞，仍然需要通过更新库、重建应用程序和重新发布等方式修复。

因此，从安全角度看，关键不只是选择静态链接还是动态链接，而是能否持续管理软件的依赖、版本与更新过程。

4.7 实际项目中的选择建议#

对于一般 Linux/C/C++ 项目，可以采用以下思路：

  • 应用程序需要灵活更新公共依赖、依赖系统共享库，或采用插件式架构时，优先考虑动态链接。
  • 某些第三方库希望随应用程序固定版本、减少独立共享库依赖时，可以考虑静态链接这些特定库。
  • 需要单文件交付或更可控的运行环境时，再评估是否值得采用更大范围的静态链接，并验证工具链和系统运行时是否支持。
  • 对启动速度、文件体积或运行性能有明确要求时，应通过真实工作负载和工具测量，再决定哪些库适合静态或动态链接。

工程项目也完全可以同时使用两种方式。例如，程序可以把某个小型第三方库静态链接进去，同时继续使用系统提供的动态 C 运行时。

最终选择应当来自实际约束，而不是预先认为某种方式绝对优于另一种方式。

5. 总结：从链接器理解程序是如何形成的#

从历史上看，链接器的出现是为了让程序能够由多个独立模块构建而成，解决跨模块符号引用和地址重定位问题。

静态链接和动态链接只是这些需求的两种不同组织方式。

静态链接通常在构建阶段把所需目标代码整合进输出文件，使相应引用不再依赖运行时的独立共享库。

动态链接则在构建阶段记录共享对象依赖，并在运行时通过动态链接器装载共享库、解析符号和完成必要的重定位。

整个过程可以归纳为：

源代码
   │
   ▼
编译与汇编
   │
   ▼
目标文件
   │
   ├── 静态链接
   │      │
   │      ▼
   │   生成包含所需目标代码的输出文件
   │
   └── 动态链接
          │
          ▼
       生成记录动态依赖的输出文件
          │
          ▼
       内核运行程序并启动动态链接器
          │
          ▼
       装载共享库、解析符号、处理重定位
          │
          ▼
       进入程序启动代码与 main()

如果想进一步深入 Linux 系统编程，可以在自己的实验环境中持续追踪以下问题：

  1. 编译器如何在 .o 文件中留下未定义符号和重定位信息？
  2. GNU ld 如何决定最终输出文件的节布局和程序段布局？
  3. ar 与真正的链接器分别负责什么工作？
  4. ELF 的 DT_NEEDED、DT_SYMTAB、DT_RELA 和 DT_JMPREL 等信息如何参与动态链接？
  5. ld.so 如何搜索共享库，又如何完成 GOT、PLT 和其他动态重定位？
  6. 使用 dlopen() 加载的插件，与程序启动时自动装载的共享库之间有何异同？

当你能够使用 nm、readelf、objdump 等工具，将源代码中的函数调用对应到目标文件中的符号、重定位记录以及运行时的装载行为时，就不再只是会使用编译器和链接器，而是开始真正理解程序是怎样从源代码变成可执行映像的。
