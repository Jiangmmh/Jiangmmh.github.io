上一篇讲的是内存，这一篇讲并发。并发是 xv6 里最容易写出 bug、也最难调试的部分：对多核的支持让两个 CPU 同时修改同一份数据，中断让内核代码在任意时刻被打断，进程切换又让同一个数据结构被不同的进程轮流访问。

这一篇先回答"为什么需要锁"，再逐行拆解 xv6 里的两种锁（Spinlock 和 Sleeplock），最后对照 Linux 的并发机制，看看一个通用操作系统为了应付更复杂的场景，做了哪些 xv6 没做的设计。

# 一、为什么要提供并发机制？

## 1.1 并发的三个来源

并发不等于"多核"。只要存在两个执行流能同时访问同一份内存，并发就存在。在 xv6 里，它有三个来源：

**来源一：多核（SMP）。** `kernel/param.h` 中定义了 `NCPU 8`，即最多 8 个 hart（CPU 核）可以同时运行内核代码。它们共享同一片物理内存，也共享同一批外设（virtio 磁盘、uart）。两个核同时修改同一个内存地址，就是一次数据竞争。

**来源二：中断与抢占。** 内核代码随时可能被中断打断，而中断处理程序与被中断的代码共享数据结构。最典型的例子在 `kernel/console.c` 里：键盘中断处理程序 `consoleintr()` 往输入缓冲区写字符，进程通过 `consread()` 从同一个缓冲区读字符，两者靠同一把 `cons.lock` 保护。

**来源三：进程切换。** 多个进程通过系统调用共享文件、管道、inode 和页表。`struct file` 的引用计数、pipe 的环形缓冲区、inode 的引用计数，都会被多个进程并发访问。

这三个来源有一个共同点：**它们都会打断一段正在运行的代码**。因此临界区里的代码必须假设"我随时可能被打断，并且被打断后别人也在改同样的数据"。

## 1.2 没有同步会发生什么

### 竞态条件：结果依赖执行顺序

看 `kernel/kalloc.c` 里分配物理页的代码：

```c
void *
kalloc(void)
{
  struct run *r;

  acquire(&kmem.lock);
  r = kmem.freelist;
  if (r) {
    kmem.freelist = r->next;
  }
  release(&kmem.lock);
  if (r)
    memset((char *)r, 5, PGSIZE); // fill with junk
  return (void *)r;
}
```

假设去掉 `acquire/release`。CPU0 和 CPU1 同时进入临界区，可能读到同一个 `r`：

- CPU0：`r = freelist`，然后 `freelist = r->next`
- CPU1：`r = freelist`（读到的是 CPU0 还没写回之前的旧值，还是同一个 `r`），然后 `freelist = r->next`

结果：`freelist` 只前进了一格，**同一个物理页被交给了两个进程**。更糟的是两个进程都会对它 `memset`，数据被静默覆盖——这类 bug 不崩溃，只是结果随机，非常难查。

这就是典型的 check-and-set 竞态：多个 CPU 同时"检查并设置"同一个状态，而检查和设置不是原子的。

### 死锁：循环等待

CPU0 持有锁 A、请求锁 B；CPU1 持有锁 B、请求锁 A。两者永远等不到对方释放，整机卡死。这是多把锁嵌套获取时最常见的问题，1.4 节讨论的锁顺序就是用来预防它的。

### 丢失唤醒：信号发给了空气

生产者—消费者模型的经典错误。消费者要读缓冲区里的数据：

```c
while (buffer_empty())
  sleep();      // 检查与睡眠之间存在窗口
data = buffer_get();
```

如果消费者检查完"缓冲区为空"、还没来得及睡下，生产者就放入数据并发出信号——此时消费者是醒着的，信号无处可送。消费者随后睡下去，数据却已经在缓冲区里了，于是消费者**永远睡下去**，数据被"吃掉"。

xv6 的 `console.c` 就是这个结构，所以它的读循环必须写成"检查 + 登记等待通道 + 睡眠"三步不可分割的形式（后面 2.5 节详述）。

## 1.3 一个同步原语要回答三个问题

设计任何一种锁，本质上都要回答三个问题：

1. **互斥**：临界区不能同时被两个执行流进入。这需要原子地"检查并设置"锁状态。
2. **内存序 / 可见性**：一个 CPU 在临界区里的写，什么时候对其他 CPU 可见？编译器可以重排指令，CPU 也有自己的 store buffer，如果没有显式约束，"先写数据再释放锁"这个顺序可能被打破，另一个 CPU 就会读到旧数据。
3. **等待策略**：拿不到锁怎么办？忙等（自旋）还是让出 CPU（阻塞）？

第 3 个问题的答案不是非此即彼，而是取决于临界区的性质：临界区短就用忙等（延迟低），临界区长（要读磁盘）就必须阻塞（否则纯属浪费 CPU）。

## 1.4 为什么不止一种锁

把 1.3 的三个维度展开，就得到了锁的分类依据：

| 维度 | 取值 | 影响 |
| --- | --- | --- |
| 临界区长度 | 短 / 长 | 决定能否忙等 |
| 执行上下文 | 内核态 / 中断上下文 | 决定能否睡眠 |
| 共享模式 | 单写多读 / 独占 | 决定要不要读写锁 |

xv6 只实现了两种锁，覆盖了"独占 + 两种等待策略"的组合：

- **Spinlock**：临界区短，可以在中断上下文用，忙等。
- **Sleeplock**：临界区长，只能在进程上下文用，阻塞。

![两种等待策略：自旋锁 vs 睡眠锁](/images/posts/xv6-concurrency/image.png)

再往下看 Linux，就会发现它把这个二维表格扩展成了一个完整的锁家族（3.10 节）。

# 二、xv6中的并发机制

## Spinlock

### 数据结构

```c
// kernel/spinlock.h
struct spinlock {
  uint locked; // Is the lock held?

  // For debugging:
  char *name;      // Name of lock.
  struct cpu *cpu; // The cpu holding the lock.
};
```

三个字段各司其职：`locked` 是锁状态本身；`name` 只用于调试（panic 时能知道是哪把锁）；`cpu` 记录当前持有者，使得 `holding()` 可以判断"这把锁是不是我自己持有的"。

### 获取锁：原子交换 + Acquire 语义

```c
// kernel/spinlock.c
void
acquire(struct spinlock *lk)
{
  push_off(); // disable interrupts to avoid deadlock.
  if (holding(lk))
    panic("acquire");

  // On RISC-V, __atomic_exchange_n turns into an atomic swap:
  //   a5 = 1
  //   s1 = &lk->locked
  //   amoswap.w.aq a5, a5, (s1)
  while (__atomic_exchange_n(&lk->locked, 1, __ATOMIC_ACQUIRE) != 0)
    ;

  // Record info about lock acquisition for holding() and debugging.
  lk->cpu = mycpu();
}
```

逐行拆开看：

- `__atomic_exchange_n(&lk->locked, 1, __ATOMIC_ACQUIRE)` 是一次**原子读改写**：无论原来是什么值，都把 `locked` 写成 1，并返回**旧值**。旧值非 0 就说明锁被别人占着，于是循环重试。这正是 1.2 节那个竞态条件需要的 check-and-set，只是"检查"和"设置"被合并成了一条硬件指令。

- 在 RISC-V 上它被编译成 `amoswap.w.aq`。`.aq` 后缀就是 **acquire 语义**：这条指令**之后**的访存操作不允许被重排到它**之前**。于是临界区里的读写一定发生在拿到锁之后，不会出现"锁还没拿到，数据已经改了"的乱序。

- 为什么用 `while` 而不是 `if`？因为多个等待者可能同时观察到"锁是空闲的"，但原子交换只允许其中一个成功，其余的必须重新循环。

- 为什么用 acquire/release 这种"单向屏障"，而不是更强的 seq_cst？单向屏障已经足以保证临界区的顺序性，开销却小得多。

### 释放锁：Release 语义与内存屏障

```c
void
release(struct spinlock *lk)
{
  if (!holding(lk))
    panic("release");

  lk->cpu = 0;

  // Release the lock, equivalent to lk->locked = 0.
  //
  // This code doesn't use a C assignment, since the C standard
  // implies that an assignment might be implemented with
  // multiple store instructions.
  //
  // On RISC-V, __atomic_store_n turns into a single atomic store:
  //   s1 = &lk->locked
  //   fence rw,w
  //   sw zero,0(s1)
  __atomic_store_n(&lk->locked, 0, __ATOMIC_RELEASE);

  pop_off();
}
```

这里有两个容易被忽略的细节：

**第一，不能写成 `lk->locked = 0;`。** C 标准并不保证一条赋值编译成一条 store 指令，它可能被拆成"load + store"两条指令——那就变成了读改写，不再是原子的操作。更重要的是，普通赋值没有 release 语义，临界区里的写可能还没对其他 CPU 可见，锁就已经放开了。

**第二，release 语义保证顺序。** `__ATOMIC_RELEASE` 表示：**之前**的访存操作不允许被推迟到释放之后。编译到 RISC-V 上就是先执行一条 `fence rw,w`（读写屏障），再执行 `sw zero, 0(s1)`。于是"临界区内写数据"一定先于"放锁"对其他 CPU 可见。

把两个方向合起来看：**acquire 保证"拿到锁之后才动数据"，release 保证"动完数据才放锁"**。这正是 1.3 节里"内存序"那一问的答案。

### 为什么 acquire 要关中断

`acquire` 的第一行是 `push_off()`，它关掉当前 CPU 的中断：

```c
void
push_off(void)
{
  uint64 flags = rc_sstatus(SSTATUS_SIE);
  int old = !!(flags & SSTATUS_SIE);

  if (mycpu()->noff == 0)
    mycpu()->intena = old;
  mycpu()->noff += 1;
}
```

考虑这样一个场景：CPU0 正持有 `cons.lock`，此时键盘中断到来，`consoleintr()` 也想 `acquire(&cons.lock)`。如果中断没有被关掉，中断处理程序就会在同一把锁上自旋等待——**而这把锁的持有者正是被中断的 CPU0 自己**。CPU0 必须等中断处理程序返回才能走到 `release()`，而中断处理程序在等 CPU0 放锁。互相等待，CPU0 彻底死锁。

所以自旋锁必须关中断：**同一把锁不能在同一个 CPU 上被重入**。

注意关中断只影响**本 CPU**，其他 CPU 依然可以正常执行 `release()`，所以自旋等待本身不会因为关中断而失去进展。

`push_off/pop_off` 是**计数式**的：`noff` 记录嵌套层数，`intena` 记录"进入最外层时中断本来是开着的"。这样 acquire/release 可以嵌套（持有 A 再获取 B），关中断也能正确配对：只有在最外层 `pop_off()` 且原本中断是开的情况下，才真正恢复中断。

### 三条使用铁律

1. **不能在持有自旋锁时睡眠。** `sleep()` 会调用 `sched()` 把当前进程换下 CPU，但它持有的锁没人释放，其他 CPU 就会永远在那把锁上自旋——整机 hang。`kernel/log.c` 里有一句注释把这事说得很直白：`// call commit w/o holding locks, since not allowed to sleep with locks.`
2. **不能递归获取同一把锁。** `acquire` 里 `if (holding(lk)) panic("acquire")` 就是这条规则的运行时检查。
3. **中断上下文只能用自旋锁。** 中断处理程序不能睡眠，也就只能自旋。

### 典型用例

| 锁 | 保护对象 | 位置 |
| --- | --- | --- |
| `kmem.lock` | 物理页 freelist | `kernel/kalloc.c` |
| `bcache.lock` | 缓冲缓存的 LRU 链表 | `kernel/bio.c` |
| `itable.lock` | inode 表 | `kernel/fs.c` |
| `cons.lock` | 控制台输入缓冲（中断与进程共享） | `kernel/console.c` |
| `p->lock` | 进程状态 `state` / `chan` / `killed` | `kernel/proc.c` |
| `ftable.lock` | 文件表 | `kernel/file.c` |
| `vdisk_lock` | virtio 磁盘请求队列 | `kernel/virtio_disk.c` |

## Sleeplock

### 为什么需要睡眠锁

自旋锁有两个硬伤：

**硬伤一：临界区可能很长。** xv6 里 `ilock()` 要从磁盘读 inode，`bread()` 要读磁盘块，这些操作是毫秒级的，其他 CPU 在旁边空转纯属浪费。

**硬伤二（更致命）：持锁者一旦被调度器换下 CPU，锁就永远不会被释放。** 如果持锁者在临界区里调用了 `sleep()`（比如去读磁盘），它会被换下 CPU，而所有其他 CPU 都在那把自旋锁上空转。系统就此僵死。

所以需要一种"拿不到锁就让出 CPU"的锁——这就是睡眠锁。

### 数据结构

```c
// kernel/sleeplock.h
struct sleeplock {
  uint locked;        // Is the lock held?
  struct spinlock lk; // spinlock protecting this sleep lock

  // For debugging:
  char *name; // Name of lock.
  int pid;    // Process holding lock
};
```

注意这是一个**两层结构**：外层 `locked` 提供"进程级、可阻塞"的语义，内层 `lk` 是一把普通的内核自旋锁，用来保护外层状态本身（读取和修改 `locked` 必须原子）。

`name` 和 `pid` 用于调试：`holdingsleep()` 会检查"锁的持有者是不是我"，防止一个进程释放别人持有的锁。

### acquiresleep 逐行拆解

```c
// kernel/sleeplock.c
void
acquiresleep(struct sleeplock *lk)
{
  acquire(&lk->lk);
  while (lk->locked) {
    sleep_prepare(lk);
    release(&lk->lk);
    sleep();
    acquire(&lk->lk);
  }
  lk->locked = 1;
  lk->pid = myproc()->pid;
  release(&lk->lk);
}
```

配合 `kernel/proc.c` 里的睡眠机制一起看：

```c
// Register current process as waiting for wakeups on chan.
void
sleep_prepare(void *chan)
{
  struct proc *p = myproc();

  acquire(&p->lock);
  if (chan == 0)
    panic("sleep_prepare: zero chan");
  p->chan = chan;
  release(&p->lock);
}

// Put the thread to sleep.  Assumes sleep_prepare() was called before.
// If the channel registered by sleep_prepare() has been woken up in
// the meantime, do not go to sleep, and instead return immediately.
void
sleep(void)
{
  struct proc *p = myproc();

  acquire(&p->lock);
  if (p->chan != 0) {
    p->state = SLEEPING;
    sched();
  }
  release(&p->lock);
}
```

`p->chan` 是进程的**等待通道**：xv6 用它记录"我在等谁唤醒"。睡眠锁对象自己的地址就充当通道号——`sleep_prepare(lk)` 相当于声明"我睡在这把锁上"。

整个流程是：

1. `acquire(&lk->lk)`：先拿内层自旋锁，保证对 `locked` 的检查与修改是原子的。
2. `while (lk->locked)`：锁被别人持有，需要等。必须用 `while` 而不是 `if`，因为醒来后可能又被别人抢走。
3. `sleep_prepare(lk)`：**登记等待通道**。此时仍持有 `lk->lk`——这个顺序至关重要（见 2.5 节）。
4. `release(&lk->lk)`：放掉内层自旋锁。如果不放手就睡，别人永远无法执行 `releasesleep()`，睡眠锁就永远解不开。
5. `sleep()`：真正让出 CPU，`state = SLEEPING`，`sched()` 切走。
6. 被唤醒后重新 `acquire(&lk->lk)`，回到 `while` 重新检查。
7. 拿到锁：`locked = 1`，记录持有者 pid，放掉内层自旋锁。

### releasesleep 与唤醒

```c
void
releasesleep(struct sleeplock *lk)
{
  acquire(&lk->lk);
  lk->locked = 0;
  lk->pid = 0;
  wakeup(lk);
  release(&lk->lk);
}
```

```c
void
wakeup(void *chan)
{
  struct proc *p;

  for (p = proc; p < &proc[NPROC]; p++) {
    acquire(&p->lock);
    if (p->chan == chan) {
      // If the process is waiting for wakeups on this channel,
      // signal that the wakeup happened by clearing p->chan.
      p->chan = 0;

      // If this waiting process has gotten so far as to actually
      // go to sleep, also set it back to RUNNING.
      if (p->state == SLEEPING) {
        p->state = RUNNABLE;
      }
    }
    release(&p->lock);
  }
}
```

`wakeup(lk)` 是在**持有 `lk->lk` 的情况下**调用的，这保证"清零 `locked`"和"唤醒等待者"对其他等待者而言是一个不可分割的步骤。否则会出现这样的错乱：释放者刚把 `locked` 清零还没 `wakeup`，新来的进程看到 `locked == 0` 直接把锁拿走并释放，随后释放者的 `wakeup` 醒来一个早已不在等待的进程，信号白白消耗掉。

### 为什么不会丢失唤醒

这是睡眠锁最微妙的地方。回到 1.2 节的丢失唤醒场景：等待者必须在"检查"和"睡下"之间保证自己**不会错过信号**。

xv6 的做法是靠**同一把内层自旋锁**建立 happens-before 关系：

- 等待者 A：`sleep_prepare(lk)` 写 `p->chan = lk` → `release(&lk->lk)`
- 释放者 B：`acquire(&lk->lk)` → `wakeup(lk)` 读 `p->chan`

A 的写发生在 A 释放锁**之前**，B 的读发生在 B 获得锁**之后**。锁本身的同步语义（acquire/release）保证：B 一定能看到 A 的登记。

反过来说，**顺序不能颠倒**。如果先 `release(&lk->lk)` 再 `sleep_prepare(lk)`，B 可能在 A 睡下之前就完成了 `wakeup`，A 将永远睡下去——这就是丢失唤醒。

![acquiresleep 的时序：为什么不会丢失唤醒](/images/posts/xv6-concurrency/image%201.png)

这个"**登记 → 放锁 → 睡 → 重新拿锁**"的模式在 xv6 里随处可见，它是"持有自旋锁时如何安全地等待一个异步事件"的标准写法。比如 `kernel/console.c` 的 `consread()`：

```c
    while (cons.r == cons.w) {
      if (killed(myproc())) {
        release(&cons.lock);
        return -1;
      }
      sleep_prepare(&cons.r);
      release(&cons.lock);
      sleep();
      acquire(&cons.lock);
    }
```

以及 `kernel/virtio_disk.c` 里等待磁盘中断完成传输：

```c
  // Wait for virtio_disk_intr() to say request has finished.
  while (b->disk == 1) {
    sleep_prepare(b);
    release(&disk.vdisk_lock);
    sleep();
    acquire(&disk.vdisk_lock);
  }
```

注意最后这个例子：进程持有 `vdisk_lock` 提交磁盘请求，然后必须**先放锁再睡**，否则设备中断处理程序 `virtio_disk_intr()` 拿不到 `vdisk_lock`，这个请求就永远完成不了。

### 典型用例

睡眠锁全部用在"临界区可能很慢"的地方：

| 睡眠锁 | 保护对象 | 为什么必须可睡眠 |
| --- | --- | --- |
| `inode.lock` | inode 元数据与块指针 | `ilock()` 里要 `bread()` 读磁盘 |
| `buf.lock` | 磁盘块缓冲 | 同一块磁盘数据同一时刻只允许一个进程使用 |
| `file.lock` | `struct file` 内容 | 保护文件描述符指向的 inode 与偏移 |
| `tx_lock` | 串口发送 | 串行化对 uart 的写，避免多个进程输出交错 |

对应的代码在 `kernel/fs.c` 的 `ilock()/iunlock()`、`kernel/bio.c` 的 `bget()/brelse()`、`kernel/uart.c` 的 `uartwrite()`。

### 使用铁律

1. **不能在持有自旋锁时调用 `acquiresleep`/`releasesleep`。** `acquiresleep` 内部会放掉自己的内层自旋锁然后睡眠，但你外面的那把自旋锁还握着——睡醒之后，别人永远拿不到你手里这把锁，死锁。
2. **睡眠锁不能在中断上下文使用。** 中断里不能睡眠。
3. **睡眠锁可以嵌套**（睡眠只是让出 CPU，不改变"谁持有锁"的事实），但同时持有多把睡眠锁时必须有全局的加锁顺序，否则会死锁。

## 两种锁的对比

| 维度 | Spinlock | Sleeplock |
| --- | --- | --- |
| 等待方式 | 忙等自旋 | 阻塞，让出 CPU |
| 临界区长度 | 必须短，不能有 I/O | 可以长，允许磁盘 I/O |
| 可用上下文 | 内核态 + 中断上下文 | 仅进程上下文 |
| 持有期间能否睡眠 | 绝对不行 | 可以（由 `acquiresleep` 内部完成） |
| 实现方式 | 原子交换 + 关中断 | 自旋锁 + `sleep`/`wakeup` |
| 主要风险 | 重入自死锁；持锁睡眠导致整机 hang | 锁顺序反转导致死锁 |
| 调试手段 | `panic("acquire")`、`holding()` | `holdingsleep()` 检查 pid |

## 锁顺序：死锁的预防

死锁的四个必要条件里，最容易被程序员主动破坏的就是"循环等待"。预防办法是给所有锁规定一个**全局顺序**，任何执行流只按这个顺序获取锁。

xv6 里的例子是 `kernel/fs.c` 的 `iput()`：

```c
  acquire(&itable.lock);
  ...
  if (last) {
    // ip->ref == 1 means no other process can have ip locked.
    acquiresleep(&ip->lock);
    release(&itable.lock);

    itrunc(ip); // free the data blocks (type stays nonzero on disk)
    ip->valid = 0;

    releasesleep(&ip->lock);

    acquire(&itable.lock);
  }
```

这里的规则是 `itable.lock` → `ip->lock`：先取 `itable.lock`，再取 `ip->lock`，然后立刻释放 `itable.lock`。这样全局顺序固定，任何地方都不会出现 `ip->lock` → `itable.lock` 的反向嵌套，也避免了长时间同时持有两把锁。

另一条隐含规则是：**不要在持有 `p->lock` 时去获取别的锁**。因为 `wakeup()` 需要遍历所有进程并逐个获取 `p->lock`，如果持有 `p->lock` 又去拿别的锁，很容易形成环形等待。

## 小结

xv6 用两种锁覆盖了内核并发需求的绝大部分场景，规则很少、代价很小：**不能持锁睡眠、不能重入、锁序固定**。代价是没有读写锁、没有 RCU、没有死锁检测工具——正确性完全依赖每个写代码的人记住这几条规则。Linux 正是为了摆脱这种"依赖记忆力"的状态，才演化出了下面这一整套机制。

# 三、Linux中的并发机制

## 3.1 Linux 的并发环境比 xv6 复杂在哪

Linux 面对的场景是 xv6 的超集：

- **SMP 与 NUMA**：多核之间还有节点亲和性问题，锁的争用路径更长。
- **完全抢占的内核**（`CONFIG_PREEMPT`）：内核态代码随时可能被调度器抢走，这比 xv6 的协作式 `yield` 激进得多。
- **中断 + softirq 两套异步环境**：硬中断、软中断（bottom half）都能抢占普通内核代码。
- **实时调度**：`SCHED_FIFO`/`SCHED_RR` 让高优先级任务可以抢占低优先级任务，锁就成了优先级反转的放大器。
- **用户态多线程**：进程内的线程也要互斥。

临界区的长度跨度从"几条指令"到"一次磁盘 I/O"，等待方式、可用上下文、优先级策略全都不同。因此 Linux 的锁不是一个原语，而是一个**家族**：

![Linux 同步原语家族](/images/posts/xv6-concurrency/image%202.png)

## 3.2 自旋锁家族

**`spinlock_t`** 是 Linux 的主力自旋锁：

- 实现上是 **ticket lock（qspinlock）**：每个等待者先取一个号，再按号顺序进入。相比 test-and-set，它避免了"惊群"和 cache line 反复失效带来的争用风暴，公平性也更好。
- 获取时会**关闭抢占**（`preempt_disable()`），因此临界区不会被调度器切走——这是 Linux 自旋锁与 xv6 自旋锁最大的行为差异：xv6 关的是中断，Linux 关的是抢占（两者在 `spin_lock_irqsave()` 里同时做）。

**`raw_spinlock_t`** 是"裸"自旋锁，连关抢占都不做，只用于真正不能睡眠的底层路径：中断上下文、访问硬件寄存器、写驱动代码等。

自旋锁的变体通过后缀表达"额外禁用了什么"：

| 变体 | 额外语义 | 典型场景 |
| --- | --- | --- |
| `spin_lock_irqsave/restore` | 关中断 | 与硬中断处理程序共享的数据 |
| `spin_lock_bh` | 关 bottom half | 与 softirq 共享的数据 |
| `spin_lock` | 仅关抢占 | 普通内核路径 |
| `read_lock` / `write_lock`（`rwlock_t`） | 多个读者可并发 | 读多写少的共享数据 |

内存序方面，Linux 用显式的屏障原语而不是依赖 C11 模型：`smp_mb()`、`smp_wmb()`、`smp_rmb()`、`barrier()`，以及 `READ_ONCE()`/`WRITE_ONCE()`（防止编译器把多次访问合并成一次，或把指针读取提升出循环）。

## 3.3 睡眠锁家族

**`mutex`（`struct mutex`）** 是最常用的可睡眠锁：

- 有明确的持有者（owner），因此可以做**优先级继承**（见 3.8）。
- 可以被信号打断（`mutex_lock_interruptible()`）。
- 支持**依赖调试**（lockdep 会记录加锁顺序）。
- 只能在进程上下文使用。

**`rwsem`（`struct rw_semaphore`）** 是读写信号量：多个读者可并发持有，写者独占。设计上**偏向写者**，避免写者被源源不断的读者饿死。`down_read()` 可以在中断上下文使用（这也是 `rwsem` 与 `mutex` 的关键区别）。

**`semaphore`（`struct semaphore`）** 是计数信号量：`down()` 一次减一，`up()` 一次加一。它没有"所有者"概念，所以**无法做优先级继承**，这是它相对 `mutex` 的主要劣势。

## 3.4 RCU：把读侧成本降到接近零

前面所有锁都要求读者和写者互相等待。但很多内核数据结构的访问模式是**读远多于写**（路由表、目录项、链表）。

RCU（Read-Copy-Update）的思路是：**读侧干脆不上锁**。

- **读侧**：`rcu_read_lock()` 在普通内核里只是禁止抢占（不碰任何锁），读完 `rcu_read_unlock()`。读一条链表的开销几乎为零。
- **写侧**：复制一份 → 修改副本 → 用 release 语义发布新指针 → 等待一个**宽限期**（grace period），确保所有可能还在读旧对象的读者都已经退出 → 再释放旧对象。

代价是写侧很重、内存占用高、对内存序要求极严。Linux 把它用在读多写少、且对象生命周期容易跟踪的地方。

## 3.5 原子操作与内存屏障

原子操作是比锁更细粒度的同步工具：

- `cmpxchg`（compare-and-swap）、`xadd`、`fetch_add` 等，用于实现无锁栈、无锁计数器、原子地修改某个标志位。
- 屏障分三层：**编译器屏障**（`barrier()`，只阻止编译器重排）、**CPU 屏障**（`smp_mb()`，在 x86 上是 `lock; addl`，在 RISC-V 上是 `fence`）、**acquire/release 语义**（单向屏障，Linux 内核里对应 `smp_store_release()`/`smp_load_acquire()`）。

xv6 里 `__atomic_exchange_n(..., __ATOMIC_ACQUIRE)` 和 `__atomic_store_n(..., __ATOMIC_RELEASE)` 用的正是 C11 的 acquire/release 模型，与 Linux 的 `smp_load_acquire()`/`smp_store_release()` 是同一套思想的两种表达。

## 3.6 futex：用户态自旋 + 内核态阻塞

glibc 的 `pthread_mutex_lock()` 走的是一条"能不进内核就不进内核"的路径：

1. **无竞争**：纯用户态 CAS 加解锁，完全不进内核（最快路径）。
2. **有竞争**：先在用户态自旋若干次（此时持有锁的线程很可能马上就会释放），仍不行则调用 `futex(FUTEX_WAIT)`，让内核把当前线程挂到等待队列上。
3. **解锁方**：原子地把锁标记为"有等待者"，再调用 `futex(FUTEX_WAKE)` 唤醒等待者。

思路和 xv6 的睡眠锁一模一样——快路径不进内核，慢路径交给内核阻塞——区别只是 Linux 把"自旋"放在用户态，并且是用无锁 CAS 实现的。

## 3.7 lockdep：把"靠自觉"变成"靠工具"

xv6 靠人记住"不能持锁睡眠、不能重入、锁序固定"。Linux 用 `CONFIG_PROVE_LOCKING` / `CONFIG_DEBUG_LOCKDEP` 把这些规则变成**可自动验证**的：

- 内核为每一类锁（lock class）记录加锁关系，维护一张偏序图。
- 如果发现 A → B 与 B → A 的反向嵌套，立刻报 `possible circular locking dependency` 并打印双方的加锁栈。
- 还能检测递归加锁、在中断上下文释放锁、持有锁时睡眠、irq 反转等等。

`3.9` 节的 PREEMPT_RT 正是靠 lockdep 强制出"睡眠锁 → `spinlock_t` → `raw_spinlock_t`"这条嵌套顺序的。

## 3.8 优先级反转与优先级继承

锁不只是"互斥工具"，在实时系统里它还是**优先级的放大器**。经典的优先级反转场景：

- 高优先级任务 H 等待一把被低优先级任务 L 持有的锁。
- 中优先级任务 M 抢占了 L（L 明明可以继续跑完临界区放锁，却让给了 M）。
- M 又不依赖那把锁，于是 H 一直等不到锁——**优先级被反转**。

**优先级继承（PI）**是解法：当有任务阻塞在一把支持 PI 的锁上时，把等待者的优先级临时提升给持有者（Linux 的 `rt_mutex_setprio()`），等持有者释放锁后再降回去（`boost()`/`deboost()`）。这样 L 会以 H 的优先级运行，尽快把锁交出去。

注意 `semaphore` 无法做 PI——计数信号量没有所有者，不知道该把谁的优先级提上去。`mutex` 和 PREEMPT_RT 下的锁都可以。

## 3.9 PREEMPT_RT：把自旋锁改造成睡眠锁

`CONFIG_PREEMPT_RT` 是 Linux 对 xv6 那个"自旋锁不能睡眠"硬约束的一次正面回应：

- `spinlock_t` / `rwlock_t` 的底层被换成**基于 `rtmutex` 的可睡眠锁**：等锁者可以睡眠而不是空转；持锁者会获得优先级继承；获取锁时用 `migrate_disable()` 钉住 CPU（保证 per-CPU 指针有效），但**不禁止抢占**。
- **中断被强制线程化**（IRQ thread）：中断处理程序跑在可被调度的内核线程上下文里，因此也可以睡眠。
- `raw_spinlock_t` 仍然是严格自旋锁，只保留在真正不能睡眠的底层路径（调度器、entry code、极底层中断代码）。
- 嵌套顺序被 lockdep 强制为：**睡眠锁 → `spinlock_t` → `raw_spinlock_t`**。

PREEMPT_RT 的意义在于：它把"绝不能睡眠"这条约束从 95% 的内核代码里删掉了，代价是一定的性能开销。对实时系统来说，这个交换是值得的。

## 3.10 xv6 与 Linux 对照

| 维度 | xv6 | Linux |
| --- | --- | --- |
| 自旋锁 | `struct spinlock` + `amoswap`，自实现 | `spinlock_t`（ticket lock）/ `raw_spinlock_t` |
| 关中断 | `push_off()` / `pop_off()`，计数式嵌套 | `local_irq_save()` / `spin_lock_irqsave()` |
| 睡眠锁 | `sleeplock`（自旋锁 + `sleep`/`wakeup`） | `mutex` / `rwsem` / `semaphore` |
| 读写锁 | 无 | `rwlock_t` / `rwsem` |
| 无锁读 | 无 | RCU |
| 原子操作 | GCC `__atomic` 内建 | `atomic_t` / `cmpxchg` / `READ_ONCE` |
| 内存序 | C11 acquire/release | `smp_mb()` / `barrier()` / `smp_load_acquire()` |
| 死锁检测 | 无（靠 `panic` 和约定） | lockdep 锁类序检查 |
| 优先级继承 | 无 | `mutex`/`rtmutex` PI，PREEMPT_RT |
| 抢占模型 | 协作式 `yield` + 定时器 | 完全抢占（PREEMPT / PREEMPT_RT） |
| 用户态同步 | 无（xv6 只有进程） | futex / pthread |

# 四、总结

1. **并发的根源是"共享状态 + 抢占"，不只是多核。** 中断和进程切换同样制造并发，xv6 里 `cons.lock` 的存在就是因为键盘中断和进程读 stdin 在抢同一个缓冲区。

2. **一个同步原语必须同时回答三个问题**：谁进临界区（互斥）、别人看到什么顺序（内存序）、拿不到锁怎么办（等待策略）。xv6 的 `__atomic_exchange_n(__ATOMIC_ACQUIRE)` 与 `__atomic_store_n(__ATOMIC_RELEASE)` 回答了前两个，Spinlock 与 Sleeplock 回答了第三个。

3. **选哪种锁是"临界区长度 × 执行上下文"的函数，不是性能问题**：短且可能出现在中断里 → 自旋锁；长且只在进程上下文 → 睡眠锁。

4. **睡眠锁最值得学的是那个"登记 → 放锁 → 睡 → 重新拿锁"的模式。** 它用同一把内层自旋锁把"检查"和"睡眠"缝成一个原子操作，从而消灭了丢失唤醒。`acquiresleep`、`consread`、`virtio_disk_rw` 三处代码是同一个模式的三个变体。

5. **Linux 走得更远，但方向和 xv6 一致**：RCU 把读侧成本降到接近零，lockdep 把规则从"靠人记"变成"靠工具验"，PREEMPT_RT 把"自旋锁不能睡"这条约束消掉。三者都在解决同一个问题——**并发规模变大之后，怎样让正确性不依赖人的记忆力**。
