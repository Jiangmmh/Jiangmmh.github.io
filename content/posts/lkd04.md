# 一、进程调度：What & Why？

上一章介绍了进程管理，讨论了 Linux 如何创建、管理和销毁进程。本章进一步讨论一个核心问题：

**当系统中存在多个可运行进程，但 CPU 资源有限时，内核应该选择哪个进程运行？**

这就是进程调度（Process Scheduling）。

进程调度器（Process Scheduler）是内核中负责分配处理器时间的子系统，它决定：

- 哪个进程获得 CPU？
- 进程什么时候获得 CPU？
- 进程可以运行多长时间？
- 什么时候应该暂停当前进程，让其他进程运行？

调度器是多任务操作系统的基础。它通过合理分配 CPU 时间，使多个进程能够交替执行，让用户感觉多个程序似乎在同时运行。

## 1.1 调度器的基本目标

假设一台单核计算机上存在三个进程：

| 进程 | 类型 | 当前状态 |
|---|---|---|
| A | 文本编辑器 | 等待键盘输入 |
| B | 视频编码 | 正在计算 |
| C | 后台任务 | 等待运行 |

CPU 在同一时刻只能执行一个进程。

如果 A 正在等待用户输入，继续让 A 占用 CPU 显然没有意义；此时应该让 B 或 C 运行。

因此，调度器的一个基本原则是：

> 只要系统中存在可运行进程，CPU 就应该尽可能保持忙碌。

注意，这里有一个重要概念：**Runnable（可运行）不等于 Running（正在运行）**。

一个进程可能处于以下两种情况：

- 正在 CPU 上执行。
- 已经具备执行条件，只是在等待 CPU 资源。

而正在等待磁盘 I/O、键盘输入、网络数据或其他事件的进程，属于阻塞状态（Blocked），暂时不参与 CPU 调度。

例如，一个进程执行 `read()`，但磁盘数据尚未准备好，它就可能进入睡眠状态。此时调度器应该选择其他可运行进程，而不是让它不断占用 CPU 检查数据是否到达。

## 1.2 多任务机制：协作式与抢占式

多任务操作系统主要有两种实现方式。

### 协作式多任务（Cooperative Multitasking）

协作式多任务要求进程主动放弃 CPU。

例如：

```c
while (1) {
    do_work();
    yield();
}
```

进程执行完一部分工作后，主动调用 `yield()`，告诉操作系统自己愿意让出 CPU。

这种机制的问题在于：操作系统无法强制一个进程让出 CPU。

如果某个进程一直执行死循环，不主动调用 `yield()`，其他进程就可能长期得不到执行机会。

因此，协作式多任务存在明显的局限：

- 进程可以长时间独占 CPU。
- 调度器无法主动控制进程运行时间。
- 一个失去响应的进程可能严重影响整个系统。

### 抢占式多任务（Preemptive Multitasking）

现代 Linux 使用抢占式多任务。

在这种机制下，操作系统可以主动暂停正在运行的进程，将 CPU 分配给其他进程。

这个过程称为抢占（Preemption）。

例如：

```text
进程 A 正在运行
       |
       v
时钟中断发生
       |
       v
内核检查是否需要重新调度
       |
       v
发现进程 B 应该运行
       |
       v
暂停 A，切换到 B
```

抢占式调度避免了进程长期占用 CPU 的问题。

通常，调度器会通过时间片（Timeslice）或其他运行时间控制机制限制进程连续占用 CPU 的时间。

需要注意：

- `yield()` 是进程主动让出 CPU。
- Preemption 是操作系统主动暂停进程。
- Context Switch 是从一个进程切换到另一个进程的执行上下文。

三者相关，但不是同一个概念。

# 二、Linux 的进程调度器

## 2.1 Linux 调度器的发展历史

Linux 调度器经历了多次重要演进。

理解这段历史，有助于理解为什么 Linux 最终采用 CFS。

| 内核版本 | 调度器 | 主要特点 |
|---|---|---|
| Linux 1.x ～ 2.4 | 早期调度器 | 实现简单，但扩展性不足 |
| Linux 2.5 | O(1) Scheduler | 常数时间调度，支持多处理器扩展 |
| Linux 2.6.23 | CFS | 引入公平调度思想 |
| Linux 6.6 起 | EEVDF 演进 | 在公平性基础上进一步考虑延迟与虚拟截止时间 |

### 早期 Linux 调度器

Linux 早期使用比较简单的调度算法。

随着系统中进程数量和 CPU 数量增加，原有调度器在性能和可扩展性方面逐渐暴露问题。

特别是当系统中存在大量可运行进程时，调度器需要考虑如何高效地完成进程选择。

### O(1) Scheduler

Linux 2.5 开发周期对调度器进行了重大改造，引入了 O(1) Scheduler。

O(1) 指的是调度器某些核心操作具有常数时间复杂度，不会随着可运行进程数量增加而线性增长。

其主要改进包括：

1. 使用优先级数组管理可运行进程。
2. 使用活动队列和过期队列管理时间片。
3. 通过位图快速定位具有可运行进程的优先级。
4. 为每个 CPU 设置独立运行队列（Per-CPU Runqueue）。

这些设计显著提高了调度器的可扩展性。

但是，O(1) Scheduler 也存在问题。

它虽然在大量服务器负载下表现不错，却在某些交互式负载下表现不理想。

例如，桌面环境中的文本编辑器、终端和图形界面程序需要快速响应用户操作。仅仅保证调度算法的执行效率，并不意味着能够保证良好的交互体验。

### CFS：Completely Fair Scheduler

为改善交互式任务的调度延迟，Linux 社区探索了其他调度方案。

其中，Rotating Staircase Deadline Scheduler（RSDL）引入了公平调度思想，对后来的 CFS 产生了重要影响。

Linux 2.6.23 正式引入 CFS，替代了原有的 O(1) 调度器。

CFS 的核心思想是：

**不再简单地为每个进程指定一个固定的绝对时间片，而是根据进程权重，动态分配其应该获得的 CPU 份额。**

后面将详细解释这一设计。

## 2.2 调度策略（Scheduling Policy）

调度策略决定在什么情况下应该运行哪个进程。

不同调度策略会直接影响系统的响应速度、吞吐量和资源分配公平性。

调度器需要平衡两个重要目标：

- 响应时间（Response Time / Latency）：任务从就绪到获得 CPU 的等待时间。
- 吞吐量（Throughput）：单位时间内系统完成的工作量。

这两个目标有时是冲突的。

例如：

- 如果频繁切换进程，交互式任务可能得到更快响应，但上下文切换开销增加。
- 如果让 CPU 密集型任务长时间运行，可以减少切换开销，但其他任务可能等待很久。

因此，调度器需要根据任务特征设计合适的策略。

## 2.3 I/O-Bound 与 Processor-Bound

根据进程使用 CPU 和等待 I/O 的行为，可以将进程大致分为两类。

### I/O-Bound Process（I/O 密集型进程）

I/O 密集型进程的大部分时间都在等待某种外部事件。

这里的 I/O 不仅包括磁盘读写，还包括：

- 键盘输入。
- 网络数据。
- 用户交互。
- 设备操作。
- 定时器事件。

例如文本编辑器：

```text
等待用户输入
      |
      v
用户按下键盘
      |
      v
处理输入
      |
      v
更新界面
      |
      v
再次等待用户输入
```

它只有在收到输入时才需要 CPU，大部分时间处于阻塞状态。

因此，I/O 密集型进程通常具有以下特征：

- CPU Burst 较短。
- 经常进入睡眠状态。
- 被唤醒后希望尽快获得 CPU。
- 对调度延迟比较敏感。

### Processor-Bound Process（CPU 密集型进程）

CPU 密集型进程的大部分时间都在执行计算，很少主动等待 I/O。

例如：

- 视频编码。
- 矩阵计算。
- 科学计算。
- 密码学运算。
- 大规模数据处理。

其典型特征：

- CPU Burst 较长。
- 很少主动阻塞。
- 只要获得 CPU，就倾向于持续运行。
- 对立即响应的要求相对较低。

### 两类进程的调度需求

| 对比 | I/O-Bound | Processor-Bound |
|---|---|---|
| CPU 使用特点 | 短时间运行 | 长时间运行 |
| 阻塞频率 | 较高 | 较低 |
| 响应延迟要求 | 高 | 相对低 |
| 典型场景 | 文本编辑器、网络服务 | 视频编码、科学计算 |
| 调度偏好 | 频繁获得 CPU | 尽可能持续运行 |

需要注意，这两类进程并不是绝对互斥的。

例如，文本编辑器平时等待用户输入，但在执行复杂拼写检查时，也可能短时间变成 CPU 密集型任务。

调度器需要适应进程行为的动态变化，而不是简单地给进程贴上永久标签。

## 2.4 进程优先级（Process Priority）

优先级调度是一种经典调度方式。

基本思想是：

- 优先级较高的进程具有更强的 CPU 竞争优势。
- 优先级相同的进程可以采用轮转方式调度。
- 某些调度器还会根据优先级分配不同长度的时间片。

Linux 提供两类重要的优先级机制：

1. Nice Value：普通进程的优先级控制。
2. Real-Time Priority：实时进程的优先级控制。

### Nice Value

Nice 值的范围是：

```text
-20 ~ +19
```

默认值为 0。

需要特别注意：**Nice 值越大，优先级越低。**

| Nice 值 | 优先级 |
|---:|---|
| -20 | 最高 |
| -10 | 较高 |
| 0 | 默认 |
| +10 | 较低 |
| +19 | 最低 |

之所以叫 Nice，是因为一个进程可以通过提高 Nice 值，降低自己与其他进程竞争 CPU 的优势。

例如：

```bash
# 以较低优先级启动进程
nice -n 10 ./program

# 修改已有进程的 nice 值
renice 10 -p 1234

# 查看进程优先级
ps -el
```

在 Linux 的公平调度机制中，Nice 值主要影响进程的 CPU 权重，而不是直接决定一个固定的运行时间。

### Real-Time Priority

实时进程使用另一套优先级体系。

在原书讨论的 Linux 2.6 环境中，实时优先级通常为：

```text
0 ~ 99
```

与 Nice 值不同，实时优先级越大，优先级越高。

实时任务的调度优先级高于普通任务。

例如：

```text
实时优先级 99
       |
实时优先级 80
       |
实时优先级 10
       |
普通进程 SCHED_NORMAL
       |
Idle
```

这里展示的是调度优先级的概念关系，并非所有现代调度类的完整内部优先级列表。

普通任务的 Nice 值和实时任务的优先级属于不同的用户接口，不能直接将二者的数值进行比较。

## 2.5 时间片（Timeslice）

时间片表示一个进程连续占用 CPU 的时间额度。

例如：

```text
CPU 时间轴：

|--- A ---|--- B ---|--- C ---|--- A ---|
   10ms      10ms      10ms      10ms
```

时间片机制能够避免某个进程无限期占用 CPU。

但是，时间片长度并不是越长越好，也不是越短越好。

**时间片太长：**

- 其他进程需要等待更久。
- 交互式任务的响应速度下降。
- 系统的并发体验变差。

**时间片太短：**

- 上下文切换次数增加。
- CPU 时间被切换开销消耗。
- Cache 局部性可能受到破坏。
- CPU 密集型任务难以持续利用缓存。

因此，调度器需要在响应延迟和切换开销之间进行权衡。

传统调度器通常会为不同优先级设置不同的时间片。

而 CFS 采用了不同的思路：它不直接给普通进程规定固定的绝对时间片，而是按照权重分配 CPU 时间比例。

# 三、Linux 调度算法：从传统 Unix 到 CFS

本章的核心是理解为什么 Linux 需要从传统的优先级与时间片模型，转向公平调度。

## 3.1 传统 Unix 系统中的进程调度

传统 Unix 调度器通常结合两个概念：

- Priority：进程优先级。
- Timeslice：进程一次可以运行的时间。

Nice 值被用来表达普通进程的优先级。

听起来非常自然：

优先级越高，进程获得的时间片越长，或者获得 CPU 的频率越高。

但这种设计存在一些问题。

### 问题一：绝对时间片导致切换行为不理想

假设我们设计如下规则：

| Nice 值 | 时间片 |
|---:|---:|
| 0 | 100ms |
| +20 | 5ms |

现在系统中只有两个可运行进程：

- A：Nice = 0，时间片 100ms。
- B：Nice = +20，时间片 5ms。

一个调度周期中：

\[
T=100+5=105ms
\]

A 获得 CPU 的比例：

\[
\frac{100}{105}\approx95.24\%
\]

B 获得 CPU 的比例：

\[
\frac{5}{105}\approx4.76\%
\]

从资源分配比例来看，这个结果是符合预期的。

但是，如果系统中只有两个 Nice = +20 的进程：

| 进程 | 时间片 |
|---|---:|
| B | 5ms |
| C | 5ms |

那么它们各自获得 50% CPU。

问题在于：

- 两个普通优先级进程，各自运行 100ms 后切换。
- 两个低优先级进程，各自运行 5ms 后切换。

也就是说，即使最终 CPU 份额相同，不同优先级进程组合却可能导致完全不同的上下文切换频率。

这很不理想。

尤其是低优先级进程通常是后台 CPU 密集型任务，它们可能更适合长时间运行，而不是频繁发生上下文切换。

### 问题二：Nice 值的相对变化不够合理

继续考虑 Nice 值与时间片的映射：

| Nice 值 | 时间片 |
|---:|---:|
| 0 | 100ms |
| 1 | 95ms |
| 18 | 10ms |
| 19 | 5ms |

比较两组情况：

第一组：

```text
Nice = 0  -> 100ms
Nice = 1  ->  95ms
```

时间片比例为：

\[
100:95
\]

第二组：

```text
Nice = 18 -> 10ms
Nice = 19 -> 5ms
```

时间片比例为：

\[
10:5
\]

虽然两组进程的 Nice 值都相差 1，但它们的 CPU 竞争优势变化完全不同。

这意味着 Nice 值每增加 1 所产生的影响，取决于进程原来的 Nice 值。

而 Nice 值在实际使用中往往是通过相对增量进行调整的，因此这种映射方式并不理想。

### 问题三：时间片受到系统时钟 Tick 粒度限制

传统调度器通常通过时钟中断进行时间记账。

例如：

```text
HZ = 100

每秒产生 100 次时钟 Tick

每个 Tick 的周期：

1 / 100 = 10ms
```

如果时间片通过 Tick 计数，那么时间片通常需要是 Tick 周期的整数倍。

这带来几个问题：

1. 最小时间片受到 Tick 周期限制。
2. 相邻 Nice 值对应的时间片差异受到 Tick 粒度限制。
3. 修改系统时钟频率可能改变时间片的实际粒度。

显然，这种设计不够灵活。

### 问题四：睡眠和唤醒机制可能被利用

为了改善交互式任务的响应速度，传统优先级调度器可能会对刚刚唤醒的任务进行优先级提升。

例如：

```text
进程 A 正在执行
       |
       v
进程 B 被唤醒
       |
       v
提升 B 的优先级
       |
       v
B 抢占 A
```

这有利于交互式任务。

但是，某些进程可能通过频繁睡眠和唤醒，反复获得额外的调度优势。

例如：

```text
运行一小段时间
      |
      v
主动睡眠
      |
      v
很快唤醒
      |
      v
重新获得优先级提升
      |
      v
重复
```

这种行为称为 Scheduler Gaming（调度器博弈）。

它可能导致某些进程获得不公平的 CPU 资源。

### 传统调度模型的根本问题

前面四个问题看起来各不相同，但它们指向同一个设计缺陷：

**传统调度器先为不同优先级指定绝对时间片，再通过这些时间片间接决定 CPU 资源分配比例。**

这种设计使时间片长度、Nice 值、系统负载和时钟粒度相互耦合。

作者由此引出 CFS 的核心思想：

不再直接为每个 Nice 值分配固定的绝对时间片，而是为每个进程分配 CPU 的相对份额。

## 3.2 公平调度（Fair Scheduling）

CFS 全称为 Completely Fair Scheduler。

它的核心思想是模拟一个理想的、可以完美并行执行多个任务的处理器。

### 理想的多任务处理器

假设系统中存在两个可运行进程：

- A
- B

在普通单核 CPU 上，我们只能交替运行它们：

```text
时间轴：

|---- A ----|---- B ----|---- A ----|---- B ----|
```

每个进程在自己运行时独占 CPU。

而在理想的完美多任务处理器上：

```text
时间轴：

A：================================
B：================================
```

两个进程可以同时运行，每个进程获得 50% 的处理器能力。

如果有 n 个相同优先级的可运行进程，那么理想情况下：

\[
CPU\ Share_i=\frac{1}{n}
\]

例如：

| 可运行进程数 | 每个进程获得的 CPU 份额 |
|---:|---:|
| 1 | 100% |
| 2 | 50% |
| 4 | 25% |
| 10 | 10% |

当然，真实的单核 CPU 无法真正做到无限细粒度的并行执行。

进程切换本身也有成本，包括：

- 保存和恢复执行上下文。
- 切换地址空间。
- Cache 局部性受到影响。
- 调度器自身的执行开销。

因此，CFS 并不是让进程无限频繁地切换，而是通过记录每个进程的运行情况，尽可能逼近理想的公平分配。

### 引入 Nice 权重

前面假设所有进程优先级相同。

如果优先级不同，就需要引入权重（Weight）。

Linux 为不同 Nice 值分配不同的权重。

权重越大，进程应该获得的 CPU 份额越多。

假设有三个进程：

| 进程 | Nice | Weight |
|---|---:|---:|
| A | 0 | 1024 |
| B | 5 | 335 |
| C | 5 | 335 |

总权重：

\[
W=1024+335+335=1694
\]

每个进程的 CPU 份额为：

\[
Share_i=\frac{w_i}{\sum_j w_j}
\]

因此：

\[
Share_A=\frac{1024}{1694}\approx60.45\%
\]

\[
Share_B=Share_C=\frac{335}{1694}\approx19.78\%
\]

这说明：

- A 获得约 60.45% 的 CPU。
- B 获得约 19.78% 的 CPU。
- C 获得约 19.78% 的 CPU。

这里有一个非常重要的认识：

**Nice 值影响的是 CPU 份额，而不是直接决定某个进程每次运行多少毫秒。**

而且，CPU 份额是相对于当前竞争的可运行实体而言的。

如果一个进程进入睡眠状态，它不再参与当前的 CPU 竞争，其他可运行进程就可以利用空闲出来的 CPU。

# 四、CFS 的实现原理

前面介绍了 CFS 的设计思想，现在进一步研究它如何在 Linux 内核中实现。

原书主要围绕四个方面展开：

1. Time Accounting：运行时间记账。
2. Process Selection：进程选择。
3. Scheduler Entry Point：调度器入口。
4. Sleeping and Waking Up：睡眠与唤醒。

## 4.1 Time Accounting：时间记账

传统调度器通常通过时间片记录进程运行时间。

例如：

```text
进程 A 的时间片：100ms

每次时钟 Tick：

timeslice -= TICK_PERIOD

当 timeslice == 0：

抢占进程 A
```

CFS 没有为普通任务使用传统意义上的固定时间片，但仍然必须记录每个进程实际运行了多长时间。

否则，调度器无法判断一个进程是否已经获得了应有的 CPU 份额。

为此，CFS 使用了 `struct sched_entity`。

## 4.2 Scheduler Entity Structure

在原书对应的 Linux 2.6 实现中，调度实体定义在 `<linux/sched.h>` 中。

简化后的结构如下：

```c
struct sched_entity {
    struct load_weight load;

    struct rb_node run_node;

    unsigned int on_rq;

    u64 exec_start;
    u64 sum_exec_runtime;
    u64 vruntime;
    u64 prev_sum_exec_runtime;
};
```

其中几个字段非常重要：

| 字段 | 含义 |
|---|---|
| `load` | 调度实体的权重信息 |
| `run_node` | 红黑树节点 |
| `on_rq` | 是否位于运行队列 |
| `exec_start` | 本次开始执行的时间 |
| `sum_exec_runtime` | 累计实际运行时间 |
| `vruntime` | 虚拟运行时间 |
| `prev_sum_exec_runtime` | 上一次记录的累计运行时间 |

`struct sched_entity` 嵌入在 `task_struct` 中，作为进程调度相关的数据结构。

因此：

```text
task_struct
    |
    +---- se (sched_entity)
              |
              +---- load
              |
              +---- run_node
              |
              +---- exec_start
              |
              +---- sum_exec_runtime
              |
              +---- vruntime
```

这体现了 Linux 内核一个重要的设计思想：

进程管理信息与调度信息分开组织，调度器通过调度实体访问任务的调度状态。

## 4.3 Virtual Runtime：虚拟运行时间

这是理解 CFS 最关键的概念。

`vruntime` 是对进程实际运行时间进行权重归一化后得到的虚拟运行时间。

它用于衡量进程相对于其应得 CPU 份额，已经获得了多少 CPU 资源。

简化公式：

\[
\Delta vruntime =
\Delta runtime \times
\frac{NICE\_0\_LOAD}{weight}
\]

其中：

- \(\Delta runtime\)：进程实际运行时间。
- \(weight\)：进程的调度权重。
- \(NICE\_0\_LOAD\)：默认 Nice 值对应的权重，通常为 1024。

注意：这是帮助理解的简化表达，内核实际使用整数运算和权重缩放函数完成计算。

### 为什么需要归一化？

假设存在两个进程：

| 进程 | Nice | Weight |
|---|---:|---:|
| A | 0 | 1024 |
| B | 5 | 335 |

现在两个进程实际运行时间都是 10ms。

对于 A：

\[
\Delta vruntime_A
=10\times\frac{1024}{1024}
=10ms
\]

对于 B：

\[
\Delta vruntime_B
=10\times\frac{1024}{335}
\approx30.57ms
\]

可以看到：

虽然两个进程实际运行时间相同，但 B 的虚拟运行时间增长更多。

原因是 B 的权重更低，理论上应该获得更少的 CPU 时间。

因此，相同的实际运行时间对低权重进程来说，意味着它消耗了更多相对于自身份额的 CPU 资源。

反过来说：

- 高权重进程：运行相同时间，vruntime 增长较慢。
- 低权重进程：运行相同时间，vruntime 增长较快。

调度器就可以通过比较 vruntime，判断哪个进程相对来说更应该获得 CPU。

### Ideal Multitasking Processor 与 vruntime

可以从理想处理器的角度理解 vruntime。

如果系统可以完美地让所有进程同时运行，那么相同权重的进程应该获得相同的虚拟运行进度。

但真实 CPU 只能交替运行进程。

于是，CFS 通过 `vruntime` 记录每个进程的运行进度，尽可能模拟理想处理器。

### vruntime 与 Timer Tick

还有一个重要细节：

`vruntime` 使用纳秒作为单位。

它并不依赖传统的系统时钟 Tick 作为计量粒度。

这意味着 CFS 能够更精细地记录进程运行时间，避免传统时间片模型中时间片必须依赖 Tick 整数倍的问题。

在原书对应的代码中，`update_curr()` 负责更新当前调度实体的运行时间。

简化逻辑如下：

```c
static void update_curr(struct cfs_rq *cfs_rq)
{
    struct sched_entity *curr = cfs_rq->curr;

    u64 now = rq_of(cfs_rq)->clock;
    unsigned long delta_exec;

    if (!curr)
        return;

    delta_exec = now - curr->exec_start;

    if (!delta_exec)
        return;

    __update_curr(cfs_rq, curr, delta_exec);

    curr->exec_start = now;
}
```

真正的关键在于：

```c
delta_exec_weighted = calc_delta_fair(delta_exec, curr);

curr->vruntime += delta_exec_weighted;
```

这段代码完成了：

1. 计算当前进程实际运行时间。
2. 根据权重归一化运行时间。
3. 更新当前进程的虚拟运行时间。

这样，调度器就能够持续掌握每个进程的 CPU 使用情况。

## 4.4 Process Selection：进程选择

理解了 vruntime，接下来就很容易理解 CFS 如何选择进程。

核心规则只有一句话：

**选择 vruntime 最小的可运行调度实体。**

为什么？

因为 vruntime 最小的进程，相对于自己的权重而言，获得的 CPU 资源最少，应该优先得到 CPU。

那么如何高效地找到 vruntime 最小的进程？

CFS 使用红黑树（Red-Black Tree）。

### 为什么使用红黑树？

假设有四个进程：

| 进程 | vruntime |
|---|---:|
| A | 10 |
| B | 20 |
| C | 30 |
| D | 40 |

可以按照 vruntime 将这些进程组织成一棵二叉搜索树：

```text
             B(20)
            /     \
        A(10)     C(30)
                      \
                      D(40)
```

在二叉搜索树中，最左边的节点具有最小的 key。

因此：

```text
最左节点 = vruntime 最小的进程
```

红黑树是一种自平衡二叉搜索树，能够保证树的高度为对数级别。

其基本操作复杂度为：

| 操作 | 时间复杂度 |
|---|---|
| 查找 | O(log N) |
| 插入 | O(log N) |
| 删除 | O(log N) |

在原书介绍的 CFS 实现中，内核还缓存了最左节点：

```c
struct rb_node *rb_leftmost;
```

这样选择最小 vruntime 的进程时，不需要每次重新遍历整棵树。

对应的核心函数是：

```c
static struct sched_entity *
__pick_next_entity(struct cfs_rq *cfs_rq)
{
    struct rb_node *left = cfs_rq->rb_leftmost;

    if (!left)
        return NULL;

    return rb_entry(left,
                    struct sched_entity,
                    run_node);
}
```

它的逻辑非常简单：

1. 获取缓存的最左节点。
2. 如果没有节点，说明没有可运行的公平调度实体。
3. 否则，将红黑树节点转换成 `sched_entity`。
4. 返回对应的调度实体。

### 进程如何加入红黑树？

当一个进程第一次创建并进入可运行状态，或者从睡眠状态被唤醒时，需要重新加入运行队列。

原书对应的函数包括：

```c
enqueue_entity()
__enqueue_entity()
```

主要工作：

1. 更新当前进程的运行时间。
2. 更新调度实体的相关统计信息。
3. 根据 vruntime 找到红黑树中的插入位置。
4. 插入红黑树。
5. 必要时更新最左节点缓存。

### 进程如何从红黑树删除？

当进程阻塞或者退出时，它不再参与当前 CPU 的公平调度。

对应的函数包括：

```c
dequeue_entity()
__dequeue_entity()
```

主要工作：

1. 更新当前运行时间。
2. 更新调度统计信息。
3. 从红黑树中删除对应节点。
4. 更新运行队列的统计信息。
5. 必要时更新 `min_vruntime`。

这里需要注意：

`min_vruntime` 是运行队列维护的虚拟运行时间基准，它用于维持运行实体的相对时间位置，并帮助处理任务唤醒、迁移等情况。

不要简单地把它理解为红黑树当前最左节点的 vruntime；二者在概念上相关，但不是同一个变量。

## 4.5 Scheduler Entry Point：调度器入口

上面介绍了 CFS 内部如何选择进程。

但内核中的其他子系统如何触发调度？

Linux 提供了一个重要的调度入口：

```c
schedule()
```

在原书对应的 Linux 2.6 实现中，`schedule()` 位于 `kernel/sched.c`。

它负责协调不同的调度类，并选择下一个运行的进程。

简化调用关系：

```text
schedule()
    |
    v
pick_next_task()
    |
    v
遍历调度类
    |
    +---- 实时调度类
    |
    +---- CFS 调度类
    |
    +---- Idle 调度类
    |
    v
选择下一个进程
    |
    v
context_switch()
```

这里引出了一个重要概念：Scheduler Classes。

### Scheduler Classes：调度类

Linux 使用模块化设计，让不同类型的进程采用不同的调度算法。

每个调度类负责管理特定类型的任务，并实现相应的调度操作。

原书介绍的主要调度类包括：

| 调度类 | 作用 |
|---|---|
| CFS | 普通任务 |
| Real-Time | 实时任务 |
| Idle | 空闲任务 |

每个调度类都有自己的优先级。

通用调度器按照调度类的优先级依次询问它们：

```text
最高优先级调度类
       |
       v
是否存在可运行进程？
       |
   +---+---+
   |       |
  有       无
   |       |
   v       v
选择任务  检查下一个调度类
```

一旦某个调度类返回了可运行任务，调度器就选择该任务。

这种设计的优点是：

- 不同调度策略可以独立实现。
- 可以支持普通任务和实时任务。
- 通用调度器不必了解每种算法的具体实现。
- 新的调度策略可以通过调度类机制接入。

这是一种典型的面向接口的模块化设计。

## 4.6 Sleeping and Waking Up：睡眠与唤醒

进程调度不仅仅是选择下一个进程，还必须处理进程什么时候退出运行队列，以及什么时候重新进入运行队列。

例如：

一个进程调用 `read()` 读取文件，但数据尚未准备好。

此时进程不能继续执行，必须等待事件发生。

Linux 通过等待队列（Wait Queue）管理这种等待关系。

### Wait Queue

等待队列是一个保存等待某个事件发生的任务的队列。

例如：

```text
磁盘数据尚未准备好

进程 A
   |
   v
加入等待队列
   |
   v
设置状态为 TASK_INTERRUPTIBLE
   |
   v
调用 schedule()
   |
   v
CPU 执行其他进程
```

等待的事件发生后：

```text
磁盘数据准备完成
       |
       v
调用 wake_up()
       |
       v
唤醒等待队列中的进程
       |
       v
进程状态变为 TASK_RUNNING
       |
       v
重新加入运行队列
```

需要注意：

`TASK_RUNNING` 在 Linux 中既可以表示正在运行，也可以表示可运行但正在等待 CPU。

它并不等同于进程此刻一定正在 CPU 上执行。

### 睡眠的基本流程

原书介绍了一种典型的等待队列使用模式：

```c
DEFINE_WAIT(wait);

add_wait_queue(q, &wait);

while (!condition) {
    prepare_to_wait(&q, &wait,
                    TASK_INTERRUPTIBLE);

    if (signal_pending(current))
        break;

    schedule();
}

finish_wait(&q, &wait);
```

理解这段代码需要注意几个细节：

1. `DEFINE_WAIT()`：创建等待队列项。
2. `add_wait_queue()`：将当前任务加入等待队列。
3. `prepare_to_wait()`：设置当前任务的睡眠状态，并确保其处于等待队列中。
4. `schedule()`：主动让出 CPU。
5. `finish_wait()`：结束等待，清理等待队列项。

为什么必须使用 `while` 检查条件，而不是简单使用 `if`？

因为可能发生两种情况：

**第一种：虚假唤醒（Spurious Wakeup）**

进程被唤醒，不代表它等待的事件一定已经发生。

因此，醒来之后必须重新检查条件。

**第二种：避免丢失唤醒（Lost Wakeup）**

假设进程刚刚检查完条件，事件就发生了，而进程随后才进入睡眠。

如果等待队列和状态设置的顺序不正确，就可能导致事件已经发生，进程却仍然睡眠。

因此，内核必须正确协调条件检查、等待队列登记和任务状态切换，避免竞态条件。

实际内核代码还需要根据具体场景使用适当的锁和内存顺序保证。

### 唤醒过程

唤醒通常通过：

```c
wake_up()
```

完成。

它会进一步调用相关的唤醒逻辑，使等待任务重新进入可运行状态。

简化过程：

```text
事件发生
   |
   v
wake_up()
   |
   v
try_to_wake_up()
   |
   v
设置 TASK_RUNNING
   |
   v
加入运行队列
   |
   v
必要时设置 need_resched
```

这里要注意：

**唤醒进程不意味着它立即开始执行。**

唤醒只意味着它重新具备了运行资格。

至于什么时候获得 CPU，还需要由调度器决定。

# 五、抢占与上下文切换

前面介绍了调度器如何选择下一个进程。

接下来需要回答：

内核如何从当前进程切换到下一个进程？

## 5.1 Context Switch

上下文切换（Context Switch）是从一个正在运行的任务切换到另一个任务的过程。

在原书介绍的 Linux 2.6 实现中，主要由：

```c
context_switch()
```

完成。

它主要执行两项工作。

### 1. 切换内存地址空间

```c
switch_mm()
```

当切换到使用不同地址空间的进程时，内核需要切换相应的内存映射上下文。

例如：

```text
进程 A
  |
  v
地址空间 A
  |
  v
切换到进程 B
  |
  v
地址空间 B
```

实际是否需要切换页表等底层状态，还取决于新旧任务是否共享地址空间以及体系结构的实现。

### 2. 切换处理器上下文

```c
switch_to()
```

它负责切换与任务执行相关的处理器状态，例如：

- 内核栈。
- CPU 寄存器。
- 指令执行上下文。
- 体系结构相关的其他状态。

可以将其理解为：

**保存旧任务的执行现场，恢复新任务上一次被暂停时的执行现场。**

因此，一个进程被切换出去之后，并不是从头开始执行，而是可以从之前暂停的位置继续执行。

## 5.2 need_resched：是否需要重新调度

内核什么时候应该调用 `schedule()`？

如果只在代码显式调用 `schedule()` 时才发生调度，那么一个始终不主动阻塞的用户进程可能长期占用 CPU。

因此，Linux 使用 `need_resched` 标志表示当前任务是否需要重新调度。

例如：

```text
进程 A 正在运行
       |
       v
时钟中断发生
       |
       v
scheduler_tick()
       |
       v
发现应该重新调度
       |
       v
设置 need_resched
       |
       v
到达安全调度点
       |
       v
调用 schedule()
```

此外，当更合适的任务被唤醒时，也可能设置该标志。

例如：

```text
进程 A 正在运行
       |
       v
高优先级进程 B 被唤醒
       |
       v
设置 need_resched
       |
       v
内核在合适时机重新调度
       |
       v
B 获得 CPU
```

`need_resched` 的作用是通知内核：

当前任务应该尽快让出 CPU，调度器需要重新选择任务。

它本身并不执行上下文切换。

## 5.3 User Preemption

用户态抢占比较容易理解。

当内核准备从系统调用或中断返回用户态时，会检查当前任务是否需要重新调度。

例如：

```text
用户态进程 A
       |
       v
发生时钟中断
       |
       v
进入内核处理中断
       |
       v
检查 need_resched
       |
       v
需要重新调度
       |
       v
schedule()
       |
       v
切换到进程 B
```

为什么选择在返回用户态时进行检查？

因为此时内核已经处于一个适合切换任务的安全边界。

## 5.4 Kernel Preemption

Linux 还有一个重要特点：内核本身也支持抢占。

这意味着进程即使正在执行内核代码，也可能被另一个任务抢占。

但并不是任何时候都可以抢占。

例如，当前进程正在持有自旋锁并访问共享数据结构，此时强行切换任务可能导致并发问题。

因此，Linux 使用 `preempt_count` 控制内核抢占。

其基本逻辑是：

```text
获取锁
  |
  v
preempt_count 增加
  |
  v
进入不可抢占区
  |
  v
执行临界区代码
  |
  v
释放锁
  |
  v
preempt_count 减少
  |
  v
可以抢占
```

当 `preempt_count` 为零时，内核代码处于可抢占状态。

如果此时：

```text
need_resched == 1
```

那么内核就可以在合适的时机执行重新调度。

原书介绍的内核抢占发生场景包括：

- 中断处理程序退出时。
- 内核代码重新变得可抢占时。
- 进程显式调用 `schedule()` 时。
- 进程在内核中阻塞时。

这里需要建立一个重要认识：

**抢占式内核不意味着内核代码可以在任意指令位置被无条件切换。锁、抢占计数和安全点共同保证内核并发执行的正确性。**

# 六、实时调度策略（Real-Time Scheduling Policies）

前面介绍的 CFS 面向普通任务。

但是，一些任务对执行时间有更严格的要求。

例如：

- 工业控制。
- 音视频处理。
- 机器人控制。
- 实时数据采集。

这些任务可能需要更明确的优先级和调度行为。

Linux 提供了实时调度策略。

原书主要介绍：

- `SCHED_FIFO`
- `SCHED_RR`

## 6.1 SCHED_FIFO

FIFO 是 First In, First Out。

它采用固定优先级的先进先出调度策略。

基本规则：

1. 实时任务优先级高于普通任务。
2. 高优先级实时任务可以抢占低优先级实时任务。
3. 相同优先级的 FIFO 任务按照队列顺序执行。
4. FIFO 任务没有普通意义上的时间片。
5. 任务会持续运行，直到主动阻塞、主动让出 CPU，或者被更高优先级任务抢占。

例如：

```text
实时任务 A：Priority 90
实时任务 B：Priority 80
普通任务 C：SCHED_NORMAL
```

如果 A 一直处于可运行状态，那么 B 和 C 都无法获得 CPU。

这也是 FIFO 使用时必须谨慎的原因：一个不主动阻塞的高优先级实时任务，可能让普通任务长期得不到执行机会。

## 6.2 SCHED_RR

RR 是 Round Robin。

它与 FIFO 非常相似，但增加了时间片机制。

例如：

```text
A：Priority 80
B：Priority 80
C：Priority 70
```

A 和 B 属于同一优先级。

当 A 的时间片耗尽时，调度器会让 B 运行。

但是，C 的优先级较低，即使 A 的时间片耗尽，C 也不能因此抢占 A 或 B。

因此：

**SCHED_RR 可以理解为带有时间片的实时 FIFO 调度。**

## 6.3 SCHED_FIFO 与 SCHED_RR 对比

| 特性 | SCHED_FIFO | SCHED_RR |
|---|---|---|
| 固定实时优先级 | 是 | 是 |
| 时间片 | 无 | 有 |
| 同优先级任务 | 按队列顺序执行 | 时间片轮转 |
| 高优先级任务抢占低优先级任务 | 支持 | 支持 |
| 低优先级任务抢占高优先级任务 | 不支持 | 不支持 |

## 6.4 Soft Real-Time 与 Hard Real-Time

这里还有一个容易混淆的概念。

Linux 的传统实时调度策略主要提供软实时能力（Soft Real-Time）。

软实时意味着：

系统尽可能满足任务的时间要求，但不能保证每次都严格在截止时间之前完成。

硬实时（Hard Real-Time）则要求：

在规定的系统假设和约束下，任务必须满足严格的时间截止要求，违反截止时间可能意味着系统失效。

因此：

- 使用 `SCHED_FIFO` 不代表系统就变成了硬实时系统。
- 使用 `SCHED_RR` 也不代表可以保证任务一定在截止时间前执行。

现代 Linux 还提供 `SCHED_DEADLINE`，使用 EDF（Earliest Deadline First）和 CBS（Constant Bandwidth Server）相关机制，为实时任务提供更明确的调度和带宽控制能力。

# 七、调度相关系统调用（Scheduler-Related System Calls）

Linux 提供了一系列系统调用，让用户程序能够查询和修改调度参数。

## 7.1 Nice 相关接口

```c
nice(int inc);
```

用于调整当前进程的 Nice 值。

命令行也可以使用：

```bash
nice -n 10 ./program
renice 5 -p 1234
```

注意，Nice 值越大，普通进程的 CPU 竞争权重越低。

## 7.2 调度策略相关接口

### sched_setscheduler()

设置进程的调度策略和优先级。

```c
int sched_setscheduler(
    pid_t pid,
    int policy,
    const struct sched_param *param
);
```

常见策略包括：

```c
SCHED_OTHER
SCHED_FIFO
SCHED_RR
```

现代 Linux 还提供其他调度策略。

### sched_getscheduler()

获取指定进程当前的调度策略。

```c
int sched_getscheduler(pid_t pid);
```

### sched_setparam()

设置进程的调度参数。

通常用于设置实时调度优先级。

### sched_getparam()

获取进程当前的调度参数。

## 7.3 CPU Affinity：处理器亲和性

Linux 允许用户限制一个进程可以在哪些 CPU 上运行。

相关接口：

```c
sched_setaffinity()
sched_getaffinity()
```

例如：

```bash
# 将进程限制在 CPU 0 和 CPU 1 上运行
taskset -c 0,1 ./program
```

为什么需要 CPU Affinity？

在多核系统中，进程迁移可能带来额外开销：

- Cache 数据可能不再命中。
- CPU 局部性受到影响。
- NUMA 系统可能访问远端内存。

因此，有些高性能应用会限制进程的 CPU 运行范围。

当然，CPU Affinity 也不是越严格越好。过度限制可能造成 CPU 负载不均衡。

## 7.4 sched_yield()

主动放弃当前 CPU。

```c
sched_yield();
```

它与 `schedule()` 不同：

- `schedule()` 是内核内部用于触发调度的函数。
- `sched_yield()` 是用户空间可调用的接口，用来主动让出 CPU。

# 八、本章知识串联：从进程就绪到上下文切换

学习完第四章后，应该能够把调度器各个部分串起来。

下面以一个进程等待 I/O，随后被唤醒为例。

```text
                  进程 A 正在运行
                         |
                         v
                   执行 read()
                         |
                         v
                  数据尚未准备好
                         |
                         v
                  设置睡眠状态
                         |
                         v
                  加入等待队列
                         |
                         v
                    schedule()
                         |
                         v
                  选择进程 B
                         |
                         v
                 context_switch()
                         |
                         v
                   进程 B 运行
                         |
                         |
                  I/O 操作完成
                         |
                         v
                     wake_up()
                         |
                         v
                  try_to_wake_up()
                         |
                         v
                  A 重新变为可运行
                         |
                         v
                    加入运行队列
                         |
                         v
                调度器重新评估任务
                         |
                         v
                 选择合适的进程
                         |
                         v
                  context_switch()
                         |
                         v
                 进程 A 恢复执行
```

需要区分三个不同的数据结构：

| 数据结构 | 作用 |
|---|---|
| Wait Queue | 管理等待某个事件的进程 |
| Runqueue | 管理可运行任务 |
| CFS Red-Black Tree | 在公平调度类中组织可运行调度实体 |

它们共同组成了进程从运行、阻塞、唤醒到重新获得 CPU 的完整流程。

# 九、从 LKD 过渡到现代 Linux：CFS 与 EEVDF

这里需要特别强调版本问题。

《Linux Kernel Development》第三版出版于 2010 年，主要讲解 Linux 2.6 时代的调度器实现。

书中介绍的 CFS 在 Linux 2.6.23 引入，是理解现代公平调度思想的重要基础。

但是，不能将原书中的代码直接视为现代 Linux 的完整实现。

Linux 6.6 开始引入 EEVDF（Earliest Eligible Virtual Deadline First），公平调度器逐步从传统 CFS 向 EEVDF 演进。

## 9.1 CFS 的局限与进一步演进

CFS 的基本策略是：

```text
根据权重更新 vruntime
          |
          v
选择 vruntime 最小的任务
          |
          v
运行任务
          |
          v
更新 vruntime
```

它很好地解决了按权重分配 CPU 份额的问题。

但在实际系统中，除了公平性，还需要考虑任务的延迟需求。

例如：

- 交互式任务希望尽快获得 CPU。
- 音频任务希望获得较短的调度延迟。
- 后台任务更关注吞吐量。

EEVDF 在公平调度基础上引入了两个关键概念：

**Lag（滞后量）**

表示任务实际获得的 CPU 时间与其应得 CPU 时间之间的差异。

- 正 Lag：任务还应该获得 CPU 时间。
- 负 Lag：任务已经获得了超过应得份额的 CPU 时间。

**Virtual Deadline（虚拟截止时间）**

在满足调度资格的任务中，根据虚拟截止时间选择下一个任务。

EEVDF 的核心过程可以概括为：

```text
计算任务的 Lag
       |
       v
判断任务是否具有调度资格
       |
       v
计算虚拟截止时间
       |
       v
选择最早虚拟截止时间的合格任务
       |
       v
运行任务
```

与 CFS 相比，EEVDF 在公平性之外，更明确地考虑了调度延迟和任务的时间需求。

它是理解现代 Linux 普通任务调度机制的重要入口。

# 十、本章总结

本章的核心并不是记住某几个调度函数，而是理解 Linux 调度器背后的设计思想。

可以将本章知识归纳为以下几个层次：

| 层次 | 核心概念 | 需要掌握的内容 |
|---|---|---|
| 多任务机制 | Cooperative / Preemptive | 为什么需要抢占 |
| 调度策略 | I/O-Bound / CPU-Bound | 响应延迟与吞吐量的权衡 |
| 优先级 | Nice / Real-Time Priority | 如何影响 CPU 竞争 |
| 公平调度 | CFS | 根据权重分配 CPU 份额 |
| 时间记账 | vruntime | 如何衡量进程获得的 CPU 资源 |
| 进程选择 | Red-Black Tree | 如何高效选择下一个进程 |
| 进程状态 | Wait Queue | 睡眠、唤醒与运行队列 |
| 调度执行 | schedule / context_switch | 如何完成任务切换 |
| 抢占机制 | need_resched / preempt_count | 何时可以重新调度 |
| 实时调度 | FIFO / RR | 如何支持固定优先级实时任务 |

建议重点记住以下五个问题：

1. 为什么传统 Unix 的绝对时间片分配方式存在问题？
2. 为什么 CFS 使用虚拟运行时间，而不是简单使用实际运行时间？
3. 为什么 CFS 选择 vruntime 最小的进程？
4. 为什么睡眠队列与运行队列必须分开管理？
5. 为什么 Linux 需要同时支持普通调度类和实时调度类？

如果能够清楚解释这五个问题，就基本掌握了本章的核心设计思想。

## 11.2 建议的实验

**实验一：观察 Nice 值对 CPU 份额的影响**

创建两个持续消耗 CPU 的进程：

```bash
nice -n 0 ./cpu_task &
nice -n 10 ./cpu_task &
```

观察它们的 CPU 使用情况。

可以使用：

```bash
top -H
ps -eo pid,ni,pri,psr,stat,comm
```

尝试改变 Nice 值，观察 CPU 竞争结果。

注意：实际结果会受到其他进程、CPU 核数、调度组和系统负载等因素影响。

**实验二：观察 CPU Affinity**

```bash
taskset -c 0 ./cpu_task
taskset -c 1 ./cpu_task
```

观察进程被限制在不同 CPU 上运行时的情况。

**实验三：观察上下文切换**

```bash
vmstat 1
```

重点观察：

- `r`：等待运行或正在运行的进程数。
- `b`：不可中断睡眠进程数。
- `cs`：每秒上下文切换次数。

还可以使用：

```bash
sudo perf sched record -- sleep 5
sudo perf sched timehist
```

观察调度延迟和进程切换情况。

**实验四：使用 ftrace 观察调度事件**

```bash
sudo trace-cmd record \
    -e sched:sched_switch \
    -e sched:sched_wakeup \
    sleep 5

sudo trace-cmd report
```

可以观察：

- 进程什么时候被唤醒。
- 进程什么时候发生上下文切换。
- 哪个进程被切出。
- 哪个进程被切入。

通过这些实验，可以把本章介绍的抽象调度流程与真实 Linux 内核行为联系起来。
