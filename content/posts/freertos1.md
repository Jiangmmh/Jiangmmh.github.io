# 一、FreeRTOS 是什么？

## 1.1 FreeRTOS 的基本介绍

FreeRTOS 是一套面向嵌入式系统的开源软件，主要由实时内核（Real-Time Kernel）以及一系列提供辅助功能的模块化软件库组成。

它最初由 Richard Barry 于 2003 年左右开发，后来由 Amazon Web Services（AWS）接手维护。FreeRTOS 使用 MIT 开源许可证，既可以用于个人项目，也可以用于商业产品。

FreeRTOS 的主要目标是为微控制器（MCU）和小型微处理器提供实时多任务处理能力。

在没有 RTOS 的传统裸机程序中，应用程序通常由一个主循环控制：

```c
int main(void)
{
    hardware_init();

    while (1) {
        read_sensor();
        process_data();
        update_display();
        handle_communication();
    }
}
```

这种方式也被称为 Super Loop（超级循环）或前后台系统。

当应用程序比较简单时，这种结构完全可行。但是，随着功能不断增加，系统可能同时需要：

- 周期性采集传感器数据。
- 实时响应外部事件。
- 更新显示界面。
- 处理通信协议。
- 执行控制算法。
- 管理设备状态。

如果所有功能都放在一个循环中，就需要开发者自行管理每个功能的执行时机、执行顺序以及等待时间。

例如，通信处理过程中如果需要等待数据，可能会影响传感器采集；如果某个功能执行时间过长，也可能导致其他功能错过执行时机。

FreeRTOS 通过引入任务（Task）和调度器（Scheduler），将应用程序组织成多个相对独立的执行单元，并由内核决定哪个任务获得 CPU 执行权。

可以将其理解为：

```text
                 Application
                      |
        +-------------+-------------+
        |             |             |
    Sensor Task   Control Task   Communication Task
        |             |             |
        +-------------+-------------+
                      |
                FreeRTOS Kernel
                      |
                  Hardware
```

每个任务负责一项相对独立的工作，任务之间通过内核提供的通信和同步机制协作。

需要注意：FreeRTOS 本身并不是一个完整的通用操作系统。它主要提供任务调度、同步、通信、定时器和内存管理等实时内核能力，具体的设备驱动、文件系统、网络协议栈等功能需要根据应用需求集成。

## 1.2 实时系统：Hard Real-Time 与 Soft Real-Time

理解实时操作系统，首先需要理解什么是实时性。

实时系统（Real-Time System）的核心并不是执行速度足够快，而是系统能否在规定的时间约束内完成任务。换句话说：

**实时系统不仅关心计算结果是否正确，还关心结果是否在规定时间内产生。**

按照时间约束被违反后的后果，通常可以将实时要求分成两类。

### 1.2.1 Soft Real-Time（软实时）

软实时系统有明确的时间要求，但偶尔错过截止时间并不会导致整个系统失效。

例如：

- 用户界面需要及时响应按键。
- 音视频系统需要尽量按时处理数据。
- 网络设备需要及时处理数据包。
- 显示系统需要定期刷新画面。

如果按键响应延迟，用户可能感觉系统卡顿，但设备仍然可以正常工作。

因此，软实时系统关注的是在大多数情况下满足时间要求，并尽可能降低延迟和抖动。

### 1.2.2 Hard Real-Time（硬实时）

硬实时系统具有严格的截止时间要求，一旦错过截止时间，就可能造成系统功能失效，甚至引发严重后果。

书中使用汽车安全气囊作为例子：

当碰撞传感器检测到事故时，气囊必须在规定时间内完成响应。如果处理过慢，气囊可能无法发挥应有的保护作用，甚至造成更严重的后果。

其他例子还包括：

- 飞行控制系统。
- 工业安全控制系统。
- 医疗设备中的关键控制功能。
- 汽车制动和安全控制系统。

硬实时并不意味着系统必须始终以最高速度运行，而是必须能够保证关键任务在规定的时间约束内完成。

### 1.2.3 实时性与优先级

FreeRTOS 内核通过任务优先级和调度机制，帮助应用程序满足不同任务的时间要求。

例如，一个单核处理器上存在三个任务：

| 任务     | 优先级 | 工作内容      |
| ------ | --: | --------- |
| Task A |   3 | 处理关键传感器事件 |
| Task B |   2 | 更新控制状态    |
| Task C |   1 | 输出日志      |

在抢占式调度模式下，如果 Task C 正在运行，此时 Task A 进入就绪状态，调度器可以让 Task A 抢占 Task C，优先获得 CPU。

这样，关键任务就不必等待低优先级任务主动让出处理器。

不过，需要特别注意：

**仅仅给关键任务分配更高优先级，并不能自动保证硬实时截止时间。**

真正的实时保证还需要考虑：

- 任务最坏执行时间（Worst-Case Execution Time，WCET）。
- 任务的周期和截止时间。
- 中断响应时间。
- 高优先级任务的干扰。
- 共享资源造成的阻塞。
- 优先级反转。
- 调度策略及系统负载。

因此，FreeRTOS 提供的是实现实时系统所需的内核机制，而最终能否满足硬实时要求，仍然取决于整个系统的设计与分析。

# 二、为什么需要 RTOS？

## 2.1 裸机编程是否足够？

并不是所有嵌入式项目都需要 RTOS。

如果系统功能简单，采用裸机编程通常更加合适。例如：

- 只需要读取一个传感器。
- 只需要控制几个 GPIO。
- 只需要执行简单的周期性任务。
- 不存在复杂的任务并发和同步需求。

此时，使用超级循环或者中断驱动方式，可能比引入 RTOS 更简单。

但随着系统复杂度提高，裸机程序会面临越来越多的问题：

1. 不同功能之间存在较强的时间依赖。
2. 某个功能的执行可能影响其他功能。
3. 事件处理逻辑越来越复杂。
4. 功能模块之间耦合度不断提高。
5. 系统难以维护、扩展和独立测试。

RTOS 的价值就在于通过任务抽象、调度机制和通信同步机制，将复杂应用拆分成更容易管理的模块。

是否采用 RTOS 没有绝对的复杂度分界线，需要根据项目需求、资源限制和维护成本综合判断。

## 2.2 RTOS 带来的主要好处

原书从多个角度解释了使用 RTOS 的价值。

### 2.2.1 抽象时间管理（Abstracting Away Timing Information）

在裸机程序中，开发者通常需要自行管理每个功能的执行时机。

例如：

```c
while (1) {
    if (sensor_timer_expired()) {
        read_sensor();
    }

    if (display_timer_expired()) {
        update_display();
    }

    if (communication_ready()) {
        handle_communication();
    }
}
```

随着功能增加，主循环中会出现大量定时判断、状态判断和事件处理逻辑。

使用 RTOS 后，可以将这些功能拆分为不同任务：

```c
void SensorTask(void *pvParameters)
{
    while (1) {
        read_sensor();
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void DisplayTask(void *pvParameters)
{
    while (1) {
        update_display();
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

每个任务通过 RTOS 提供的时间 API 管理自身的执行周期，不需要应用程序自己维护所有功能的时间调度逻辑。

这样可以降低模块之间的时间耦合，使应用程序结构更加清晰。

### 2.2.2 可维护性与可扩展性（Maintainability / Extensibility）

使用 RTOS 后，各个任务可以围绕明确的功能职责组织。

例如：

- 传感器任务只负责采集数据。
- 控制任务只负责计算控制量。
- 通信任务只负责收发数据。

任务之间通过 Queue、Semaphore 等机制交换信息，而不是直接依赖彼此的内部实现。

这种方式降低了模块间的耦合度。

当需要修改传感器采样周期时，通常只需要修改传感器任务，而不必重构整个主循环。

同时，内核负责提供统一的调度和时间管理机制，使应用程序更容易适应底层硬件的变化。

### 2.2.3 模块化（Modularity）

RTOS 的任务模型天然适合模块化设计。

每个任务应当具有：

- 明确的职责。
- 相对独立的执行逻辑。
- 清晰的输入和输出。
- 明确的任务间通信接口。

例如，一个机器人控制系统可以拆分为：

```text
                 Robot Application
                         |
       +-----------------+-----------------+
       |                 |                 |
   Sensor Task       Control Task      Network Task
       |                 |                 |
       +-----------------+-----------------+
                         |
                  FreeRTOS Kernel
```

每个任务承担不同职责，任务之间通过定义好的接口协作。

这使得系统更容易理解和扩展。

### 2.2.4 团队协作（Team Development）

模块化也有利于多人协作开发。

不同开发者可以负责不同任务，只要约定好任务之间的数据格式、通信接口和资源访问规则，就可以相对独立地进行开发。

例如：

- 开发者 A 负责传感器采集任务。
- 开发者 B 负责控制算法任务。
- 开发者 C 负责通信任务。

这种组织方式能够减少多人修改同一段代码造成的冲突。

### 2.2.5 更容易测试（Easier Testing）

任务具有明确职责和接口之后，可以针对单个任务进行独立测试。

例如，传感器任务的测试可以使用模拟数据替代真实硬件输入，验证其数据处理逻辑。

控制任务也可以独立输入测试数据，检查控制结果是否符合预期。

需要注意，任务的独立测试并不代表可以忽略任务间通信、并发访问和时序问题。这些仍然需要集成测试验证。

### 2.2.6 代码复用（Code Reuse）

模块职责越清晰，内部实现与外部依赖越少，代码就越容易在其他项目中复用。

例如，一个通用的传感器采集模块，可以通过抽象硬件接口适配不同型号的传感器。

RTOS 的任务和通信机制能够帮助开发者建立相对稳定的模块边界。

### 2.2.7 提高效率：事件驱动（Improved Efficiency）

RTOS 的另一个重要价值是支持事件驱动编程。

在裸机程序中，经常使用轮询（Polling）检查事件：

```c
while (1) {
    if (data_available()) {
        process_data();
    }
}
```

即使没有数据，CPU 仍然需要不断执行检查逻辑。

RTOS 可以让任务进入阻塞状态，等待事件发生。

例如：

```c
void ReceiverTask(void *pvParameters)
{
    uint8_t data;

    while (1) {
        if (xQueueReceive(xQueue, &data, portMAX_DELAY) == pdPASS) {
            process_data(data);
        }
    }
}
```

当队列中没有数据时，任务进入阻塞状态，不再占用 CPU 执行轮询。

当其他任务向队列发送数据时，接收任务可以被唤醒，继续处理数据。

这种方式减少了无效轮询，提高了处理器利用效率。

当然，RTOS 本身也有运行开销，例如：

- Tick 中断处理。
- 任务上下文切换。
- 调度器运行。
- 内核数据结构维护。

因此，RTOS 并不是没有成本的。实际项目需要在任务组织、响应时间和系统开销之间进行权衡。

### 2.2.8 空闲时间管理（Idle Time）

当没有应用任务需要执行时，FreeRTOS 会运行自动创建的 Idle Task（空闲任务）。

Idle Task 的主要职责包括：

- 处理已经删除任务的资源清理工作。
- 为应用程序提供空闲钩子函数执行机会。
- 在合适的条件下配合系统进入低功耗状态。

Idle Task 是理解 FreeRTOS 调度器的重要概念。

当没有其他就绪任务需要运行时，调度器会选择 Idle Task。

### 2.2.9 电源管理（Power Management）

嵌入式设备经常需要考虑功耗，尤其是电池供电的设备。

当系统没有任务需要执行时，可以利用空闲时间让处理器进入低功耗状态。

FreeRTOS 还支持 Tickless Idle（无节拍空闲）机制。

传统情况下，系统会周期性产生 Tick 中断，即使没有任务需要运行，处理器也可能被周期性唤醒。

Tickless Idle 可以在系统预计会空闲一段时间时，抑制不必要的周期性 Tick 中断，并根据具体移植层和硬件能力安排更长时间的低功耗等待。

其价值在于：

- 减少不必要的中断唤醒。
- 延长处理器处于低功耗状态的时间。
- 降低系统整体功耗。

具体的低功耗实现与 MCU 的定时器、时钟和睡眠机制密切相关。

### 2.2.10 灵活的中断处理（Flexible Interrupt Handling）

嵌入式系统需要响应大量外部事件，例如：

- UART 接收到数据。
- 定时器溢出。
- GPIO 输入发生变化。
- DMA 传输完成。
- 网络数据到达。

传统做法是在中断服务程序（ISR）中完成事件处理。

但是，如果 ISR 执行时间过长，会增加其他中断的响应延迟，也会影响系统实时性。

FreeRTOS 支持将中断处理拆分为两个部分：

1. ISR：完成必要的快速处理。
2. Task：完成剩余的复杂处理。

例如：

```text
       Hardware Event
              |
              v
             ISR
              |
       Notify a Task
              |
              v
       Processing Task
              |
       Process the Data
```

ISR 只负责读取必要的数据、清除中断状态，并通过信号量、任务通知或队列等机制唤醒任务。

后续复杂工作交给任务执行。

这种方式称为 Deferred Interrupt Processing（延迟中断处理）。

它能够缩短 ISR 的执行时间，让中断上下文保持简单。

### 2.2.11 混合处理需求（Mixed Processing Requirements）

实际嵌入式应用通常同时存在不同类型的工作：

| 工作类型   | 示例                |
| ------ | ----------------- |
| 周期性任务  | 每 10ms 采集一次传感器    |
| 连续任务   | 持续执行数据处理          |
| 事件驱动任务 | 收到 UART 数据后处理     |
| 硬实时任务  | 必须在严格截止时间前完成的控制任务 |
| 软实时任务  | 显示刷新、日志输出         |

RTOS 通过任务优先级、阻塞机制、中断处理和定时器等功能，为这些不同类型的工作提供统一的组织方式。

# 三、FreeRTOS Kernel 的主要功能

原书列举了 FreeRTOS Kernel 提供的标准功能。可以将它们按照用途归纳。

## 3.1 调度与任务管理

FreeRTOS 支持：

- 抢占式调度（Pre-emptive Scheduling）。
- 协作式调度（Co-operative Scheduling）。
- 可选的时间片调度（Time Slicing）。
- 灵活的任务优先级设置。

这些功能构成了 FreeRTOS 的核心。

任务调度决定了哪个任务能够获得 CPU 执行权；任务管理则负责创建、删除、挂起、恢复和延时等操作。

后续需要重点阅读 `tasks.c`。

## 3.2 任务通信与同步

FreeRTOS 提供多种任务间通信和同步机制：

| 机制                 | 主要用途          |
| ------------------ | ------------- |
| Queue              | 在任务之间传递数据     |
| Binary Semaphore   | 事件通知和任务同步     |
| Counting Semaphore | 计数型资源或事件管理    |
| Mutex              | 保护共享资源        |
| Recursive Mutex    | 支持同一任务递归获取互斥锁 |
| Task Notification  | 任务之间直接进行轻量级通知 |
| Event Group        | 使用多个事件位进行同步   |
| Stream Buffer      | 字节流传输         |
| Message Buffer     | 消息传输          |

这些机制解决的问题并不完全相同。

例如：

- Queue 更适合传递数据。
- Semaphore 更适合进行事件同步。
- Mutex 更适合保护共享资源。
- Event Group 更适合等待多个事件条件。
- Task Notification 更适合轻量级的一对一任务通知。

实际开发中需要根据通信模型选择合适的机制，而不是所有问题都使用 Queue。

## 3.3 定时器与钩子函数

FreeRTOS 还提供：

- Software Timer：软件定时器。
- Tick Hook：Tick 中断钩子函数。
- Idle Hook：空闲任务钩子函数。

软件定时器允许应用程序注册回调函数，在指定时间到达时执行。

Tick Hook 和 Idle Hook 则提供了在特定内核执行阶段运行应用代码的机会。

需要注意，钩子函数运行的上下文具有约束，不能随意调用可能阻塞的 API。

## 3.4 调试与运行状态分析

FreeRTOS 还支持：

- Stack Overflow Checking：栈溢出检测。
- Trace Macros：跟踪钩子。
- Task Run-Time Statistics：任务运行时间统计。

这些功能有助于分析任务执行情况、定位栈空间不足和排查系统问题。

## 3.5 内存管理

FreeRTOS 支持使用静态分配和动态分配创建内核对象。

例如：

- 创建任务时分配 TCB 和任务栈。
- 创建队列时分配队列控制结构和存储空间。
- 创建定时器时分配定时器控制结构。

应用程序可以根据配置选择静态分配、动态分配，或者两者结合。

这对于 RAM 资源有限的嵌入式设备非常重要。

## 3.6 其他高级功能

根据具体处理器架构和移植层，FreeRTOS 还可以支持：

- 中断嵌套。
- Tickless 低功耗模式。
- MPU 内存保护。
- 软件管理的中断栈。
- 静态和动态内存分配。

需要注意，并非所有功能都能在所有架构和移植端上使用。具体能力取决于硬件、编译器和 FreeRTOS Port。

# 四、FreeRTOS、OpenRTOS 与 SafeRTOS

原书还介绍了 FreeRTOS 相关产品和许可证。

## 4.1 FreeRTOS

FreeRTOS 使用 MIT 开源许可证。

其主要特点：

- 可以免费用于商业产品。
- 用户不需要公开自己的应用程序源代码。
- 用户保留自己应用程序的知识产权。
- 内核源码可以公开获取和修改。

这使得 FreeRTOS 能够被广泛应用于商业嵌入式设备。

实际产品开发时，仍然需要检查所使用的 FreeRTOS 版本、附加组件及第三方依赖各自的许可证要求。

## 4.2 OpenRTOS

OpenRTOS 是由第三方提供的商业授权产品，基于 FreeRTOS 提供商业许可和相关支持服务。

它与免费开源的 FreeRTOS 在使用授权和商业支持模式上有所区别。

## 4.3 SafeRTOS

SafeRTOS 与 FreeRTOS 具有相似的使用模型，但其开发过程更加注重安全相关标准所要求的工程实践、流程和验证。

它主要面向对功能安全有严格要求的嵌入式系统。

需要注意：使用 FreeRTOS 并不意味着产品自动满足功能安全标准。安全认证涉及系统设计、开发流程、验证和具体产品的整体证据链。

# 六、本章总结

第一章主要回答了三个问题：

1. FreeRTOS 是什么？
2. 为什么嵌入式系统需要 RTOS？
3. FreeRTOS 提供了哪些核心功能？

可以将本章的核心思想总结为：

**RTOS 的价值在于将复杂的嵌入式应用组织为多个相对独立的任务，由内核统一管理任务调度、时间、通信和同步，从而提高系统的模块化程度、可维护性和对实时需求的处理能力。**

但需要明确，RTOS 并不是所有嵌入式系统的必需品。简单系统使用裸机编程可能更加合适；复杂系统则可以通过 RTOS 降低时间管理和任务协作的复杂度。

对于 FreeRTOS，后续最值得掌握的核心知识包括：

- Task：任务抽象与任务管理。
- Scheduler：任务调度。
- Queue：任务间通信。
- Semaphore / Mutex：同步与互斥。
- Software Timer：软件定时器。
- Event Group：事件管理。
- Task Notification：轻量级任务通知。
- Memory Management：内存管理。

这些机制构成了 FreeRTOS 内核的主要功能，也是后续阅读源码的基础。
