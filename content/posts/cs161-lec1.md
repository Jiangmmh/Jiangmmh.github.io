# 教材阅读笔记

这是[教材](https://textbook.cs161.org/)第一章内容的笔记，主要介绍了13个安全原则。

## 1. **了解你的威胁模型**

> **威胁模型（threat model）** 是对攻击者身份及其所拥有资源的描述。
> 

攻击者攻击系统的原因多种多样，可能是金钱、政治、娱乐等等。有些攻击者毫无逻辑可言——他们只是想看世界毁灭。以你自身的人身安全为例。了解你的威胁模型，就意味着了解谁会以及为什么会攻击你

我们通常会对攻击者给出如下常见的假设：

1. 攻击者可以在无人察觉的情况下与您的系统进行交互，这意味着您可能无法总能在攻击者发动攻击之前检测到他们篡改您的系统。
2. 攻击者掌握了一些关于您系统的基本信息，例如操作系统、任何潜在的软件漏洞等等。
3. **攻击者坚持不懈，而且运气不错（不要有侥幸心理）**；例如，如果一次攻击成功的概率是百万分之一，那么攻击者就会尝试一百万次。
4. 攻击者愿意投入时间和资源进行攻击。
5. 攻击者可以协调跨多个系统的复杂攻击。攻击者不仅限于攻击单个设备，还可以同时攻击整个网络，或将多个攻击串联起来。
6. 任何系统都可能成为攻击目标。例如，一家赌场曾遭到黑客攻击，原因是其网络中的一个鱼缸温度计被入侵。

## 2. **考虑人为因素**

> 安全系统必须方便普通用户使用，因此在设计时必须考虑到人为因素。
> 

如果一个安全系统不好用、不人性化，无论它多么安全，最终都会无人问津。

如果某种方法能让用户的更方便使用，那他们总会找到办法来规避安全系统。

## 3. **安全即经济学**

> 经济学是一门研究**人们如何在资源有限的情况下做出选择**的社会科学。
> 

安全其实与经济学类似。没有任何系统能够完全抵御所有攻击，更高级别的安全通常需要投入更多资金，因此防御措施的预期收益应该与攻击的预期成本成正比。

这条原则的推论是：**你应该集中精力加固最薄弱的环节**。安全就像一条链条：**一个系统的安全性取决于它最薄弱的环节**。攻击者会选择阻力最小的路径，他们会攻击系统最薄弱的地方。在纱门上安装昂贵的高档防盗锁毫无意义；攻击者不会费力去撬锁，他们可以直接拆掉纱门走进去。

## 4. **如果无法预防，请进行检测**

> **预防**是指阻止攻击发生，**检测**是指获悉攻击已经发生，而**响应**是指对攻击采取应对措施。
> 

如果无法阻止攻击发生，至少应该能够知道攻击已经发生。一旦知道攻击已经发生，就应该找到应对方法，因为没有响应的检测毫无意义。

## 5. **纵深防御**

> **纵深防御**的关键思想是**将多种类型的防御措施分层叠加**，这样攻击者就必须突破所有防御才能成功攻击系统。
> 

纵深防御的一个例子是通过探测器的组合。假设你有两个探测器，D1和D2这两个探测器都有一定的误报率（并非实际安全漏洞的警报）和漏报率（未触发任何警报的安全漏洞）。一种使用方法是将这两个探测器并联，即任何一个探测器发出警报都会触发响应。这样可以提高误报率，降低漏报率。另一种方法是将探测器串联，即两个探测器都必须发出警报才能触发响应。在这种情况下，误报率会降低，而漏报率会升高。

## 6. **最小权限原则**

> 为了确保最佳安全，任何一方都应仅拥有履行其职责所需的最小权限。
> 

程序拥有的权限越少，即使将来遭受缓冲区溢出攻击，造成的损害也越小。

- Unix 在最小权限原则方面做得如何？答案是：非常糟糕。每个程序都会获得调用它的用户的所有权限。
- Windows表现如何？答案：同样糟糕。
- 移动设备在这方面做得更好。每个应用程序都运行在沙盒环境中，通常无法访问其他应用程序的数据。

## 7. **责任分离**

> 分散权限，避免任何个人或程序拥有绝对权力。要求在授予访问权限前必须获得多方批准。
> 

如果你需要保护一项高度敏感的行动，就应该要求多方合作来执行该行动，因为单方恶意行事的可能性比所有参与方都恶意行事并相互勾结的可能性要大得多。

## 8. 确保完全中介（Ensure Complete Mediation）

> 每一次对受保护资源的访问，都必须经过权限检查。
> 

执行访问控制策略时，必须检查对每一个对象的每一次访问。

这里有两个关键词：

- **Every access**（每一次访问）：不能只在登录时检查，也不能只检查第一次访问。读取、修改、删除等操作，都必须受到适当的访问控制。
- **Every object**（每一个对象）：不能只保护部分资源。文件、数据库记录、账户、API 资源等，都要纳入相应的权限控制范围。

## 9. **香农定律**

> 香农格言指出，攻击者了解他们正在攻击的系统。
> 

“隐蔽式安全”指的是依靠系统设计、算法或源代码的保密性来保障安全的系统。

**我们不应该依赖隐蔽性来保障安全，要始终假设攻击者了解你所使用系统的每一个细节。**

与此密切相关的原则是柯克霍夫原则，该原则指出，即使攻击者掌握了系统的所有内部细节，密码系统也应该保持安全。

## 10. **使用故障安全默认值**

> 选择具有“故障安全”功能的默认设置，在系统宕机时兼顾安全性和可用性。**确保即使安全机制失效或崩溃，系统仍会默认采用安全行为，而不是不安全行为**。
> 

## 11. **从一开始就将安全性融入设计**

> 在设计系统的开始就将安全性考虑到设计中。
> 

在应用程序已经完成规范、设计和实现之后，试图为其添加安全措施通常非常困难。向后兼容性往往尤其棘手，因为您可能不得不维护软件所有先前版本中最严重的安全漏洞。

## 12. Trusted Computing Base（TCB）

> 关键问题：如何选择一种架构，以降低系统出现缺陷的可能性，或者提高系统应对此类缺陷的能力？
> 

可信计算基（Trusted Computing Base，简称TCB）。在任何系统中，**可信计算基（TCB）**是指**系统中必须正确运行以确保实现系统安全的组件**。

**TCB设计原则**：

- **不可绕过（或完整性）**：必须没有办法通过绕过 TCB 来破坏系统安全。
- **防篡改（或安全性）**：TCB 应受到保护，免受任何人的篡改。例如，TCB 之外的系统其他部分不应能够修改 TCB 的代码或状态。必须维护 TCB 的完整性。
- **可验证性（或正确性）**：TCB 的正确性应该可以验证。这通常意味着 TCB 应该尽可能简单，因为验证任何具有相当复杂程度的子系统的正确性通常超出了现有技术水平。

**TCB 的优势**：TCB 的概念非常强大且实用，因为它允许一种原始但有效的模块化形式。它允许我们将系统分成两部分：安全关键部分（TCB）和其他所有部分。

安全并非易事。构建既安全又正确的系统并非易事。系统包含的内容越多，确保其安全性就越困难。如果我们能够识别出一个清晰的TCB（技术控制边界），那么我们就知道，只有TCB中的部分正确无误，系统才能安全。因此，在考虑安全性时，我们可以将精力集中在真正重要的地方。而且，如果TCB只占系统的一小部分，那么我们最终获得安全系统的概率就会大大提高：**我们依赖的系统部分越少，系统出现故障的可能性就越小。**

## 13. **TOCTTOU 漏洞**

> **TOCTTOU** 是计算机安全中非常重要的一类竞态条件漏洞。在检查某个条件时，条件成立；但是当你真正依据这个条件执行操作时，相关状态已经发生了变化。
> 

**TOCTTOU** 是 **Time Of Check To Time Of Use** 的缩写，即“从检查时到使用时”的漏洞。

```c
procedure withdraw(amount w) {
    // contact central server to get balance
    1. let b := balance
    2. if b < w, abort

    // contact central server to set the balance
    3. set balance := b - w
    4. give w dollars to the user
}
```

假设`withdraw`可以同时被调用（例如，在两台不同的ATM机上），并且假设攻击者能够以某种方式暂停其中一台ATM机上的操作。

假设你账户余额为 100 美元，你想取 100 美元。在第一台 ATM 机，假设你在第二步完成后暂停了取款程序。然后，你前往第二台 ATM 机，成功取走了 100 美元（此时你的账户余额应该为 0 美元）。之后，你回到第一台 ATM 机并恢复取款程序；由于账户余额检查在你从第二台 ATM 机取款之前已经完成，第一台 ATM 机仍然认为你的账户里有 100 美元，因此允许你再次取走 100 美元！所以，尽管你的银行账户最初只有 100 美元，最终你却有了 200 美元。
