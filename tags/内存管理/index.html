一、简介 RISC-V的支持 RISC-V 指令（包括用户指令和内核指令）操作的是虚拟地址。而机器的RAM则需要使用物理地址来访问。RISC-V 页表硬件通过将每个虚拟地址映射到一个物理地址，将这两种地址连接起来。 xv6使用RISC-V的Sv39模式，其仅使用64位虚拟地址中低39位。在该设置下： 每个页面为4KB，使用低12位地址索引 采用三级页表，每级页表使用9位，共剩余27位进行索引 RISC-V 的设计为虚拟地址和物理地址的扩展都预留了空间。如果需要更多虚拟地址空间，RISC-V 支持 Sv48 模式，即 48 位虚拟地址。 下面是页表项的构成，包括了上述的39位物理地址和低10位的标志位。 PTE_V：指示了该PTE是否存在 PTE_R、PTE_W、PTE_X：指示可读、可写和可执行权限 PTE_U：控制该页面是否可以被用户程序访问 PTE_G、PTE_A：暂时未使用 RSW：还剩下两个保留位，可以根据需要来使用 每当执行RISC-V的访存指令时，就需要执行上述地址转换过程。在xv6的进程被调度上CPU时，会将进程根页目录表的地址存放到当前CPU的控制寄存器 satp 中。 多级页表虽然节省内存，但是访问某个页面中的数据需要多次访问内存，为了尽可能避免从虚拟地址到物理地址转换过程中的访存开销，RISC-V硬件提供了TLB（Translation Look-aside Buffer）来缓存部分虚拟地址到物理地址到映射，其思想和Cache类似，都是通过局部性原理构建。 内核地址空间 xv6 启动时会创建一个单页表，用于描述内核的地址空间，具体的布局定义见kernel/memlayout.h。 QEMU 模拟一台计算机，该计算机包含从物理地址0x80000000开始，直至0x88000000 。 其中大部分页面都采用对等映射（对等映射）实现（虚拟地址 == 物理地址），只有少数几个内核虚拟页面没有直接映射： 跳转页（Trampoline）。它被映射到虚拟地址空间的顶部；用户页表也具有相同的映射关系。一个物理页（包含跳转代码）在内核的虚拟地址空间中被映射了两次：一次在虚拟地址空间的顶部，另一次是直接映射。 内核栈保护页。每个进程都有自己的内核栈，它映射到较高的内核虚拟地址，这样 xv6 可以在其下方留下一个未映射的保护页。保护页的页表项 (PTE) 无效（即PTE_V未设置），因此如果内核栈溢出，很可能会导致缺页错误，内核崩溃。如果没有保护页，溢出的栈会覆盖其他内核内存，导致运行异常。崩溃崩溃是更可取的。 二、物理内存源码分析 物理内存的初始化 在main()函数中，调用了kinit()函数来初始化物理内存子模块： void kinit() { initlock(&kmem.lock, "kmem"); freerange(end, (void *)PHYSTOP); } 其中调用了freerange()函数，传入两个参数end和PHYSTOP，前者在链接脚本中被定义，位于 .text, .rodata, .data, .bss段之后的位置。后者的值为0x88000000，表示物理地址顶部。 void freerange(void *pa_start, void *pa_end) { char *p; p = (char *)PGROUNDUP((uint64)pa_start); for (; p + PGSIZE <= (char *)pa_end; p += PGSIZE) { kfree(p); } } 其中通过反复调用kfree()构造出一个存储4KB物理页帧的freelist。 struct run { struct run *next; }; struct { struct spinlock lock; struct run *freelist; } kmem; // Free the page of physical memory pointed at by pa, // which normally should have been returned by a // call to kalloc(). 一、简介 动态内存管理 在 C++ 中，内存管理一直是一个重要而又容易出错的问题。理解智能指针之前，我们需要先回答一个问题：为什么程序需要动态内存？ 为什么需要动态内存？ 在程序中，我们经常需要创建对象。对于生命周期和数量都能够提前确定的对象，可以直接使用局部变量、全局变量或其他具有适当存储期的对象。然而，在很多实际场景中，程序无法在编译时确定所需对象的数量、具体类型，甚至无法确定对象应该在什么时候销毁。 动态内存管理正是为了解决这些问题而存在的。 1. 程序不知道自己需要多少对象 考虑一个读取用户输入并处理数据的程序： #include <iostream> #include <vector> int main() { int n; std::cin >> n; std::vector<int> data(n); for (int i = 0; i < n; ++i) { std::cin >> data[i]; } // 处理数据 } 程序在运行之前并不知道用户会输入多少个整数。数据量取决于运行时的输入，因此程序需要在运行时管理相应的存储空间。 这里使用 std::vector，它能够根据需要管理动态分配的内存。我们不必手动申请和释放底层存储空间。 需要注意的是，动态内存并不意味着必须显式调用 new。标准容器、字符串以及其他资源管理类型已经封装了大量动态内存管理工作。 2. 程序不知道所需对象的准确类型 在面向对象程序中，我们可能需要根据运行时的信息创建不同类型的对象。 例如，一个图形程序需要处理圆形和矩形： #include <memory> struct Shape { virtual ~Shape() = default; virtual void draw() = 0; }; struct Circle : Shape { void draw() override { // 绘制圆形 } }; struct Rectangle : Shape { void draw() override { // 绘制矩形 } }; std::unique_ptr<Shape> createShape(bool isCircle) { if (isCircle) { return std::make_unique<Circle>(); } return std::make_unique<Rectangle>(); } 调用者只需要知道自己获得了一个 Shape 对象，而不必提前确定其具体类型。 这类设计广泛存在于插件系统、图形界面、游戏引擎和各种基于多态的程序中。 不过，动态分配并不是实现多态的必要条件。这里使用动态对象，主要是为了让不同派生类型能够以统一的接口返回，并具有独立的生命周期。 3. 程序需要在多个对象之间共享数据 ...
