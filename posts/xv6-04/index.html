一、何为异常控制流#

1. 从普通控制流到异常控制流#

在学习操作系统之前，我们通常通过函数调用、条件分支、循环等机制理解程序的执行过程。 例如：

int add(int a, int b) {
    return a + b;
}

int main(void) {
    int result = add(1, 2);
    return result;
}

程序从 main() 开始执行，调用 add()，然后返回调用者。这种执行过程主要由程序自身的指令决定，我们可以称之为普通控制流。

然而，操作系统需要处理更多复杂的事件：

  • 用户程序希望读取文件，需要请求内核提供服务。
  • 网卡收到网络数据，需要通知 CPU 处理。
  • 磁盘完成 I/O 操作，需要唤醒等待中的进程。
  • 程序访问非法地址，需要由内核处理异常。
  • 定时器触发，需要操作系统获得运行机会，进行调度。

这些事件可能发生在程序执行过程中的任意时刻，不能完全依赖当前程序主动调用函数来处理。

因此，计算机提供了一套特殊的控制流转移机制：当特定事件发生时，CPU 暂停当前执行路径，转而进入相应的处理程序。处理完成后，CPU 可以恢复原来的执行过程，也可能终止当前程序或切换到其他进程。

这种由异常、陷入和中断等事件引发的控制流转移，称为异常控制流（Exceptional Control Flow，ECF）。

理解异常控制流，需要回答三个问题：

  1. 什么事件触发了控制流转移？
  2. CPU 如何找到处理程序，并切换到适当的执行环境？
  3. 处理完成后，如何恢复原来的执行过程？

在 xv6 中，系统调用和中断是理解这些机制的两个重要切入点。

2. 异常、陷入与中断#

严格来说，异常控制流是一个广义概念。RISC-V 架构使用 trap 描述导致控制权转移到更高特权级处理程序的一类事件，主要包括同步异常和中断。

2.1 同步异常#

同步异常由当前正在执行的指令直接引起，因此与程序执行位置存在明确的因果关系。

例如：

  • 执行 ecall，主动请求操作系统服务。
  • 执行非法指令。
  • 访问未映射的虚拟地址。
  • 违反内存访问权限。

同步异常的特点是：如果程序以相同状态重复执行到同一条指令，并且环境没有发生变化，那么通常会再次触发相同事件。

系统调用是其中一种特殊情况。用户程序执行 ecall 指令，主动请求从用户态进入内核态，因此也常被称为主动陷入。

2.2 中断#

中断通常由当前指令执行之外的事件引起，例如外部设备发出的中断请求。

典型场景包括：

  • UART 接收到新的输入数据。
  • 磁盘控制器完成一次 I/O 操作。
  • 网卡收到数据包。
  • 定时器到期。

中断的特点是：它通常与 CPU 当前执行的指令没有直接因果关系。即使 CPU 正在执行完全无关的计算，外部设备仍然可能产生中断。

因此，中断也常被称为被动陷入。

需要注意，这里的“主动”和“被动”是为了帮助理解控制流的触发方式，并不是 RISC-V 规范中的正式分类名称。

2.3 同步异常与异步中断的区别#

对比维度同步异常异步中断
触发来源当前执行的指令外部设备或定时器等事件
与指令的关系有直接因果关系通常没有直接因果关系
典型例子ecall、页故障、非法指令UART、磁盘、定时器中断
处理时机执行到相关指令时触发在满足中断条件时响应
返回行为取决于异常类型及处理结果通常在处理完成后继续执行

二者都可能导致 CPU 转移到内核处理程序，但具体的触发原因、返回地址和处理逻辑存在差异。

3. RISC-V 的特权级与陷入机制#

理解 xv6 的异常控制流，必须先了解 RISC-V 的特权级。

RISC-V 定义了不同的特权级，其中操作系统最关心的是：

  • U-mode（User Mode）：用户态，运行普通用户程序。
  • S-mode（Supervisor Mode）：监管者态，运行操作系统内核。
  • M-mode（Machine Mode）：机器态，拥有更高权限，通常负责底层固件和机器级初始化。

xv6-riscv 的主要设计是：用户程序运行在 U-mode，内核运行在 S-mode，而机器级初始化代码负责完成早期启动和必要的机器态配置。

用户程序不能随意执行只有高特权级才允许执行的操作。例如，它不能直接修改内核页表、任意访问设备寄存器，或直接控制 CPU 的特权级。

当用户程序需要内核服务时，就必须通过受控的入口进入内核。

3.1 关键的 CSR 寄存器#

RISC-V 通过一组控制状态寄存器（Control and Status Registers，CSR）保存陷入处理所需的信息。

以下是 xv6 中尤其重要的几个寄存器：

寄存器作用
stvec指定 S-mode 陷入时的入口地址
sepc保存发生陷入时需要记录的程序计数器
scause描述陷入的原因
sstatus保存监管者态状态信息，包括中断使能和特权级相关状态
stval保存与部分异常相关的附加信息，例如某些页故障中的故障地址
satp保存当前使用的地址转换模式及页表根地址

当 CPU 从 U-mode 陷入 S-mode 时，硬件会根据事件类型更新相应的 CSR，并根据 stvec 的配置转移控制流。

其中，scause 用于区分不同的陷入原因。例如：

  • 用户态执行 ecall：异常码为 8。
  • S-mode 收到外部中断：中断位为 1，异常码为 9。
  • S-mode 收到软件中断：中断位为 1，异常码为 1。

scause 的最高位用于区分中断和异常，其余位编码具体原因。实际编码宽度取决于 XLEN；xv6-riscv 使用 64 位架构，因此需要结合 64 位寄存器解释这些值。

3.2 硬件负责什么，软件负责什么？#

理解陷入机制时，一个常见误区是认为 CPU 会自动完成整个上下文切换。

实际上，硬件只完成一部分工作。

发生陷入时，硬件会：

  1. 记录必要的陷入状态，例如 sepc 和 scause。
  2. 更新特权级相关状态。
  3. 根据 stvec 转移到指定入口。

但是，硬件不会自动保存所有通用寄存器，也不会自动切换到内核页表，更不会自动执行完整的进程调度。

这些工作需要操作系统通过汇编和 C 代码完成。

这也是 xv6 中 trampoline.S、trap.c 和 kernelvec.S 等文件存在的原因。

4. xv6 中异常控制流的整体结构#

在 xv6 中，可以先把异常控制流概括为下面这张图：

                    用户程序（U-mode）
                           |
              +------------+------------+
              |                         |
         执行 ecall                外部中断到达
              |                         |
              +------------+------------+
                           |
                    CPU 进入 S-mode
                           |
                  trampoline / trap 入口
                           |
                        usertrap()
                           |
                  +--------+--------+
                  |                 |
              系统调用            中断处理
              syscall()          devintr()
                  |                 |
                  +--------+--------+
                           |
                   必要的调度与处理
                           |
                       usertrapret()
                           |
                       userret
                           |
                    返回用户态执行

这张图展示的是从用户态发生陷入时的主要路径。内核态运行过程中发生的中断或异常，则通常通过 kernelvec 进入 kerneltrap()，与用户态陷入的入口有所不同。

接下来，我们分别分析系统调用和外部中断的源码。

二、xv6 的系统调用源码分析#

1. 为什么需要系统调用？#

操作系统需要为用户程序提供受保护的服务，例如：

  • read()：读取文件或设备。
  • write()：写入文件或设备。
  • fork()：创建进程。
  • exec()：加载并执行新程序。
  • sbrk()：调整进程的内存空间。
  • exit()：终止进程。

如果允许用户程序直接执行所有内核操作，那么用户程序就可能破坏其他进程的数据、修改内核状态，或者直接控制硬件。

因此，操作系统将这些操作放在内核中，并通过系统调用暴露有限的接口。

从程序员的角度看，系统调用通常表现得像一个普通函数：

int fd = open("README", 0);

但它与普通函数调用存在本质区别。

普通函数调用主要通过 call、ret 等指令完成控制流转移；系统调用则需要通过特殊指令跨越特权级边界，并由内核验证参数、执行操作，然后返回结果。

2. 从用户程序到 ecall#

以 xv6 中的 write() 为例。

用户程序调用：

write(fd, buf, n);

这看起来像普通的 C 函数调用，但用户程序链接的 write() 通常不是内核里的 sys_write()，而是用户态的系统调用封装函数。

在 xv6 的 user/usys.S 中，可以看到类似这样的汇编代码：

.global write
write:
    li a7, SYS_write
    ecall
    ret

这里有两个关键操作。

第一，li a7, SYS_write 将系统调用编号放入 a7 寄存器。

第二，ecall 指令触发环境调用异常，使 CPU 从 U-mode 进入 S-mode。

RISC-V 的调用约定使用 a0 到 a7 等寄存器传递参数和返回值。xv6 约定：

  • a7：系统调用编号。
  • a0 到 a5：最多六个系统调用参数。
  • a0：系统调用返回值。

例如，write(fd, buf, n) 的参数通过 a0、a1、a2 传递，而 a7 存放 SYS_write。

需要注意，ecall 并不直接跳转到 sys_write()。它只触发陷入，后续的入口处理和系统调用分发都由内核完成。

3. trampoline.S：进入内核的第一站#

用户程序执行 ecall 后，CPU 进入 S-mode，并跳转到 stvec 指定的地址。

在 xv6 的用户态陷入路径中，stvec 被设置为 uservec，其实现位于：

kernel/trampoline.S

为什么需要一个专门的 trampoline？

因为发生用户态陷入时，CPU 仍然使用用户页表。即使特权级已经切换到 S-mode，页表也不会因此自动切换。

这意味着内核不能简单地假设所有内核虚拟地址都已经可以访问。

xv6 使用 trampoline 页面解决这一问题：同一段特殊汇编代码被映射到用户页表和内核页表中的相同虚拟地址，使得 CPU 可以在切换页表的过程中继续执行这段代码。

uservec 的主要工作包括：

  1. 保存用户态通用寄存器。
  2. 获取当前进程的 trapframe。
  3. 保存用户程序的寄存器状态。
  4. 从 trapframe 中获取内核页表、内核栈和 usertrap() 的入口地址。
  5. 切换到内核页表。
  6. 跳转到 usertrap()。

trapframe 是内核保存用户态执行现场的重要数据结构。它让内核能够在处理完系统调用或中断后恢复用户程序的寄存器状态。

这里需要注意：切换特权级并不等于切换页表，保存用户寄存器也不等于切换进程。 这几个动作相互关联，但各自承担不同职责。

4. usertrap()：识别陷入原因#

进入 C 语言内核代码后，控制流来到 kernel/trap.c 中的 usertrap()。

不同版本的 xv6 可能存在细节差异，但其核心逻辑可以概括为：

void
usertrap(void)
{
    // 当前必须处于 S-mode。
    // 将后续陷入入口切换为内核态入口。
    w_stvec((uint64)kernelvec);

    struct proc *p = myproc();

    // 保存发生陷入时的用户程序计数器。
    p->trapframe->epc = r_sepc();

    uint64 cause = r_scause();

    if (cause == 8) {
        // 用户态执行 ecall。
        // ecall 返回后应继续执行下一条指令。
        p->trapframe->epc += 4;

        intr_on();
        syscall();
    } else if ((cause & 0x8000000000000000L) != 0) {
        // 中断。
        if (devintr() == 0) {
            // 未识别的中断。
            // 具体处理逻辑依版本而定。
        }
    } else {
        // 其他异常。
        // 通常需要记录错误并终止进程。
    }

    // 根据进程状态决定是否调度，
    // 最终准备返回用户态。
    usertrapret();
}

上面是为了说明核心流程而整理的示意代码，并不是可直接替换整个文件的完整实现。

首先，usertrap() 会将 stvec 切换为 kernelvec。这是因为内核开始运行后，如果再次发生陷入，就需要使用内核态的陷入入口，而不是再次进入用户态入口。

然后，内核读取 scause，判断陷入原因。

如果 scause == 8，说明用户程序执行了 ecall。在调用系统调用分发器之前，xv6 将保存的用户程序计数器加 4。

为什么是 4？

因为 RISC-V 的 ecall 指令长度为 4 字节。这里希望系统调用返回后，从 ecall 的下一条指令继续执行，而不是再次执行同一条 ecall。

接下来，syscall() 才真正负责系统调用分发。

5. syscall()：系统调用分发器#

在 kernel/syscall.c 中，xv6 维护一个系统调用处理函数表，结构大致如下：

static uint64 (*syscalls[])(void) = {
    [SYS_fork]   sys_fork,
    [SYS_exit]   sys_exit,
    [SYS_wait]   sys_wait,
    [SYS_read]   sys_read,
    [SYS_write]  sys_write,
    // ...
};

这张表建立了系统调用编号与内核实现之间的映射关系。

分发器读取 a7 中的系统调用编号，根据编号调用相应的内核函数。

其核心逻辑可以概括为：

void
syscall(void)
{
    struct proc *p = myproc();

    int num = p->trapframe->a7;

    if (num > 0 &&
        num < NELEM(syscalls) &&
        syscalls[num]) {
        p->trapframe->a0 = syscalls[num]();
    } else {
        p->trapframe->a0 = -1;
    }
}

这里最值得注意的是：

p->trapframe->a0 = syscalls[num]();

内核函数的返回值被写入 trapframe 中保存的 a0。当后续返回用户态时，这个值会恢复到用户程序的 a0 寄存器中，成为系统调用的返回值。

例如，write() 最终可能进入 sys_write()，再调用文件系统或设备驱动相关的函数，完成实际写入操作。

整个过程可以总结为：

用户态 write()
    |
    v
usys.S 中的 write
    |
    | a7 = SYS_write
    | ecall
    v
uservec
    |
    v
usertrap
    |
    v
syscall
    |
    v
sys_write
    |
    v
文件系统 / 设备驱动
    |
    v
返回值写入 trapframe->a0

这也说明，系统调用不仅是一次特权级切换，还涉及参数传递、权限边界、内核功能分发和返回值传递。

6. 系统调用参数是如何获取的？#

内核不能简单地把用户程序传入的指针当作内核指针直接使用。

例如：

write(fd, buf, n);

其中 buf 是用户虚拟地址。内核需要确认用户提供的地址有效，并以安全的方式访问对应的数据。

xv6 在 kernel/syscall.c 中提供了参数读取辅助函数，例如：

argint(0, &fd);
argaddr(1, &addr);
argint(2, &n);

这些函数负责从保存的用户寄存器中获取系统调用参数。

但要区分两件事：

  • argaddr() 读取并返回一个用户虚拟地址。
  • copyin()、copyout() 等函数负责在内核和用户地址空间之间安全地复制数据。

读取到一个用户地址，不代表这个地址已经被验证为可安全访问。

例如，内核不能直接执行：

char c = *(char *)addr;

并假定这个操作一定安全。用户指针可能未映射、越界，或者指向不可读的内存。

因此，在 sys_read()、sys_write() 等系统调用中，通常会通过 copyin() 或 copyout() 等机制处理用户内存访问。

这一设计体现了操作系统中的一个核心原则：用户程序提供的数据必须经过适当检查，才能被内核使用。

7. usertrapret()：返回用户态#

系统调用处理完成后，控制流回到 usertrap()，随后进入 usertrapret()，为返回用户态做准备。

它的主要工作包括：

  1. 关闭适当的中断，避免在返回现场尚未准备好时发生不合适的陷入。
  2. 将 stvec 重新设置为 uservec。
  3. 更新 trapframe 中返回用户态所需的信息。
  4. 设置 sstatus 中与返回特权级和中断使能有关的状态。
  5. 设置 sepc 为用户程序下一条需要执行的指令地址。
  6. 跳转到 trampoline 中的 userret。

随后，userret 切换回用户页表，并恢复用户态寄存器，最终执行 sret 返回 U-mode。

可以把完整过程总结为：

用户程序
   |
   | ecall
   v
uservec                 trampoline.S
   |
   | 保存用户寄存器、切换页表
   v
usertrap                trap.c
   |
   v
syscall                 syscall.c
   |
   v
sys_write               sysproc.c / sysfile.c 等
   |
   | 返回结果
   v
usertrapret             trap.c
   |
   v
userret                 trampoline.S
   |
   | 恢复寄存器、切换页表、sret
   v
用户程序继续执行

实际文件归属取决于具体系统调用。例如，sys_write() 在常见的 xv6-riscv 版本中位于 kernel/sysfile.c，而进程相关系统调用通常位于 kernel/sysproc.c。

至此，一次系统调用的完整控制流就串联起来了。

三、xv6 的外部中断源码分析#

1. 为什么需要外部中断？#

系统调用由正在执行的程序主动触发，而外部中断则通常由设备异步触发。

假设用户程序正在执行：

while (1) {
    compute();
}

此时 UART 收到一个字符，或者磁盘完成一次读操作。CPU 不可能要求当前程序先执行某个函数来报告这些事件，因为当前程序可能根本不知道事件已经发生。

因此，硬件提供中断机制，让设备在需要 CPU 处理时发出中断请求。

不过，中断请求不意味着 CPU 会立刻执行对应设备的驱动程序。CPU 需要在允许中断、当前执行状态适当等条件下响应请求，再由内核识别中断原因并分派给相应的处理程序。

xv6 中外部中断的主要路径涉及：

  • kernel/trap.c：识别中断并调用 devintr()。
  • kernel/kernelvec.S：处理内核执行期间发生的陷入。
  • kernel/plic.c：与平台级中断控制器交互。
  • kernel/uart.c：处理 UART 设备中断。
  • kernel/virtio_disk.c：处理 VirtIO 磁盘中断。

2. RISC-V 外部中断的基本机制#

RISC-V 的外部中断通常通过平台级中断控制器（Platform-Level Interrupt Controller，PLIC）等平台组件传递给 CPU。

以 xv6 常见的 QEMU virt 平台为例，PLIC 负责管理 UART、VirtIO 磁盘等设备的外部中断。

当设备需要 CPU 处理时，大致会发生以下过程：

  1. 设备产生中断请求。
  2. PLIC 根据优先级、使能状态和目标 hart 的配置，决定是否向 CPU 发送中断。
  3. CPU 在满足中断响应条件时接受中断。
  4. CPU 根据当前特权级和陷入向量配置转移到相应入口。
  5. 内核读取中断原因，并向 PLIC 查询具体设备。
  6. 内核调用对应的设备中断处理函数。
  7. 处理结束后，内核通知 PLIC 当前中断已经完成。

这里需要区分两个层次：

  • scause 告诉内核 CPU 收到的是哪一类中断。
  • PLIC 的 claim 操作告诉内核具体是哪一个外部设备提出了中断请求。

CPU 本身并不会仅凭一个通用的外部中断异常码就知道发生中断的是 UART 还是磁盘。

3. 从 usertrap() 进入 devintr()#

当外部中断发生在用户程序运行期间时，CPU 从 U-mode 进入 S-mode，随后经过 uservec 进入 usertrap()。

在 usertrap() 中，内核检查 scause。如果最高位为 1，说明这是中断；随后调用 devintr()，识别具体中断类型。

xv6 的 kernel/trap.c 中，外部中断处理逻辑大致如下：

int
devintr(void)
{
    uint64 scause = r_scause();

    if (scause == 0x8000000000000009L) {
        // S-mode 外部中断。
        int irq = plic_claim();

        if (irq == UART0_IRQ) {
            uartintr();
        } else if (irq == VIRTIO0_IRQ) {
            virtio_disk_intr();
        } else if (irq != 0) {
            // 未知设备中断。
        }

        if (irq != 0)
            plic_complete(irq);

        return 1;
    }

    // 其他类型的中断或异常由相应逻辑处理。
    return 0;
}

这是为了说明处理过程而整理的示意代码，实际版本还可能包含定时器中断等分支。

在 RV64 中，0x8000000000000009 表示 S-mode 外部中断：最高位表示这是中断，低位异常码为 9。

接下来，内核调用：

int irq = plic_claim();

PLIC 返回当前需要服务的中断编号。

然后，内核根据中断编号分派处理函数：

if (irq == UART0_IRQ) {
    uartintr();
} else if (irq == VIRTIO0_IRQ) {
    virtio_disk_intr();
}

UART 和 VirtIO 磁盘分别由不同的驱动程序处理。这是典型的中断分派机制：底层中断入口负责识别中断来源，再由设备驱动执行具体操作。

4. PLIC 的 claim 和 complete#

理解 xv6 外部中断处理时，plic_claim() 和 plic_complete() 是两个重要函数。

4.1 Claim：认领中断#

PLIC 可能同时管理多个设备的中断请求。CPU 收到外部中断后，需要知道究竟应该处理哪个设备。

plic_claim() 会从 PLIC 的 claim/complete 寄存器读取中断编号，并认领相应的中断。

如果返回值为 0，通常意味着当前没有可认领的中断。

4.2 Complete：通知处理完成#

设备中断处理完毕后，内核需要通过 plic_complete(irq) 通知 PLIC：编号为 irq 的中断已经完成处理。

在常见的 xv6 实现中，这两个函数在 kernel/plic.c 中实现，通过访问 PLIC 的内存映射寄存器完成操作。

完整过程如下：

设备产生中断
     |
     v
PLIC 向 CPU 发出外部中断
     |
     v
CPU 进入 S-mode
     |
     v
devintr()
     |
     v
plic_claim()
     |
     +------ UART 中断 ------> uartintr()
     |
     +------ 磁盘中断 -------> virtio_disk_intr()
     |
     v
plic_complete(irq)
     |
     v
返回后续执行路径

为什么需要 claim 和 complete 两个步骤？

因为中断控制器不仅需要把设备请求通知给 CPU，还需要维护中断请求的服务状态。完成通知让控制器知道内核已经处理了相应请求，从而继续按照中断控制器的规则管理后续请求。

需要注意，plic_complete() 并不等价于设备驱动已经处理完所有业务，也不保证设备此后不会再次产生中断。它只是中断控制器协议中的一个必要环节。

5. UART 中断：从硬件输入到内核处理#

UART 是 xv6 中比较容易理解的外部中断来源。

例如，用户在 QEMU 控制台输入一个字符。UART 接收到字符后，可以通过中断通知 CPU：当前有输入数据需要处理。

在 xv6 中，UART 驱动位于：

kernel/uart.c

当 devintr() 识别出 UART0_IRQ 时，会调用：

uartintr();

UART 中断处理程序负责从 UART 接收数据，并将数据交给内核的控制台输入逻辑。

典型路径是：

用户输入字符
      |
      v
UART 接收寄存器中出现数据
      |
      v
UART 产生中断请求
      |
      v
PLIC 通知 CPU
      |
      v
devintr()
      |
      v
uartintr()
      |
      v
consoleintr()
      |
      v
内核控制台输入缓冲区

具体函数的细节应以你正在学习的 xv6 版本为准，但这条路径揭示了一个重要事实：设备中断处理程序通常不是直接执行用户程序，而是将设备事件转化为内核可以管理的状态变化。

例如，输入字符进入控制台缓冲区后，等待输入的进程可能才有机会继续运行。

这就把中断机制与进程调度、睡眠和唤醒机制联系起来了。

6. VirtIO 磁盘中断：I/O 完成后的通知#

再看一个更能体现并发与同步机制的例子：磁盘 I/O。

假设内核发起一次磁盘读操作。磁盘设备的处理并不一定会在当前函数调用中立即完成，内核可以提交请求，然后等待设备完成。

当 VirtIO 磁盘完成请求后，会产生中断，通知 CPU 处理完成事件。

在 xv6 中，相关驱动代码位于：

kernel/virtio_disk.c

devintr() 识别 VIRTIO0_IRQ 后，会调用：

virtio_disk_intr();

驱动程序会检查设备队列中的完成信息，并更新对应请求的状态。

一个简化的执行路径如下：

内核提交磁盘请求
        |
        v
VirtIO 设备处理请求
        |
        | 设备异步完成
        v
产生外部中断
        |
        v
devintr()
        |
        v
virtio_disk_intr()
        |
        v
更新请求状态、唤醒等待者
        |
        v
等待 I/O 的内核执行路径继续

这里最值得关注的是：中断处理与发起 I/O 的代码可能不在同一条执行路径上。

发起请求的代码可能在某个进程的上下文中运行，而设备完成请求时，CPU 可能正在执行另一个进程的代码。中断处理程序需要通过共享数据结构，将设备完成的事实传递给等待者。

这正是操作系统并发问题的一个典型来源。

7. 中断、睡眠与锁：并发从哪里产生？#

中断机制不仅涉及控制流转移，还直接影响内核的同步设计。

考虑一个简化场景：

  1. 进程 A 发起磁盘 I/O。
  2. 进程 A 等待请求完成。
  3. CPU 调度进程 B 运行。
  4. 磁盘完成请求，触发中断。
  5. 中断处理程序更新请求状态，并唤醒等待者。
  6. 进程 A 之后获得运行机会，继续执行。

在这个过程中，不同执行路径可能访问同一份共享状态，例如磁盘请求队列、缓冲区状态或等待队列。

如果没有适当的同步机制，就可能出现竞态条件。

例如，假设请求状态由一个变量表示：

struct request {
    int done;
};

发起请求的代码可能检查 done，而中断处理程序可能修改它。如果双方在没有同步的情况下并发访问相关状态，就可能出现错误的判断或状态转换。

因此，内核需要使用锁、睡眠与唤醒协议，以及适当的内存访问规则，保证共享状态的一致性。

7.1 为什么锁和中断有关系？#

假设某段内核代码持有一个自旋锁，而中断处理程序也可能尝试获取同一把锁。

如果 CPU 在持锁期间接收中断，进入中断处理程序后又尝试获取这把锁，那么就可能发生死锁：

普通内核代码：
    获取锁
       |
       v
    被中断
       |
       v
中断处理程序：
    尝试获取同一把锁
       |
       v
    一直等待锁释放

但锁的持有者无法继续执行，
因为 CPU 正停留在中断处理程序中。

这也是为什么 xv6 的自旋锁实现与中断控制存在联系。

在常见的 xv6-riscv 实现中，kernel/spinlock.c 的 acquire() 和 release() 会配合 push_off()、pop_off() 等机制管理本地中断状态。其目的之一是避免在持有特定自旋锁期间发生可能导致死锁的本地中断。

不过，这并不意味着所有中断都会被全局关闭，也不意味着关闭中断就能解决所有并发问题。多核系统中，其他 CPU 仍然可能并发执行代码，因此共享数据通常仍然需要锁或其他同步机制。

此外，中断处理程序也不能随意睡眠。中断上下文并不是普通进程上下文，通常不能像普通进程一样等待某个事件并主动让出 CPU。

因此，设计中断处理程序时，需要仔细考虑：

  • 是否会访问共享数据？
  • 是否需要获取锁？
  • 这把锁是否可能被中断打断的代码持有？
  • 是否可能调用睡眠函数？
  • 是否需要将较复杂的工作推迟到普通内核执行路径中？

这些问题把异常控制流与操作系统的并发、锁和调度机制紧密地联系在一起。

8. 外部中断发生在内核态时会怎样？#

前面主要讨论的是用户程序运行期间发生外部中断的情况。

如果 CPU 已经在 S-mode 执行内核代码时发生中断，控制流则会经过另一条入口路径。

xv6 在内核态运行时，将 stvec 设置为 kernelvec，其汇编实现位于：

kernel/kernelvec.S

kernelvec 会保存必要的寄存器状态，并调用 kerneltrap()。后者位于 kernel/trap.c，负责检查内核态陷入原因，并调用相应的处理逻辑，例如 devintr()。

可以将两条路径对比为：

用户态发生中断：

U-mode
  |
  v
uservec
  |
  v
usertrap
  |
  v
devintr

内核态发生中断：

S-mode
  |
  v
kernelvec
  |
  v
kerneltrap
  |
  v
devintr

为什么需要两套入口？

因为用户态与内核态的执行环境不同。

用户态陷入时，CPU 仍然使用用户页表，需要通过 trampoline 保存用户寄存器并切换到内核页表。

内核态陷入时，CPU 已经在内核地址空间中执行，通常不需要重复执行用户态陷入所需的页表切换流程。但仍然需要保存必要的寄存器，确保中断处理结束后能够恢复被打断的内核执行路径。

因此，xv6 为两种场景设计了不同的入口，但可以在后续处理中复用设备中断分发逻辑。

9. 不要把定时器中断与外部设备中断混为一谈#

定时器中断也是操作系统的重要中断来源，但它与 UART、VirtIO 磁盘等外部设备中断并不完全相同。

在常见的 xv6-riscv 实现中，机器态启动代码配置定时器，并通过机器态定时器中断相关机制向监管者态传递时钟事件。监管者态处理时可能表现为软件中断，而不是 PLIC 管理的外部中断。

因此，devintr() 通常会区分：

  • S-mode 外部中断。
  • S-mode 软件中断，例如 xv6 中用于时钟事件传递的路径。
  • 其他异常或中断。

时钟事件可以用于维护系统时钟、触发进程调度等操作，而外部设备中断则主要负责响应设备请求。

二者都属于异常控制流，但不能因为它们都称为“中断”，就认为它们使用完全相同的硬件路径。

四、总结#

异常控制流是连接用户程序、操作系统内核与硬件设备的重要机制。

从 xv6 的实现中，可以总结出几个关键结论。

第一，系统调用和外部中断虽然都会导致控制流转移到内核，但触发机制不同。系统调用由用户程序执行 ecall 主动触发；外部中断通常由设备异步触发。

第二，硬件与操作系统内核共同完成陷入处理。硬件负责记录关键状态、切换特权级并转移到陷入入口；内核负责保存寄存器、切换页表、识别事件、执行处理逻辑，并在适当时机恢复执行。

第三，系统调用是一套完整的受控服务机制。用户程序通过系统调用封装函数传递编号和参数，经过 uservec、usertrap()、syscall() 进入具体的内核实现，最后通过 usertrapret() 和 userret 返回用户态。

第四，外部中断是设备与 CPU 协作的重要方式。PLIC 管理设备中断请求，devintr() 识别中断来源，UART 和 VirtIO 驱动负责处理具体设备事件。

第五，中断机制与并发、锁、睡眠和唤醒机制密切相关。设备事件可能发生在与请求发起者不同的执行路径中，内核必须通过适当的同步机制维护共享状态的一致性。

最后，建议阅读源码时沿着真实的控制流逐层深入，而不是孤立地理解每个函数：

  • 系统调用：user/usys.S → kernel/trampoline.S → kernel/trap.c → kernel/syscall.c → 具体系统调用实现。
  • 用户态外部中断：kernel/trampoline.S → kernel/trap.c → kernel/plic.c → 对应设备驱动。
  • 内核态中断：kernel/kernelvec.S → kernel/trap.c → 中断分发与处理逻辑。
  • 同步机制：kernel/spinlock.c → 设备驱动中的锁、等待与唤醒代码。

只有把这些代码放回完整的执行路径中，才能真正理解 xv6 如何在用户程序、内核和硬件之间实现受控的控制流转移。
