Linux 内核代码风格：官方规范与实践指南#

原始文档：Linux kernel coding style

本文根据 Linux 内核官方文档整理，以中文概括核心规则并补充实践说明。具体开发时，应结合目标内核版本、所属子系统的现有代码和相关 API 文档。

代码风格并非单纯的排版问题。Linux 内核是一个由大量开发者长期协作维护的项目，统一的编码约定可以降低阅读成本，使代码审查更容易进行，也有助于发现资源管理、错误处理和并发访问中的问题。

本文按官方文档的主要主题梳理相关规范，并重点说明这些规则在 C 语言和 Linux 内核开发中的实际意义。

1. 缩进与代码布局#

1.1 使用 8 字符宽度的制表符缩进#

Linux 内核传统代码风格使用 Tab 进行缩进，Tab 宽度为 8 个字符。不要将普通空格当作代码块的缩进字符。

static int process_item(int value)
{
	if (value < 0)
		return -EINVAL;

	return handle_item(value);
}

较宽的缩进能够突出代码层级。当函数需要过多缩进时，也是在提醒开发者：控制流可能过于复杂，需要重新审视函数结构。

1.2 避免一行写多个语句#

不要为了节省行数而将多个语句挤在一行，也不要通过逗号运算符绕过大括号约定。

不推荐：

if (condition) do_this(); do_that();

更清晰的写法：

if (condition) {
	do_this();
	do_that();
}

对于包含多个操作的分支，应使用大括号明确划分代码块。

1.3 避免过深的嵌套#

过多的条件分支和循环会增加理解成本。与其不断增加缩进，不如考虑：

  • 提前处理错误条件并返回。
  • 将独立职责拆分为辅助函数。
  • 简化条件表达式。
  • 减少不必要的控制流层级。

1.4 控制行长度#

官方文档建议通常将单行长度控制在 80 列左右。超长语句应根据逻辑结构合理换行，但不要为了机械满足列数而牺牲可读性。

函数参数较多时，可以按参数列表的结构进行对齐。

另外，不要随意拆分用户可见的日志字符串，否则会增加通过日志文本检索代码的难度。

2. 大括号、空格与运算符#

2.1 大括号的位置#

对于 if、switch、for、while 等非函数代码块，通常将左大括号放在控制语句行末尾：

if (condition) {
	do_something();
}

函数定义则将左大括号放在下一行：

static int calculate(int value)
{
	return value * 2;
}

如果 if 和 else 两个分支中有一个包含多条语句，两个分支都应使用大括号，保持结构一致。

对于只有一条简单语句的分支，通常不必机械地添加大括号，应遵循所在代码的约定并保持清晰。

2.2 空格的使用#

控制关键字后通常添加空格：

if (condition)
	process_item();

函数调用的函数名与左括号之间不加空格：

process_item(value);

指针声明通常将 * 放在变量名一侧：

char *buffer;

大多数二元运算符两侧保留空格：

result = left + right;

一元运算符通常不在操作数之间添加空格：

value = -offset;
ptr = &item;

结构体成员访问运算符 . 和 -> 两侧不添加空格：

item.value = 10;
ptr->value = 20;

2.3 清理行尾空白#

不要在行末留下无意义的空格或 Tab。代码审查时，这类改动会制造噪声，干扰真正的逻辑差异。

3. 命名规范#

C 语言的命名应尽量简洁，但简洁不能以牺牲含义为代价。

3.1 局部变量可以简短#

循环计数器可以使用 i，临时变量可以使用 tmp。如果上下文足以表达含义，就没有必要将所有局部变量都命名为很长的描述性名称。

3.2 全局符号应当具有描述性#

全局变量和公共函数的名称应明确表达其职责。

例如，统计活动用户数量的函数可以命名为：

count_active_users()

避免使用只有作者自己才能理解的缩写。

3.3 避免匈牙利命名法#

不要仅仅为了在变量名中编码类型而添加冗余前缀。C 编译器已经能够检查类型，命名应更多地表达用途，而不是重复类型信息。

3.4 选择中性、清晰的术语#

新增代码中的符号名称和文档应避免引入带有不必要历史歧义的术语。可以根据上下文选择 primary、secondary、leader、follower、allowlist 和 denylist 等更明确的表达。

如果必须兼容现有用户空间 ABI/API，或遵循既有硬件、协议规范，则需要考虑兼容性约束。

4. 谨慎使用 typedef#

不要仅仅为了隐藏普通结构体或指针的真实类型而使用 typedef。

例如：

struct virtual_container *container;

通常比一个无法直接看出底层类型的别名更容易阅读。

官方文档列举了几类合理使用 typedef 的情况：

  • 完全不透明的对象，使用者只能通过规定的访问函数操作。
  • 能够减少整数类型歧义的明确类型抽象。
  • 配合 sparse 等工具创建用于类型检查的新类型。
  • 某些特殊的标准整数类型兼容场景。
  • 需要与用户空间共享、遵循特定类型约定的结构。

Linux 内核中的 u8、u16、u32、u64 等类型便是常见例子。

判断标准是：这个别名是否提供了明确的抽象、兼容性或类型检查价值，而不是单纯缩短声明。

5. 函数设计#

5.1 一个函数尽量只做一件事#

函数应当职责明确，避免将过多互不相关的操作堆积在一个函数中。

官方文档建议将函数长度控制在大约一到两个终端屏幕的范围内，但这不是机械的行数限制。函数复杂度、缩进深度和需要跟踪的局部变量数量都应纳入考虑。

当函数变得难以理解时，可以：

  • 将独立步骤提取为辅助函数。
  • 用清晰的函数名表达操作意图。
  • 减少同时需要跟踪的局部状态。
  • 将复杂的错误处理与正常路径分离。

5.2 函数原型应包含参数名#

即使 C 语言允许函数声明省略参数名，Linux 内核仍倾向于在函数原型中写出参数名称，以帮助读者理解参数的用途。

例如：

int process_buffer(const char *buffer, size_t size);

比只写出类型、不写参数名更有信息量。

函数声明中的存储类别、属性、返回类型、参数以及相关属性也应保持一致的排列顺序，具体顺序应参考官方文档和现有内核代码。

6. 使用 goto 统一资源清理#

在 Linux 内核中，goto 并非一概禁止。当函数存在多个错误出口，而且多个出口需要执行共同的资源释放操作时，使用 goto 可以减少重复代码和嵌套层级。

static int process_data(void)
{
	void *buffer;
	int ret;

	buffer = kmalloc(128, GFP_KERNEL);
	if (!buffer)
		return -ENOMEM;

	ret = process_buffer(buffer);
	if (ret)
		goto out_free_buffer;

out_free_buffer:
	kfree(buffer);
	return ret;
}

上例展示了统一清理的结构。实际代码中，只有在需要跳过后续操作或发生错误时，才应跳转到相应标签；不需要清理的简单错误路径可以直接返回。

标签名称应描述清理动作或跳转目的，例如：

out_free_buffer:

而不是使用含义模糊的 err1、err2。

尤其要注意资源之间的依赖关系。如果某个对象为空，就不能无条件访问其成员进行释放。多个资源的清理顺序应与资源获取顺序及依赖关系相匹配。

在可能的情况下，应测试不同失败路径，确保每种退出路径都能正确释放已经申请的资源。

7. 注释规范#

7.1 注释应补充必要信息#

注释不应该只是把代码逐行翻译成自然语言。

优先说明：

  • 代码要完成什么工作。
  • 为什么选择这种实现。
  • 存在哪些不明显的约束或副作用。
  • 调用者需要满足什么前置条件。

如果代码本身可以清楚地表达操作，就不必重复解释显而易见的执行过程。

7.2 使用规范的多行注释#

Linux 内核常见的多行注释形式如下：

/*
 * This is a multi-line comment.
 * Keep the formatting consistent.
 */

注释格式应统一，不要混合多种无明确理由的排版风格。

7.3 使用 kernel-doc 描述内核 API#

对需要正式文档说明的内核 API，应遵循 kernel-doc 格式及相关文档规范。

可以参考内核源码中的 Documentation/doc-guide/ 和 tools/docs/kernel-doc 相关资料。

同时避免添加大量只重复函数声明信息的样板注释。

8. 编辑器与格式化工具#

代码风格的一致性不应完全依赖开发者手动维护。

官方文档介绍了多种可辅助格式化和检查代码的工具：

  • clang-format：可以帮助调整缩进、参数对齐和部分代码布局。
  • scripts/Lindent：Linux 内核源码中用于辅助格式化的脚本。
  • EditorConfig：可以统一支持该规范的编辑器中的缩进和换行设置。

使用格式化工具时，应注意它的配置是否与目标内核代码风格一致。格式化工具能够改善排版，但无法替代正确的程序设计和逻辑检查。

此外，官方文档不建议在源文件中加入强制修改个人编辑器行为的 modeline。项目可以通过适当的编辑器配置和开发工具来统一规范，而不应随意覆盖每位开发者的个人环境。

9. Kconfig 文件的特殊缩进#

Kconfig 配置文件使用不同于普通 C 源文件的缩进规则。

在 config 定义下，配置项使用一个 Tab 缩进；帮助文本相对于 help 关键字进一步缩进。

示例：

config AUDIT
	bool "Auditing support"
	depends on NET
	help
	  Enable auditing infrastructure.

对于具有明显风险的配置选项，应在提示文本中明确标出风险，帮助配置人员作出知情判断。

10. 数据结构与引用计数#

在多线程或多个执行上下文可能访问同一个对象的场景下，必须明确对象的生命周期管理方式。

引用计数与锁解决的是不同问题：

  • 引用计数用于追踪对象的使用情况，决定对象何时可以释放。
  • 锁用于协调并发访问，保护共享数据的一致性。

二者通常需要配合使用，不能相互替代。

例如，一个对象可能需要分别追踪不同类别使用者的数量，再根据这些计数决定对象何时真正释放。Linux 内存管理和文件系统中都存在这类设计。

只要其他执行上下文仍可能找到或使用一个对象，就必须保证对象的生命周期管理是正确的，不能让对象在仍被使用时提前释放。

11. 宏、枚举与内联函数#

11.1 常量宏和枚举命名#

定义常量的宏名通常使用大写字母：

#define BUFFER_SIZE 256

多个相关常量可以优先考虑使用 enum，使它们之间的关系更加明确。

11.2 优先考虑内联函数，而非函数式宏#

函数式宏可能出现以下问题：

  • 参数被重复求值。
  • 运算符优先级导致意外结果。
  • 宏内部变量与调用者的局部变量冲突。
  • 宏展开后改变调用者的控制流。
  • 调用形式看起来像普通函数，实际行为却并不相同。

对于普通函数逻辑，应优先考虑静态内联函数等更容易进行类型检查的形式。

11.3 多语句宏需要正确封装#

如果确实需要定义包含多个语句的宏，通常应使用 do { ... } while (0) 封装，避免宏在调用位置产生不符合预期的语法行为。

定义包含表达式的宏时，还应注意参数和整体表达式的优先级，并为必要的表达式添加括号。

12. 内核日志#

内核日志应当简洁、明确，并尽可能提供对调试有价值的信息。

驱动开发中，应根据上下文选择合适的日志接口，例如：

  • dev_err()：设备相关错误。
  • dev_warn()：设备相关警告。
  • dev_info()：设备相关信息。
  • dev_dbg()：设备相关调试信息。
  • pr_err()、pr_warn()、pr_info()：不直接关联特定设备的日志。

设备工作正常时，不应无节制地输出日志。调试信息应优先使用相应的调试接口，以便根据编译配置或动态调试设置控制输出。

日志内容应做到简洁、清晰、便于检索。不要仅仅为了显示一个数字就添加无意义的括号，也不必机械地在每条日志末尾添加句号。

13. 内存分配#

内核提供了多种通用内存分配接口，例如 kmalloc()、kzalloc()、vmalloc() 和 vzalloc()。选择接口时，应参考其 API 文档，考虑内存连续性、分配大小、调用上下文和失败处理等要求。

13.1 使用合适的大小表达方式#

传递结构体大小时，应优先采用目标内核版本推荐的对象大小辅助接口，避免重复写出类型名称而导致指针类型变更后大小表达式没有同步修改。

官方文档当前示例采用 kmalloc_obj() 等对象分配接口：

p = kmalloc_obj(*p, ...);

对于数组，也有相应的数组分配辅助接口。使用这些接口时，应确认目标内核版本是否提供，并参考对应 API 的使用约定。

13.2 避免不必要的指针类型转换#

kmalloc() 等返回 void * 的接口，在 C 语言中可以直接赋值给其他对象指针类型，因此通常不需要显式转换。

13.3 关注整数溢出#

分配数组时，需要确保元素数量与单个元素大小相乘不会发生溢出。合适的内核分配辅助接口可以提供相应的大小检查，避免分配空间不足。

另外，应了解所用分配接口在失败时的日志行为，避免重复输出没有额外价值的错误消息。

14. 不要过度使用 inline#

inline 不是一个保证程序更快的开关。

过度内联可能增加生成代码体积，扩大指令缓存占用，并增加内存压力。编译器通常能够根据优化信息自行决定是否内联。

因此，内联应服务于明确的设计目的，例如替代存在问题的函数式宏，或者配合编译期常量优化，而不是仅仅因为函数很短就一律添加。

15. 函数返回值与命名#

函数返回值应当具有一致且容易理解的语义。

Linux 内核中常见的错误码约定是：

  • 0 表示成功。
  • 负的 -Exxx 值表示失败。

而用于判断某个条件是否成立的谓词函数，通常使用布尔语义：

  • 非零表示条件成立。
  • 0 表示条件不成立。

例如：

int add_work(void);
bool device_is_ready(void);

这里的命名和返回类型能够帮助调用者理解函数的用途。

不要混淆错误码与布尔值。对于公共函数和导出函数，应尤其注意遵守一致的约定。

如果函数返回的是计算结果本身，例如长度、数量或指针，则应遵循该返回值对应的 API 语义，并明确约定失败时的表示方式。

16. 合理使用 bool#

在适合表达真假状态的场景中，优先使用 bool 通常能够提高代码可读性。

bool is_ready;

is_ready = true;

使用 bool 时，应使用 true 和 false 表达逻辑值，不必为了得到 0 或 1 而额外进行 !! 转换。

不过，在结构体布局、缓存行对齐或特定大小约束非常重要的场景中，应考虑 bool 的大小与对齐可能随架构而变化。多个真假状态也可以根据实际布局需求使用位域或适当的固定宽度类型。

17. 优先使用内核已有的宏#

编写内核代码时，不要轻易重复实现内核已经提供的通用功能。

例如，计算数组元素数量可以使用：

ARRAY_SIZE(array)

而不是每次都手写 sizeof(array) / sizeof(array[0])。

内核还提供了用于计算结构体成员大小、进行类型安全的最小值与最大值比较等辅助宏。

在实现通用功能之前，先检查 include/linux/ 等相关头文件，有助于避免重复造轮子，并与内核已有的约定保持一致。

18. 不要在源文件中强制设置个人编辑器配置#

源文件不应随意加入强制改变编辑器模式、缩进宽度或编译命令的特殊标记。

不同开发者可能使用不同的编辑器和工作流。个人编辑器配置应尽量放在各自的开发环境或项目认可的配置文件中，而不是隐式地嵌入源文件。

19. 内联汇编#

在架构相关代码中，必要时可以使用内联汇编访问处理器指令或平台功能。但如果普通 C 代码已经能够完成任务，就不应无故引入汇编。

实用原则包括：

  • 尽可能将重复的汇编操作封装成辅助函数。
  • 简单的汇编操作可以使用 C 参数传递数据。
  • 大型、复杂的汇编代码通常应放在独立的 .S 文件中，并通过相应的 C 函数声明提供接口。
  • 只有在编译器无法正确识别副作用时，才应根据需要使用 volatile；滥用它可能限制优化。
  • 多条汇编指令应清楚分行，避免破坏生成汇编的格式。

内联汇编涉及编译器约束、寄存器、内存副作用和架构语义，实际编写时还应参考 GCC 文档及目标架构的相关资料。

20. 条件编译#

尽可能减少在 .c 文件中散布大量 #if 和 #ifdef，因为它们会让控制流分散在多个编译配置之间，增加理解和维护难度。

一种可行的设计是，在头文件中为不同配置提供真实实现或空操作实现，再由 .c 文件统一调用。这样可以让普通 C 代码保持清晰。

在适合的场景中，可以使用 IS_ENABLED() 将配置选项转化为普通的 C 条件表达式：

if (IS_ENABLED(CONFIG_SOMETHING)) {
	/* Optional behavior */
}

编译器可以对配置条件进行常量折叠。不过，如果条件分支引用的符号在某些配置下根本不存在，仍需要使用适当的预处理条件。

对于较长的条件编译块，应在 #endif 处注明对应的配置条件，方便阅读和检查。

21. 避免不必要的内核崩溃#

内核开发应优先考虑可诊断性和可恢复性，而不是遇到异常就直接终止整个系统。

21.1 谨慎使用 panic()#

panic() 会导致内核进入严重故障处理流程，应当谨慎使用。只有在确实无法继续运行的场景，例如启动阶段发生无法恢复的关键错误时，才可能有合理理由使用它。

21.2 优先考虑 WARN 系列宏，而不是新增 BUG()#

官方规范不建议新增 BUG()、BUG_ON() 和 VM_BUG_ON() 等调用。应根据情况考虑 WARN_ON_ONCE() 等警告接口，并在可行时提供恢复逻辑。

这并不意味着所有异常都可以忽略，而是要求开发者认真考虑是否存在更安全的错误处理方式。

21.3 不要滥用警告#

WARN*() 应用于真正异常、按设计不应发生的情况，而不是普通运行流程中可能自然出现的条件。

频繁输出警告会污染内核日志，甚至影响系统性能。对于需要通知用户但并不意味着内部状态已经严重损坏的情况，可以考虑更合适的日志接口。

21.4 编译期断言#

BUILD_BUG_ON() 等编译期检查机制可以用于验证静态条件。在适当场景中，这种方式能够在构建阶段发现问题，而不必等到运行时才暴露。

总结：提交内核代码前的检查清单#

完成内核模块、驱动或其他 C 代码后，可以按照以下清单进行自检。

代码布局#

  • 使用符合内核约定的 Tab 缩进。
  • 大括号位置、空格和运算符格式保持一致。
  • 没有无意义的超长行、行尾空白或多个语句挤在一行的情况。
  • 控制流没有不必要的深层嵌套。

命名与设计#

  • 全局函数和变量名称能够表达用途。
  • 没有仅为隐藏类型而添加的 typedef。
  • 函数职责清晰，局部状态数量合理。
  • 函数原型包含有意义的参数名称。

资源与错误处理#

  • 所有资源获取失败路径都经过检查。
  • 资源释放顺序正确，没有重复释放或遗漏释放。
  • goto 清理标签具有明确含义。
  • 函数返回值遵循一致的语义约定。
  • 分配大小和数组长度计算考虑了溢出风险。

可维护性与调试#

  • 注释解释必要的意图和约束，而不是重复代码。
  • 使用内核已有的宏和辅助 API，而非重复实现。
  • 宏没有隐藏控制流或造成参数重复求值。
  • 日志清晰、适量，且使用合适的日志级别。
  • 避免不必要的内联汇编、条件编译和内核崩溃操作。

工具与参考资料#

  • 使用合适的格式化工具辅助检查代码。
  • 根据目标内核版本核对相关 API 和规则。
  • 阅读所在子系统的现有实现，保持风格一致。
