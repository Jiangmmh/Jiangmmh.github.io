1. 本章概览#

第一章主要介绍 Linux 内核的历史背景、基本概念、设计特点以及开发社区。

本章并不会深入某个具体的内核子系统，而是先回答几个基础问题：

  • Unix 是如何诞生的？Linux 与 Unix 有什么关系？
  • Linux 是什么？Linux 内核与 Linux 操作系统有什么区别？
  • 内核究竟负责什么工作？
  • Linux 内核与传统 Unix 内核相比，有哪些设计特点？
  • Linux 内核如何进行版本发布和协作开发？

理解这些背景，有助于我们在后续阅读 Linux 源码时建立整体认识。

2. Unix 的历史#

2.1 Unix 的诞生#

Unix 最初诞生于 1969 年的贝尔实验室（Bell Labs），主要开发者是 Ken Thompson 和 Dennis Ritchie。

Unix 的出现与一个更早的操作系统项目有关：Multics。

Multics 是一个由多个研究机构共同参与的大型操作系统项目，目标是构建一个支持多用户、多任务的计算环境。但由于项目过于复杂，开发进展缓慢，最终贝尔实验室退出了该项目。

Ken Thompson 等人希望拥有一个更加简单、实用的交互式操作系统，于是开始在一台 PDP-7 计算机上实现新的操作系统。这项工作逐渐演变成 Unix。

Unix 发展过程中有几个重要节点：

时间事件
1969Unix 在贝尔实验室诞生
1971Unix 被移植到 PDP-11
1973Unix 使用 C 语言重新实现
1977Unix System III 发布
1982AT&T 发布 Unix System V

其中，1973 年是 Unix 历史上非常重要的一个节点：Unix 从汇编语言实现转向 C 语言实现。

这在当时具有重要意义。操作系统通常与具体硬件架构联系紧密，使用汇编语言实现意味着移植到新平台时需要大量重写代码。

C 语言提供了更高层次的抽象，使 Unix 可以在不同硬件平台之间移植，同时仍然保留直接操作硬件的能力。

关键点：C 语言的出现不仅改变了应用程序开发，也深刻影响了操作系统的发展。Unix 是早期使用高级语言实现、并因此获得良好可移植性的操作系统之一。

2.2 Unix 的发展与分化#

随着 Unix 的传播，不同公司和研究机构开始在 Unix 基础上进行修改和扩展，逐渐形成多个分支。

其中比较重要的是：

  • System V：AT&T 开发的 Unix 系统分支，后来成为商业 Unix 的重要基础。
  • BSD（Berkeley Software Distribution）：加州大学伯克利分校发展出的 Unix 分支，引入了许多重要的系统功能和接口。
  • 其他商业 Unix：例如 IBM 的 AIX、HP 的 HP-UX、Sun 的 Solaris 等。

虽然这些系统在实现上存在差异，但它们在接口和设计理念上有很多共同点。

这也促成了 Unix 标准化工作的开展。

其中，POSIX（Portable Operating System Interface）是非常重要的一套标准，定义了操作系统向应用程序提供的一系列接口。

例如，进程创建、文件操作、进程间通信等功能，都有相应的标准接口。

需要注意：

  • Unix 最初是一个具体的操作系统。
  • 后来 Unix 逐渐成为一类具有共同设计传统和接口规范的操作系统的统称。
  • Unix-like 则通常指在接口和设计理念上与 Unix 相似的操作系统，并不意味着它们都具有 Unix 商标认证。

Linux 就属于 Unix-like 操作系统。

3. Linux 的诞生#

3.1 Linux 的起源#

1991 年，Linus Torvalds 开始开发 Linux。

当时，他使用的是基于 Intel 80386 处理器的个人计算机，希望实现一个可以在自己的计算机上运行的操作系统内核。

在 Linux 出现之前，Minix 是一个很有影响力的教学操作系统。它由 Andrew S. Tanenbaum 开发，主要用于操作系统教学和研究。

Linux 的早期开发受到 Unix 和 Minix 的影响，但它并不是直接基于 Minix 源码开发的。

Linux 最初是一个个人项目，后来逐渐吸引了世界各地的开发者参与。

随着网络的发展，开发者可以通过互联网交换代码、提交补丁、讨论设计问题，Linux 逐渐发展为一个大规模的协作开发项目。

3.2 GNU 与 Linux 的关系#

理解 Linux 的发展，还需要了解 GNU 项目。

GNU 项目由 Richard Stallman 于 1983 年发起，目标是构建一个自由的类 Unix 操作系统。

GNU 项目已经开发了大量操作系统基础工具，例如：

  • GCC：GNU Compiler Collection。
  • GNU Binutils：包含汇编器、链接器等工具。
  • GNU Bash：命令行 Shell。
  • GNU Coreutils：提供常见的命令行工具。
  • glibc：GNU C Library。

Linux 内核与这些工具结合，构成了我们熟悉的 GNU/Linux 操作系统环境。

因此，需要区分几个概念：

名称含义
Linux KernelLinux 内核，负责管理硬件资源并提供内核服务
GNU提供编译器、Shell、基础工具和运行库等软件
Linux Distribution将 Linux 内核、系统工具、软件包和配置整合起来的完整操作系统发行版

例如 Ubuntu、Debian、Fedora 都是 Linux 发行版。

关键点：Linux 严格来说指的是内核，而我们日常使用的 Linux 操作系统通常是由 Linux 内核与大量用户空间软件共同组成的。

4. 操作系统与内核概述#

4.1 什么是内核？#

操作系统的核心任务是管理计算机硬件资源，并向应用程序提供统一、受控的使用接口。

内核（Kernel）是操作系统中最核心的部分。

它位于应用程序和硬件之间，负责管理 CPU、内存、设备以及其他系统资源。

典型的内核职责包括：

子系统主要职责
进程管理创建、销毁进程，管理进程状态和调度
内存管理管理物理内存、虚拟内存和地址空间
文件系统提供文件、目录和文件访问接口
设备驱动管理硬件设备，提供统一的设备访问方式
网络子系统实现网络协议栈和网络通信
系统调用接口为用户程序提供进入内核的受控入口
中断处理响应硬件中断和处理器异常

这些子系统并不是彼此完全独立的，它们会通过内核内部接口相互协作。

例如，用户程序执行 read() 读取文件时，可能涉及：

  1. 系统调用接口接收请求。
  2. VFS 根据文件描述符找到对应的文件对象。
  3. 文件系统处理具体文件操作。
  4. 如果需要访问磁盘，进一步调用块设备层。
  5. 块设备层与设备驱动协作完成 I/O。

这说明内核并不是一堆孤立功能的集合，而是一个相互协作的复杂系统。

4.2 用户态与内核态#

现代处理器通常提供不同的特权级别，用于隔离普通应用程序和操作系统内核。

在 Linux 中，可以从两个角度理解程序的执行环境：

  • 用户态（User Mode）：普通应用程序运行的环境，权限受到限制。
  • 内核态（Kernel Mode）：内核运行的环境，可以执行特权操作并管理系统资源。

应用程序不能直接随意访问硬件或修改其他进程的内存，而是通过系统调用请求内核完成这些工作。

例如：

int fd = open("test.txt", O_RDONLY);

应用程序调用 open() 后，通过系统调用机制进入内核，由内核完成文件打开操作，并将结果返回给用户程序。

这里需要区分：

  • 系统调用（System Call）：用户程序请求内核服务的接口。
  • 内核函数（Kernel Function）：内核内部实现具体功能的函数。
  • 库函数（Library Function）：用户空间库提供的函数，可能进一步封装系统调用，也可能完全在用户态完成。

这几个概念在阅读源码时非常重要。

4.3 内核架构：宏内核与微内核#

操作系统内核有多种组织方式，其中比较典型的是宏内核（Monolithic Kernel）和微内核（Microkernel）。

宏内核

宏内核将许多操作系统核心功能放在同一个内核地址空间中运行。

例如，进程管理、内存管理、文件系统、网络协议栈和设备驱动等，都可以作为内核的一部分运行。

优点：

  • 内部调用通常不需要跨越用户态和内核态边界。
  • 子系统之间可以直接调用内核接口。
  • 通常具有较高的执行效率。

缺点：

  • 内核代码规模较大，模块之间的依赖关系复杂。
  • 内核中的错误可能影响整个系统。
  • 需要谨慎管理共享数据和并发访问。

微内核

微内核只将最基础的机制放在内核中运行，例如：

  • 线程调度。
  • 基本内存管理。
  • 进程间通信（IPC）。

文件系统、网络服务和部分驱动等功能可以放在用户空间运行，通过 IPC 相互通信。

优点：

  • 模块之间隔离性较好。
  • 某些服务发生故障时，可以降低对整个系统的影响。
  • 系统结构更加模块化。

缺点：

  • 服务之间需要进行 IPC。
  • 用户态与内核态之间的切换可能带来额外开销。
  • 系统设计和通信机制也会带来复杂性。

需要注意，宏内核和微内核是架构组织方式，不应该简单理解为性能和安全性的绝对高低。

5. Linux 与传统 Unix 内核的区别#

Linux 遵循 Unix 的许多设计理念，但并不是对某个传统 Unix 内核的简单复制。

它在内核组织、并发执行、模块化和硬件支持等方面形成了自己的特点。

5.1 Linux 是宏内核，但支持模块化#

Linux 通常被归类为宏内核。

进程管理、内存管理、文件系统、网络协议栈等核心功能都运行在内核空间。

但 Linux 并不是一个完全静态、不可扩展的内核。

它支持可动态加载的内核模块（Loadable Kernel Modules，LKM）。

例如，可以将某个设备驱动编译成模块，在系统运行过程中动态加载：

# 加载模块
sudo insmod my_driver.ko

# 查看已加载的模块
lsmod

# 卸载模块
sudo rmmod my_driver

也可以使用 modprobe 加载模块，它能够处理模块依赖关系。

模块化带来的好处是：

  • 不需要将所有驱动都编译进内核镜像。
  • 可以根据实际硬件和系统需求加载功能。
  • 某些内核功能可以在系统运行期间动态扩展。

但需要注意，内核模块并不是运行在用户空间的独立服务。模块加载后仍然运行在内核态，拥有较高权限。

5.2 Linux 支持内核线程#

内核线程（Kernel Thread）是只在内核空间执行的线程。

它们不需要像普通用户进程那样拥有完整的用户地址空间，主要用于执行内核后台任务。

例如，Linux 中存在一些内核线程，用于处理内存回收、块设备 I/O 等后台工作。

可以通过以下命令查看：

ps -ef

其中，一些内核线程通常以 k 开头命名，例如：

kthreadd
kworker
kswapd

内核线程的一个重要特点是：

它们执行内核代码，但并不代表所有内核代码都运行在内核线程中。

普通用户进程通过系统调用进入内核执行代码，同样是在内核态运行。

5.3 Linux 支持对称多处理（SMP）#

SMP（Symmetric Multiprocessing，对称多处理）是指多个处理器或 CPU 核心共同参与系统运行，并能够访问共享的系统资源。

在 SMP 系统中：

  • 多个 CPU 可以同时执行不同任务。
  • 多个 CPU 可能同时访问内核共享数据。
  • 内核必须处理并发访问和数据同步问题。

这也是 Linux 内核同步机制如此重要的原因。

例如，多个 CPU 同时修改一个共享链表，如果没有适当的锁保护，就可能破坏链表结构。

Linux 提供了多种同步机制，例如：

  • 自旋锁（Spinlock）。
  • 互斥锁（Mutex）。
  • 读写锁（Read-Write Lock）。
  • 原子操作（Atomic Operations）。

这些机制将在后续章节中深入讨论。

5.4 Linux 支持内核抢占#

传统内核可能会在某些内核代码执行期间禁止其他任务抢占当前任务。

Linux 2.6 系列进一步增强了内核抢占能力。

内核抢占（Kernel Preemption）意味着：在满足相应条件时，内核可以暂停当前正在执行的内核任务，让更高优先级的任务运行。

它能够改善系统的响应延迟，尤其适用于对实时响应有要求的场景。

但需要注意：

  • 内核抢占不等于任意位置都可以安全抢占。
  • 持有某些锁或处于特定临界区时，仍然需要禁止抢占。
  • 抢占能力越强，对内核同步和代码正确性的要求也越高。

5.5 Linux 的可移植性#

Linux 并不局限于某一种处理器架构。

它支持多种硬件平台，例如：

  • x86 / x86-64
  • ARM / ARM64
  • RISC-V
  • PowerPC
  • MIPS（历史及特定版本支持情况不同）

可移植性要求内核尽可能将通用逻辑与体系结构相关代码分离。

例如：

  • 进程调度算法具有较强的通用性。
  • 页表操作需要考虑不同处理器架构的内存管理单元。
  • 中断控制器和异常入口通常与具体架构密切相关。

在 Linux 源码中，可以通过 arch/ 目录观察不同体系结构相关的实现。

关键点：Linux 的可移植性并不意味着所有架构都使用完全相同的实现，而是通过抽象接口和架构相关代码，将通用内核逻辑与硬件差异隔离开。

6. Linux 内核版本#

Linux 内核持续迭代，版本号用于标识内核的发布版本。

例如：

6.12.10

可以将其理解为主版本、次版本和修订版本的组合。

不过，版本号的具体含义和发布规则会随着内核开发周期变化。

6.1 书中介绍的版本管理背景#

第三版《Linux Kernel Development》出版于 2010 年，主要讨论 Linux 2.6 内核时期的开发模式。

在 Linux 2.6 之前，曾经使用过这样的开发版本约定：

  • 偶数次版本号通常代表稳定系列。
  • 奇数次版本号通常代表开发系列。

例如，2.4 系列是稳定版本，而 2.5 系列是开发版本。

但 Linux 2.6 系列改变了这种发布模式，采用持续集成和较短周期发布稳定版本的方式。

因此，阅读本书时需要注意：

书中介绍的是 Linux 2.6 时代的内核开发和发布背景，不应将其中的版本管理规则直接套用到今天的 Linux 内核。

6.2 当前内核版本的阅读方式#

阅读内核源码时，首先需要明确自己正在研究的内核版本。

可以通过以下命令查看：

uname -r

查看当前运行的内核版本。

如果是在源码目录中，也可以通过：

make kernelversion

查看源码对应的版本。

研究内核时，建议始终明确：

  • 当前使用的是哪个版本？
  • 阅读的是哪个分支？
  • 代码是否来自稳定版本，还是开发中的版本？
  • 某个函数或数据结构是否已经在后续版本中发生变化？

内核源码变化很快，版本差异可能直接影响函数签名、数据结构和实现流程。

7. Linux 内核开发社区#

Linux 内核是一个典型的大规模开源协作项目。

它并不是由某一家公司的开发团队独立完成，而是由全球大量开发者、维护者和企业共同参与。

7.1 内核开发的基本模式#

Linux 内核开发通常采用邮件列表和补丁（Patch）进行协作。

一个典型的开发流程是：

  1. 开发者发现问题或提出新功能。
  2. 修改内核源码。
  3. 生成 Git Patch。
  4. 将补丁发送到相关维护者和邮件列表。
  5. 其他开发者进行代码审查和讨论。
  6. 维护者决定是否接受补丁。
  7. 补丁逐步进入相应的开发分支。

这意味着 Linux 内核开发不仅要求开发者能够写出正确的代码，还要求能够清晰地描述设计、解释修改原因，并接受其他开发者的审查。

7.2 维护者与子系统#

Linux 内核包含大量子系统，例如：

  • 进程调度。
  • 内存管理。
  • 文件系统。
  • 网络协议栈。
  • 块设备层。
  • 设备驱动。

这些子系统通常由不同的维护者负责。

维护者负责：

  • 审查相关代码。
  • 讨论设计方案。
  • 管理子系统代码。
  • 将经过审查的补丁提交到更高层的集成分支。

这种分层维护模式，使得规模庞大的内核项目能够由许多相对独立的开发团队协作完成。

7.3 为什么代码审查如此重要？#

内核代码与普通应用程序代码有很大的区别。

内核代码运行在高权限环境中，错误可能导致：

  • 系统崩溃。
  • 内存损坏。
  • 数据丢失。
  • 安全漏洞。
  • 并发竞态。
  • 死锁。

因此，内核开发非常重视代码审查。

一个补丁不仅需要证明功能正确，还需要考虑：

  • 是否引入竞态条件？
  • 是否正确处理错误路径？
  • 是否可能造成内存泄漏？
  • 是否影响其他体系结构？
  • 是否破坏已有接口？
  • 是否存在性能回退？

关键点：内核开发不仅是实现功能，更重要的是在复杂的并发环境和硬件环境中保证系统的正确性。

9. 复习时需要记住的几个问题#

读完第一章，建议能够回答下面这些问题：

1. Linux 和 Unix 是什么关系？

Linux 并不是传统 Unix 的直接派生版本，而是一个受 Unix 设计理念影响的 Unix-like 内核。

2. Linux Kernel 和 Linux 操作系统有什么区别？

Linux Kernel 是内核；完整的 Linux 操作系统还包含用户空间程序、系统库、工具和应用软件等。

3. Linux 为什么被称为宏内核？

因为进程管理、内存管理、文件系统和网络协议栈等核心功能主要运行在内核空间。

4. Linux 是宏内核，为什么又支持模块化？

宏内核描述的是内核功能的运行位置和组织方式；模块化描述的是内核功能的组织与加载方式，两者并不矛盾。

5. 为什么 SMP 会增加内核开发的复杂度？

多个 CPU 可以同时访问共享数据，必须使用适当的同步机制避免竞态条件和数据损坏。

6. 为什么 Linux 内核需要支持抢占？

抢占能够改善系统响应能力，但同时也提高了内核并发控制的复杂度。

7. Linux 内核为什么能够运行在不同的硬件平台上？

通过将通用内核逻辑与体系结构相关实现分离，并为不同硬件平台提供对应的底层支持。
